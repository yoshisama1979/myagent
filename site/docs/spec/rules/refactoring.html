1. これは何をするルールか

外から見た振る舞いを1ミリも変えずに、内部の品質だけを上げるときの手順書。
機能追加・仕様変更・バグ修正は別の作業であり、同じコミットに混ぜない。

このリポジトリで実際に効いた例＝重複の集約（spotY(spot)／終了コードの決め方を1箇所へ／
クールダウン状態ファイルの書き込みを1箇所へ）、デッドコード削除（tag_attr）、定数化（_METRICS）。
いずれも「片方だけ直して不整合になる芽」を摘む目的だった。この目的から外れる整形はしない。

2. 絶対に変えないもの

  • 外部から観測できるすべて：コマンドの引数・終了コード・標準出力の文言・生成ファイルのパスと中身。
  • 無人ループが依存する状態：カーソル（state.json 等）・マーカー・ロック・台帳の書式。

ここを変えると次の無人実行で静かに壊れる（取りこぼし・二重処理）。触るなら仕様変更として別途合意。

  • 判定ロジックの結果：宛先判定・冷却・金額照合・文字コード・許可リスト。分岐の順序も含めて同じ結果を返すこと。
  • ログ・通知の文言：grep で拾っている箇所があるため、文言変更は挙動変更とみなす。
  • 秘密の扱い：.env の読み方を共通化する場合も、値をログ・例外メッセージ・コミットへ出さない規律は不変

（automation.md が正）。

3. スコープ（既定は STRICT）

スコープ範囲誰の許可が要るか
STRICT（既定）git diff --staged に含まれるファイル・行だけ不要（/commit-pipeline ステップ3の通常運転）
同一ファイル全体そのファイルの diff 外の行も触る社長に一言（何を・なぜ・影響範囲）
複数ファイル横断共通化・ライブラリ抽出など社長の明示承認。原則は「直さず起票」→ §7

⚠️ STRICT には原理的な限界がある：差分の中しか見ないので、ファイルをまたぐ重複は永久に見つからない
（実測 2026-08-11＝.env の読み込みを python 11本・shell 5本が各自で実装していた。
毎コミットで11回リファクタしてきたが、どれも「直前コミットの後始末」で、この重複には一度も触れていない。
同日の横断作業で python は 11→3本まで減らしたが、shell 5本・atomic write 10本・flock 6本の自作は残っている）。
横断的な重複はこのルールでなく §7 の起票経路で扱う。差分レビューと全体最適は別物だと自覚すること。

4. 複数エージェント同居のための鉄則（このリポジトリ固有・最重要）

同じ作業ツリーで他のエージェントが同時に別の作業をしている。リファクタは広い範囲に触りやすく、
最も混入事故を起こしやすい作業なので、次を必ず守る：

  1. git add . を使わない。必ず pathspec で自分のファイルだけをステージする。
  2. ステージ後に git diff --cached --stat を必ず読む。身に覚えのないファイル・行数があれば止めて調べる。
  3. 共有ファイル（data/partner/*.md・site/office/index.html 等）に自分の1行だけを入れたいときは、

git show HEAD:<path> に自分の変更だけを当てた内容を git hash-object -w + git update-index --cacheinfo で
ステージする（作業ツリーは触らない＝他エージェントの未コミット分を巻き込まない）。

  1. 他エージェントがインデックスに自分の分を置いている場合は git commit -- <pathspec> で回避する

（git restore --staged で相手の作業を剥がさない）。

  1. 実例＝2026-08-11 に office/index.html（他エージェントの233行）と milestones.md（13行）を巻き込みかけ、

上記3・4で回避した。過去には3回、混入したまま commit している（[[project_git-index-race]]）。

4.5 隔離して直す（worktree の手順・横断的変更のとき）

STRICT を超える変更（§3 の「複数ファイル横断」）は、main の作業ツリーで直接やらない。
git worktree で別フォルダを生やし、そこで書いて検証し、通ったものだけ main に入れる。
失敗しても丸ごと捨てられる＝同居エージェントに一切影響しない。

git worktree add ../myagent-refactor -b refactor/<用件>   # 作業場を生やす（追跡ファイル12MBだけ・.git は共有）
# …作業・検証・コミット…
cd /home/vpsuser/projects/myagent                          # ★必ず main 側へ戻ってから
git merge --ff-only refactor/<用件>
git worktree remove ../myagent-refactor && git branch -d refactor/<用件>

踏んだ落とし穴（2026-08-11・3回まわして全部当たった）

  1. git checkout <別ブランチ> は同居環境では禁じ手＝作業ツリーの中身が丸ごと入れ替わり、

他のエージェントの足元からファイルが消える。ブランチを分けたいなら必ず worktree。

  1. worktree の中から git merge / git worktree remove を打たない。前者は自分自身にマージして

「Already up to date」になるだけ、後者は立っている床を外して cwd を失う。必ず main 側へ戻ってから。

  1. 枝が古くなったら、当てずに作り直す。ブランチを切った後で main 側が進んでいると、

git checkout <枝> -- <file> はその後の変更を巻き戻す（実際に、後から main に入った
新モード204行を消しかけた）。枝を捨てて、今の版に同じ修正をやり直す方が速くて安全。

  1. .env や data/ は worktree に無い（git 管理外だから）。実データでの検証が要るときだけ

.env をコピーし、検証が終わったら必ず消す（コミット前に git status で確認）。

  1. マージ前に、対象ファイルが main 側で編集中でないか見る（git status --short <paths>）。

編集中なら git がマージを拒否する＝それは正しい動作。強行せず、
①相手がコミットするのを待つ ②衝突しないファイルだけ先に入れる（git checkout <枝> -- <安全な paths>）
のどちらかを選ぶ。相手の未コミット作業を上書きする選択肢は無い。

5. 挙動不変を「示す」（言うだけにしない）

リファクタは「たぶん同じ」で通してはいけない。同じであることを機械で示してからコミットする：

  1. 関連する回帰スイートを流す（testing.md §7 の表で対象を引く）。**触ったツールにテストが無いなら、

まずテストを書く**（リファクタの前提条件＝安全網が無い場所で内部をいじらない）。

  1. 前後の出力を突き合わせる：読み取り専用ツールは実データで実行し、出力の diff がゼロであることを確認する

（実例＝gsc-fetch の定数抽出は summary・queries の結果一致を確認してからコミットした）。
⚠️ 実データの結果を報告に貼るときは固有名詞・金額をマスクする。

  1. 無人ループが呼ぶものは env -i HOME=... PATH=/usr/bin:/bin の空環境でも通す

（対話環境でだけ動く形に退化していないか）。

  1. 示せないなら、やらない。「動作確認できないが安全なはず」は、このリポジトリで最も高くついてきた判断。

6. やる／やらないの判断

やる（＝不整合の芽がある）

  • 同じロジックが2箇所以上にあり、片方だけ直す事故が実際に起こりうる（起きた前例があるなら最優先）
  • 定義のみで呼ばれていない関数・到達しないコード（デッドコード）
  • 同じ値・同じ式の繰り返し（マジックナンバー・SQLの集計式など）
  • 判定が複数箇所に散っていて、テストがどこを叩けばよいか決められない

やらない

  • 既に簡潔で、読んで意図が分かる
  • 「統一感」「好み」だけが理由（＝挙動不変でも履歴のノイズになり、他エージェントの差分と衝突する）
  • 将来の拡張を見越した抽象化（使う場面が来てから作る）
  • 意図が推測でしか分からない箇所＝直さずに質問する（推測修正が別の場所を壊すのは testing.md §3 と同じ）

7. 横断的な改善は「直さず起票」する

STRICT を超える改善（共通ライブラリの抽出・データモデルの変更・複数ツールの統合）は、
その場で実装しない。次のどちらかに載せる：

  • 統括（overseer）へ：O-NNN として起票し、月次の全体最適棚卸し／「社長との全体最適セッション」の議題にする。
  • 経営パートナー台帳へ：社長の判断が要るもの（工数・優先度）は A-NNN／P-NNN。

起票には必ず実測値を添える（「重複が多い」ではなく「11本が各自で実装」）。
数字が無い改善提案は優先度を付けられず、埋もれる。

8. 手順

  1. 差分を自分で取る（git diff --staged／git show <hash>）。貼ってもらうのを待たない。
  2. 問題点を挙げる（重複・デッドコード・ネスト・命名・責務）。無ければ「リファクタリング不要」と報告して終わる

——これは正しい結論であり、何かしら変更するより価値がある。

  1. 1コミット1目的に分ける。混ぜない。
  2. §5 で挙動不変を示す → コミット。
  3. コミットメッセージは既存の型に合わせる：

<対象>のリファクタリング（<元コミット> の後始末）：<何を1箇所へ集約したか>

9. 報告フォーマット（/commit-pipeline ステップ3で出す）

  • 実施内容：何を、どのファイルで
  • 挙動不変の根拠：流したテスト（スイート名と項目数）／前後で一致を確認した出力
  • スコープ：STRICT／同一ファイル／横断（横断なら許可の経緯）
  • やらなかったこと：気づいたが STRICT 外だったもの＝§7 で起票した番号（起票せず流さない）
  • 質問事項：意図が読めず触らなかった箇所
