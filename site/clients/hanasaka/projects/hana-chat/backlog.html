⚠️ 用語の区別（混同注意）

HANAチャット（サービス本体） クライアントのウェブサイトに設置する AI チャット。エンドユーザー向け。これが販売対象。
システム内チャット（管理側） HANAチャットの管理画面の中にあるチャット。クライアント自身（HANAチャットを契約している事業者）が使う。サービス本体とは別物。

AI学習（RAG）強化

① 学習データ登録 — 自由入力 → 自動整理 → 登録

  • ☐RAGに登録したい内容を雑に入力するだけで、AIが整理して登録する機能
  • ☐学習時に警告する機能 2026-07-31 社長メモ：登録しようとしている内容に問題があるとき（既存と重複／既存と矛盾／情報が足りない 等）、登録の瞬間に指摘する
  • ユーザーは思いついた内容をそのまま投げ込めばよい（箇条書きでも口語でも可）
  • AI側で構造化（タイトル / カテゴリ / 本文 / タグ 等）してから登録
  • 「登録前のプレビュー → 承認 → 確定」のフローにするかは要検討
  • 目的：学習データ更新のハードルを下げ、RAG の鮮度と網羅性を上げる

社長の問い（2026-07-31）：「学習時のインストラクション、ルール化の方がいい？」

添えた一案（判断は開発）：警告とルール化は排他ではない。正はルール（インストラクション）側に一本化し、警告はそのルールから生成する形にすれば、二重管理にならない。ルールを1箇所直せば警告の挙動も追随する。

出典：partner台帳 A-046（Slack 2026-07-31 10:10 投函）

② 会話分析 → 学習内容の改善提案

  • ☐ユーザー会話を分析し、回答品質を上げるための学習内容の改善提案をする機能

想定の分析観点：

  • 回答できなかった / 回答精度が低かった質問の抽出
  • 「うまくいかなかった会話」の原因の切り分け（2026-05-28 追加）：抽出して終わりにせず、なぜ今の学習状態では回答できなかったか を 学習データ不足／表現の揺れ／文脈不足 に分類する
  • 同じトピックの質問が繰り返されていないか
  • 既存ナレッジで不足している領域の検出
  • エンドユーザーの会話傾向・質問内容の要約（2026-05-28 追加）：改善提案とは別に、クライアントが自社の顧客インサイトとして読める形の要約を出す（decisions.html の「運営者側にユーザーの課題・質問データを提供」という価値に直結）

出力イメージ：

  • 「この質問に答えられるよう、◯◯のドキュメントを追加してください」
  • 「既存ドキュメント X の説明が不足。以下を追記推奨」

目的：運用しながら自律的に賢くなる RAG にする（学習データの保守を自動補助）

届け方：分析結果を システム内チャットで対話的に引き出せるようにしたい（2026-05-28 追加）。静的なレポート画面だけにするか、チャットで掘れるようにするかは要検討 → 「実装前に詰めたい点」#4 と関連。

③ 学習データの類似整理（2026-05-28 追加）

  • ☐学習データの中で似通った項目を発見し、統合・整理を補助する機能
  • ☐答えられなかった質問を、似たものでまとめる 2026-07-31 社長メモ：②が拾った未回答ログを類似でグルーピングし、「何件も聞かれているのに答えられていない塊」を上に出す
  • 重複・矛盾・冗長を 見える化する（似ている項目をグルーピングして提示）
  • ②と同じ「類似判定」を使い回せる（学習データ側に向ければ重複整理、未回答ログ側に向ければ質問のまとめ）＝項目設計は一度で済ませるのが得。未回答ログ → 類似まとめ → ナレッジ充実 のループは回答率＝商品価値（解約防止）に直結する（出典：partner台帳 A-046）
  • 目的：①で登録のハードルを下げるほどデータは増えて散らかる。増やす機能と対で、掃除する機能が要る
  • 矛盾したデータが混在すると RAG の回答精度がそのまま落ちるため、②の「回答できなかった原因」とも地続き

④ 検索方法の拡張 — ハイブリッド検索（2026-05-28 追加）

  • ☐現状の RAG（ベクトル検索）に、キーワード検索等を組み合わせて必要な情報を引き出す
  • 現代のエージェントがよく行う方法（ツール呼び出し・複数手法の併用）を取り入れる
  • ベクトル検索は「意味は近いが用語が違う」に強く、型番・固有名詞・略語の完全一致に弱い。キーワード検索の併用はそこを埋める
  • この4件の中で、既存ユーザーの回答精度に最も直接効く可能性がある（①③は運用の質、②は改善サイクル、④は今日の回答そのもの）

⑤ ナレッジグラフの導入 2026-07-31 社長メモ

  • ☐HANAチャットにナレッジグラフを入れる（社長の意向・2026-07-31）

⚠️ これは①〜④と重さが違う。「検索方式を1つ足す」ではなく 知識の持ち方そのものの変更（文章の断片を並べて持つ → 概念と関係で持つ）。

先に入れるなら、①の登録フォーマット・③の類似整理の単位・④の引き方がすべてその上に乗る。後から入れるなら作り直しが出る。①〜④の着手順（論点 #9）の前提そのものが変わるため、他より先に方針を決める必要がある。

  • 効きどころ：「A社の担当者は誰か」「この製品に対応する型番は」のような関係をたどる質問。ベクトル検索が最も苦手な領域で、④のキーワード併用でも埋まらない
  • コスト：グラフの設計・構築・維持が要る。①の自動登録がそのままグラフを育てられるかが実務上の分かれ目（人手で関係を張り続ける作りにすると運用が持たない）
  • 判断は開発の領域。ここは「社長の意向として記録し、設計判断の前提に置く」までが本ファイルの役割

出典：partner台帳 A-046（Slack 2026-07-31 10:19 投函）
