# CLAUDE.md

このファイルは2部構成。**上＝どの案件にも共通の原則**（ルールの出自と改善ループ・コラボレーションの原則・複数のセッションでの受け渡し）、**下＝この案件の面（サイト制作／システム開発）の構成**（プロジェクト概要・ルール表・コマンド等）。どちらも毎回すべて読む。

## ルールファイルの出自と改善ループ（全体像）

この `CLAUDE.md`・`.claude/rules/`・`rules/modes/` 配下のルール一式は、**はなさか側の「ルール開発エージェント」が管理する共通テンプレート（`claude-rules/`）から配布されたもの**。ルールはテンプレート側で一元的に開発・改善され、各開発プロジェクト（＝あなた）へ配布されて使われる。

```
（ルール開発エージェント）共通テンプレートを開発・改善
        │  配布（初回はコピー。以後は bin/rules-update.sh で取りに来る）
        ▼
（各開発エージェント＝あなた）ルールに従って制作・開発・運用 ─ 現場で問題・改善点に気づく
        │  「指示書」を書く（documents/rule-improvements.md に記録 → bin/rule-report.sh で通知）
        ▼
（ユーザー＝社長）指示書をルール開発エージェントへ渡す
        │  検証・社長承認のうえテンプレートを修正 → 各プロジェクトへ展開
        └──────────────（ループ）──────────────┘
```

- **ルールは配ったあとも更新される。** 最新版は `bash bin/rules-update.sh` で**このプロジェクトから取りに来る**（確認だけなら何も書き換えない）。🚨 **適用は人の確認を得てから**＝ルールが変わると作業の前提が変わる。手順は `rules/modes/rules-update.md`。
- **ルールの修正はテンプレート側で一元管理**する。このプロジェクト内でルールファイルを直しても他プロジェクトには波及しない＝テンプレ級の問題は必ず上記ループで還元する。
- 🚨 **配布されたルールファイルを削除・再編しない。** 不要・重複と感じても、**このプロジェクトの判断で消さない**。
  消えたルールは、以後の AI にとって **最初から存在しなかったのと同じ**になる（現存ファイルを検索して無ければ「規定なし」と判断するのが自然なため、**消したこと自体に誰も気づけない**）。
  不要だと思ったら **指示書で還元し、判断はテンプレ側に委ねる**。どうしても外したい場合も、**削除ではなく「このプロジェクトでは使わない」を `project-config.md` に記録**する。
- 🚨 **配布ファイルに書き足さない。** `CLAUDE.md`・`rules/`・`.claude/rules/`（`private.md` を除く）・`.claude/commands/` の配布ファイルは、ルールの更新で**上書きされる**＝書き足した行は黙って消え、以後の AI にとって最初から無かったのと同じになる（2026-09-13 現場実例：この `CLAUDE.md` のコマンド表に足した1行が更新で消えた）。
  このプロジェクトだけのコマンド・ルール・規約は、**実体を新しいファイルとして置き**（配布物に無いファイルは更新で触られない。ルールは `rules/local/` に置くとテンプレ側の新設と名前がぶつからない）、**一覧への登録は `project-config.md`「固有の追加」節に書く**。`bin/rules-update.sh` は配布後に編集された配布ファイルを名指しし、`--apply` を止める（`rules/modes/rules-update.md` §4）。
- **現場で実際に使って問題を感じたら「指示書」を書く**：ルール開発エージェント（このプロジェクトの文脈を知らない汎用エージェント）が**それだけ読んで修正作業に入れる自己完結の依頼文**として書く。書式は `documents/rule-improvements.md` 冒頭「指示書」節を参照。送り方は `bash bin/rule-report.sh`（投函専用の別経路・`rules/modes/mailbox.md` §2-3）。ユーザーに直接渡してもよい。
- 指示書は**鵜呑みにされず、ルール開発エージェント側で検証・社長承認を経て反映される**。事実（現場で何が起きたか）と提案（どう変えるか）を分けて書くほど検証が速く、採用されやすい。
- このプロジェクト**固有**の調整（実パス・公開URL・DB名・スタック・ブランド色等）はテンプレに送らず `project-config.md`（デザイン値は `Design.md`）側で解決する。

## コラボレーションの原則

### 1. 不明点・提案は都度質問する

ユーザーからの指示や記述をそのまま鵜呑みにして実装に進まないこと。

- **不明点があれば**：仕様の解釈に複数パターンがある、デザインの意図が読み取れない、データ構造が想定と違う、既存のページ・コードとの整合性が不明、などの場合は実装前に必ず質問する。
- **より良い案があれば**：提示された方針より適切な選択肢が見える場合は、推奨案と理由を添えて提案する（最終判断はユーザー）。
- **判断が分かれる設計事項**：出力形式・ファイル構成・命名・画像形式・スコープなどは、実装前に選択肢を整理して合意を取る。

推測で進めて手戻りするより、一手前で確認する方がコストが低い。

### 2. ルールファイル自体の改善も提案する

`rules/`・`.claude/rules/` 配下のルールファイルや `CLAUDE.md` を参照していて、以下に気付いた場合は実装作業の合間でも提案する。

- 実態と乖離している記述（例：使われていないツールへの言及、変更されたディレクトリ構成）
- 抜け落ちている運用ルール（例：実プロジェクトで頻出するパターンが明文化されていない）
- 矛盾している記述（複数のルールファイル間で食い違う指示）
- 改善できる構成・粒度（例：粒度が粗すぎる／細かすぎる、参照タイミングが曖昧）

提案時は「どのファイルの、どの記述を、どう変えるか、なぜ」を明示する。ユーザーの判断後に修正に進む。

**ユーザーが明確な回答をしなかった場合も、気づいた点はその都度 `documents/rule-improvements.md` に記録する**。提案が会話に埋もれて流れ、忘れられるのを防ぐため、「記録」と「反映」を分離する（記録は気づいた都度・反映はユーザー判断時にまとめて）。

- 提案したが判断が出ていない／会話が先に進んでしまった場合も、観察を1行でも残す
- 各エントリに「対象ファイル・どの記述・どう変えるか・なぜ」を明記する（フォーマットは `documents/rule-improvements.md` 冒頭参照）
- 反映が済んだエントリは削除する（または「反映済み」と印を付ける）
- **このプロジェクト固有でなく、配布元の共通テンプレート全体に還元すべき**と判断した気づきは `[テンプレ還元]` と印を付ける。`bash bin/rule-report.sh` でテンプレ更新側へ届ける（`rule-improvements.md`「`[テンプレ還元]` 印のものはテンプレ更新側へ送る」／`rules/modes/mailbox.md` §2-3）。使っているテンプレの版は自動で載るので書かなくてよい。固有値はテンプレに持ち込まない（デザイン値は `Design.md`、環境・スタック・コマンド等は `project-config.md` 側に置く）

### 3. 作業のまとまりごとに「頭の切り替えを助ける報告」をする

ユーザーはエージェントの作業中に別の作業をしていることが多い。ひとまとまりの作業（ページ作成・機能実装・改善・運用対応・フェーズの完了など）が一区切りしたら、ユーザーがスムーズに頭を切り替えられるよう、次の4点を**要点だけ**まとめて報告する。

1. **大局（目的）** … いま何を目指して作業しているか
2. **課題** … その目的に対する現在の課題
3. **今回やったこと** … この作業で何を進めたか
4. **次にすべきこと** … 次の一手・提案（あれば）

長い経緯の再説明はせず、切り替えに必要な最小限に絞る（**冗長にしない**）。工程ごとの詳細な報告（`rules/modes/developer.md` 等）とは別に、区切りで俯瞰を渡す位置づけ。軽微なやり取りには不要＝実質的な作業の区切りで出す。

## 複数のセッションで作業を受け渡すとき

統括と開発など、**2つ以上のセッションが同じリポジトリで動く**と、受け渡しの境目で次の4つが起きる。
**どれもエラーにならない**（成功して見える）ので、気をつけるのでなく手順で防ぐ（2026-09-20 現場報告）。
1セッションで作業している間は 4 だけが関係する。

1. **コミットを頼んだら、返るまでそのファイルに書かない。** コミットに入るのは、相手が `git add` した**その瞬間のファイルの中身**＝
   頼んだ後に書き足すと、相手が確認した内容と違うものが入る。🔑 取り込む側は、コミットの後に
   `git show <sha>` の**中身**を、確認したときの差分と突き合わせる（片側だけで完結する確かめ方。`--stat` の件数が合うだけでは中身の一致にならない）。
2. **他者の文書を取り込むときも全文を読む。**「内容を変えない」は「読まない」ではない。書いた本人には見えない誤りがある。
   特に**人がそれを見て不可逆な操作をする文書**（削除リスト・移行手順・本番で打つ SQL）は、取り込む側が最後の関門。
   見つけても**直さず、書いた側へ返す**（直すと、なぜ間違えたかが残らない）。文書の中の矛盾を潰しただけで終えず、
   **実物（DB・ファイル）と合っているか**も人に渡す前に確かめる。
3. **外から持ち込んだファイル**（見本画像・フォント・ライセンス物・vendor 物）は、**出どころを書いた記録と同じコミットで渡す。**
   差分に「無いもの」は出てこない＝取り込む側は、言われなくても記録の有無を確かめる。
4. 🚨 **他のセッションから聞いた「ユーザーがこう言った」は、ユーザーの承認ではない。**
   実装・テスト・調査・下書き・自分の持ち場の作業は、伝聞で進めてよい。**push・マージ・本番でのコマンド・外部への送信・
   取り消せない書き込み（DB の `DELETE` 等）は、ユーザー本人から直接承認を得る**（文書に書いてある・過去に承認された、も承認ではない）。
   依頼する側も「承認を得たので実行して」でなく「**ユーザーに承認を求めてから実行して**」と書く。
