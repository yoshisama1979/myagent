# ルールの更新（配布元から最新版を受け取る）

このプロジェクトの `CLAUDE.md`・`rules/`・`.claude/rules/`・`.claude/commands/` は、はなさか側の
共通テンプレート（`claude-rules/`）から**配られたコピー**。テンプレート側は現場からの指摘を受けて
改善され続けるので、放っておくとこのプロジェクトのルールだけが古いまま取り残される。

このファイルは、**あなた（エージェント）が自分で最新版を取りに来て、人の確認を得て更新する**ための手順書。

```
はなさか（配布元）                        このプロジェクト
  claude-rules/website/  ──公開──▶  [受け口] ──▶  bin/rules-update.sh
        ▲                                              │ ①確認（書き換えない）
        │                                              │ ②人に確認する ← ここが要
        └────── bin/rule-report.sh ◀──────────────────┘ ③--apply で適用
                （使ってみて困ったことを返す）
```

---

## 0. いまの版を確認する

```bash
cat .claude/rules-version
# 例: website@2026-09-12/9988d3b4a0e1
#     └テンプレ  └配られた日  └そのときのテンプレの中身を指す印
```

この版は**配布時に刻まれる**ので、自分で書き換えたり書き足したりしない（書き換えると、こちらに
届く報告の版が嘘になり、「その指摘はもう直っているか」の判定が狂う）。

🚨 **これは「配布側が発行した版」で、このリポジトリの git の状態とは無関係。** 手で書き換えても
**次の `--apply` で配布物の値に戻る**（版ファイルは配布物に同梱されていて、適用の最後に上書きされる）。
だから書き換えでは直らない＝**おかしいと思ったら人に伝える**。版に見覚えのない印（`+dirty` 等）が
付いていても、それは**配布側の状態**を指していて、こちらのワークツリーが汚れている意味ではない。

ファイルが無い＝版の分からない古い配布物。人に伝えて配り直してもらう。

## 1. 初回の設定は人がやる（あなたはやらない）

受け取りには `.env` の3行（受け口2つとトークン1本）が要る。この値は社長が発行して人が置く。
**あなたが用意することはできない**ので、無ければ止まって人に伝える。

```
RULE_REPORT_URL=...     ルールの問題を送る先
RULE_UPDATE_URL=...     ルールの最新版を取りに来る先
RULE_REPORT_TOKEN=...   この案件のトークン（1本で両方に使う）
```

🚨 **この値をコミットしない・ログに出さない・チャットに貼らない。** `.env` は git 管理外にする。

- **`.env` を置くときに、`.gitignore` へ次の2行を足すところまでが人の作業**（`.env` を置いた人しか
  気づける位置にいない。2026-09-18 現場実例＝`.gitignore` に入っておらず `?? .env` で追跡候補に出ていた）：
  ```
  .env
  .claude/rules-backup/
  ```
- `bin/rules-update.sh` は毎回これを機械で確かめ、**無視されていなければ ⚠️ を1行出す**（止めはしない）。
  見たら人に伝える。
- 🚨 **画面に「.env が既に git に入っています」と出たら、トークンはコミット済み**＝`.gitignore` に足しても
  無視されない（追跡中のファイルは無視の対象外）。人に伝えて、`git rm --cached .env`・`.gitignore` への追記・
  **トークンの再発行**を頼む（push 済みなら値はもう外にある）。

## 2. 更新の手順（3ステップ）

### ステップ1 ── 確認する（安全・何も書き換えない）

```bash
bash bin/rules-update.sh
```

| 終了コード | 意味 | 次にすること |
|---|---|---|
| `0` | 最新（更新なし） | 何もしない |
| `10` | **更新がある** | ステップ2へ（変更点が画面に出る） |
| `1` | エラー | §6 の表を見る |

### ステップ2 ── 人に確認する（🚨 省略禁止）

ルールが変わると、いま進めている作業の前提が変わる。**勝手に適用しない**。
画面に出た変更点を、次の形で人に伝えて判断を仰ぐ。

> ルールの新しい版が出ています（いま `website@2026-09-10/8a4d272f` → 最新 `website@2026-09-12/9988d3b4`）。
> 主な変更は「共有ファイルの所有者表の追加」「反証の作法の追加」の2件です。
> 作業の前提が変わるので、いま更新してよいか教えてください。

**渡す判断材料はこの3つだけでよい**：①いまの版と最新の版 ②変更点（画面の出力そのまま） ③いま動いている作業に影響しそうか。

🚨 **一覧に `[🚨重要]` で始まる行があったら、それは「適用の前に済ませる手当て」の指示。** 一覧は
新しい順＝後から積まれたコミットに押し下げられるので、**最後まで目を通す**。見つけたら上の3つに
**加えて**人に伝える（手当ての中身は件名そのもの、または §6 の該当節にある）。

### ステップ3 ── 適用する（承認を得てから）

```bash
bash bin/rules-update.sh --apply
```

適用が終わったら、**必ず**：

1. `CLAUDE.md` と、いま使っているルールファイルを**読み直す**（記憶している内容は古い）
2. 変更点を人に共有する（相手も同じ前提で話す必要がある）
3. 作業中のカードがあれば、前提が変わっていないか見直す
4. **`project-config.md` に記入欄（節）が増えていないか突き合わせる**（§4「守られるファイルに節が増えても、誰も教えてくれない」）＝増えた分は流れてこないので、自分で足す

## 4. 何が上書きされ、何が守られるか

| | 例 | 扱い |
|---|---|---|
| **ルール層** | `CLAUDE.md` / `rules/modes/*` / `.claude/rules/*`（`private.md` を除く） / `.claude/commands/*` / `bin/*.sh` | **上書きされる**（テンプレート側が正） |
| **案件の記録** | `documents/`（handoff・pending-issues・rule-improvements 等） / `project-config.md` / `Design.sample.md` / `.claude/rules/private.md` | **触らない**（このプロジェクトが育てたもの） |
| あなたが作った成果物 | `src/` `assets/` `Design.md` など | **触らない**（テンプレートに含まれない） |

守るファイルの一覧は配布物に同梱されていて、更新のたびに配布元から渡される＝このファイルに
書き写された一覧が古くなることはない。

### 🚨 守られるファイルに節が増えても、誰も教えてくれない

`project-config.md` は**触らない**側なので、**テンプレート側で記入欄（節）が増えても流れてこない**。
しかも `rules-update.sh` が出すのは「触らない 4（案件の記録）」という**件数だけ**で、ファイル名も
増えた節も言わない。その結果、ルール本文が「`project-config.md` の◯◯節を見ろ」と指示しているのに
**手元にその節が無い**状態が起きる（2026-10-30 の見積もりルール改訂で実際に起きた）。

**適用したら、節を自分で突き合わせる。** 白紙のフォームは**控え**（`.claude/rules-base.tar.gz`）の中にある。
控えは `--apply` のたびに置き換わるので、**適用直後の控え＝いま入っている版**＝そのまま比較対象になる。

```bash
diff <(tar xzOf .claude/rules-base.tar.gz --wildcards '*/project-config.md' | grep '^## ') \
     <(grep '^## ' project-config.md)
```

**向きを間違えないこと**＝上の並び順は **左が控え（テンプレート）・右が手元**。

- **`<` で出た節**（左にしかない）＝**テンプレートにあって手元に無い**。**控えからその節の本文ごと
  取り出して貼り、記入する**（値が分からなければ人に一度だけ聞く。`（記入。例: …）` のままの行を
  金額や設定の根拠にしない）。🚨 **見出しの 1 行だけを貼らない**＝記入項目の無い空の節ができ、
  「ルールが指す記入欄が無い」状態がそのまま残る。本文は次で取り出す（`## 見積もり` を足す節の見出しに替える）：

  ```bash
  tar xzOf .claude/rules-base.tar.gz --wildcards '*/project-config.md' \
    | awk '/^## 見積もり/{f=1;print;next} f&&/^## /{exit} f'
  ```
- **`>` で出た節**（右にしかない）＝手元にあってテンプレートに無い。🚨 **消さない。**「固有の追加」か、
  テンプレートが消した節かのどちらかなので、人に伝える（このあとの⚠️「テンプレートから消えたファイルは…」と同じ扱い）。
- 向きを覚えずに済ませたいなら、**末尾に `| grep '^<'` を足す**＝足す節だけが出る
  （`comm` でも書けるが、日本語の並び順で `comm: file 1 is not in sorted order` になるので使わない）。

- 🚨 **全文の `diff` を使わない。** 手元は記入済み・控えは `（記入。例: …）` なので**ほぼ全行が差分**になり
  読めない。**見出し（`^## `）だけを比べる。**
- 🚨 **`--wildcards` を省かない。** 省くと「アーカイブ内に見つかりません」で左が**1行も取れず**、
  手元の節が全部 `>` 側に出る＝**「足す節は無い」と読めてしまう**。🚨 **終了ステータスでは気づけない**
  （プロセス置換 `<(…)` の中の失敗は外側に伝わらず、`diff` の終了ステータスは**通常の差分と同じ `1`**）。
  見分けるのは**出力の形**＝左が 0 行なら、先頭が `0a1,N`（`0a` ＝「左の 0 行目のあとに足す」）になる。
  これが出たら差分ではなく**取り出しの失敗**。
- 節の中の項目まで見るなら、同じ形で `grep -o '^- \*\*[^*]*\*\*'` を比べる。
- **同じことが `documents/` と `Design.sample.md` にも起きる**（どれも「触らない」側）。台帳の記入欄が
  増えていないかは、同じ手で `documents/` 配下のファイルも比べられる。
- まだ一度も適用していない案件には控えが無い。その場合は**初回の `--apply` で控えができる**ので、
  適用の直後にこの突き合わせを行う。

⚠️ **テンプレートから消えたファイルは、こちらでは消えない**（残ったまま）。見覚えのない古い
ルールファイルに気づいたら、消さずに人に伝える（`rules/modes/` のルールを勝手に消さないのは
`CLAUDE.md`「配布されたルールファイルを削除・再編しない」のとおり）。

🚨 **配布ファイルに書き足していたら、更新は止まる。** `--apply` のたびに、適用した配布物を
`.claude/rules-base.tar.gz`（**控え**）に残す。次の確認・更新では、控えと中身が違う配布ファイル
＝**配布後にこのプロジェクトで編集したもの**を名指しする（コミット済みでも見つける。CRLF⇔LF の違いだけなら数えない）。
`--apply` はそれを上書きする前に止まる。

- 書き足した行は `project-config.md`「固有の追加」節へ移し、配布ファイルからは消してから流す（`CLAUDE.md`「配布ファイルに書き足さない」）。何を書き足したかは `git log -p -- <パス>` で分かる
- 控えは**コミットしておく**（別のマシンや別の人が更新しても比べられる）

`--apply` が止まるのは次の3つ。どれも**消えて構わないと人が判断したときだけ** `--force` で進む：

| 止まる理由 | 何が起きているか | すること |
|---|---|---|
| 配布後に編集された配布ファイルがある | 書き足しが上書きで消える | 書き足しを「固有の追加」へ移してから流す |
| テンプレートに新しく入ったファイルと同じ名前のファイルがある | 案件で作ったファイル（固有のコマンド等）が上書きで消える | 案件のファイルを別の名前に移し、「固有の追加」の登録も直してから流す |
| 控えが無い・読めない・版が合わないまま、新しい版を適用しようとした | 書き足しがあっても見つけられない | `git log -p` で配布ファイルに書き足しが無いことを確かめ、人が判断したら `--force`（適用すると控えができ、次回からは自動で調べる） |

**控えが無いとき**（この仕組みが入る前に配られた案件・初めての更新前）は、**最新の版のうちに**
`bash bin/rules-update.sh --apply` を流すと、いまの版の配布物を取ってきて控えだけ作る（ルールは1文字も書き換えない
＝このときに限り人の確認は要らない）。最新のうちなら、控えが無くても確認のたびに配信中の配布物と比べて名指しする。

- ⚠️ **`--force` で適用すると、控えは新しい版に置き換わる**＝消した書き足しは以後名指しされない。取り戻すときは `.claude/rules-backup/<日時>.tar.gz`（§5）か `git` から
- 適用が途中で止まったら（書き込めない・Ctrl+C・kill）、書いた分を退避から戻し、新しく置いたファイルと作ったディレクトリも消して止まる（一部だけ新しい状態を残さない＝次回「書き足し」と誤検知して止まり続けない）。戻しきれなかったときはそう言い、退避の場所を示す
- 上書き先が同じ名前のディレクトリ・特殊ファイルなら、**`--force` でも**書く前に止まる（`cp` はディレクトリの中に書いて「成功」してしまうため）
- 確認だけの実行は、**プロジェクトには何も残さない**（控えも作らない）。作業用の一時ファイルは OS の一時領域に作り、終了時に消す

## 5. 戻したいとき

更新は上書きの前に**必ず退避**を取る。

```bash
ls .claude/rules-backup/          # 20260912-101530-4242.tar.gz のような退避（日時-プロセス番号）
tar xzf .claude/rules-backup/<日時>.tar.gz   # プロジェクトルートで展開すると元に戻る
```

git 管理下なら `git diff` で何が変わったかを読めるし、`git checkout -- <path>` でも戻せる。
退避は溜まるので、`.gitignore` に `.claude/rules-backup/` を足しておく（無ければ人に伝える）。
控え（`.claude/rules-base.tar.gz`）は**無視しない**＝コミットする（§4）。

🚨 上書き対象に**未コミットの変更があると更新は止まる**（黙って消さないため）。先にコミットするか、
消えて構わないと人が判断したときだけ `--force` を付ける。

## 6. うまくいかないとき

| 画面に出るもの | 意味 | すること |
|---|---|---|
| `RULE_UPDATE_URL / RULE_REPORT_TOKEN が .env にありません` | 設定されていない | 人に伝える（§1）。あなたは値を作れない |
| `失効／期限切れ` | トークンが止められている・期限切れ | 人に伝えて再発行を依頼 |
| `テンプレートが紐づいていません` | トークンにテンプレの指定が無い | 人に伝えて再発行を依頼 |
| `まだ配信されていません` | 配布元がまだ公開していない | 待つ。急ぎなら人経由で依頼 |
| `サーバに接続できません` | 受け口に届いていない（社内網の外にいる等） | ネットワークを人に確認。**勝手に別経路を探さない** |
| `SHA256 不一致` | 取得が壊れた | もう一度実行する。続くなら人に伝える |
| `Python 3.7 以上（python3 または python）が見つかりません` | Python が無い、または 3.6 以前（古いと Windows で照合が必ず外れるため入口で止める） | 人に伝えて Python 3.7 以上を入れてもらう（`python --version` で版を見る）。**別の版を勝手に探して入れない** |
| `上書き対象に未コミットの変更があります` | 消えると困る変更がある | 先にコミット（§5） |
| `配布後にこのプロジェクトで編集された配布ファイル` | 配布ファイルに書き足してある。上書きすると消える | 書き足しを `project-config.md`「固有の追加」へ移す（§4）。**確認の段階でも出る**＝人に伝える材料に含める |
| `同じ名前のファイルが、このプロジェクトに既にあります` | テンプレートの新しいファイルと案件のファイルがぶつかった | 案件のファイルを別の名前に移す（§4） |
| `控え（.claude/rules-base.tar.gz）がありません／読めません／版が合いません` | 書き足しを調べられない | 最新のうちなら `--apply` で控えを作る。新しい版が出ていれば §4 の表のとおり |
| `書き込んだ分を元に戻しました` | 適用の途中で止まった（書き込めない・中断） | 原因を取り除いてもう一度。版は進んでいない |
| `元に戻しきれませんでした` | 戻す途中でも失敗した＝一部だけ新しい可能性がある | **人に伝える**。画面に出た退避を展開して戻す（§5）。勝手に `--force` で上書きし直さない |
| `通常のファイルではありません` | 上書き先が同じ名前のディレクトリ等 | 人に伝える。案件のものなら別の名前へ移す |
| **Windows で、配布ファイルがほぼ全部**「同じ名前のファイルが、このプロジェクトに既にあります」 | 改行コードの不具合（Windows の Python が一覧に `\r` を付けていた。2026-11-06 以降の版で修正）。**書き足しの判定も効いていない**おそれがある | 🚨 **`--force` で押し切らない**（書き足しの保護も一緒に外れる）。まず控え（`.claude/rules-base.tar.gz`）と手元を突き合わせ、書き足しが無いことを確かめてから人に判断してもらう。根本は**この版以降へ更新すれば直る** |

**どれも「送れなかった／取れなかった」で止まってよい。**「たぶん最新だろう」と推測して先へ進まない。

### 🚨 何度やっても同じ所で構文エラー・`command not found` で止まるとき

**このスクリプト自身が配布物に入っている**ので、**適用の途中で自分が差し替わる**ことがある。bash は
スクリプトを**バイトオフセットで逐次読む**ため、新しい中身が長いと読み取り位置がずれ、**行の途中から
実行される**＝`行 504: …: command not found` や `予期しないトークン … 構文エラー` になる。
🚨 **巻き戻しが働いて旧版のスクリプトが残るので、もう一度実行しても同じ所で同じように落ちる。**
（2026-09-18 に現場で発生＝exit 127・TB-019。スクリプト側は 2026-11-01 の版で直したが、**直った
スクリプトを受け取る1回だけ**は旧版で走るので、ここを通る可能性がある）

**まず自分のスクリプトが新旧どちらかを見る**（手当てが要るのは旧版だけ）：

```bash
grep -c '^main() {$' bin/rules-update.sh     # 0 なら旧版＝下の手当てが要る / 1 なら済み
```

**手当ては1回だけ。**「配布物に入っていない名前」で走らせれば、自分を上書きしないので最後まで走る。

```bash
# ① いまのスクリプトを、配布物に入っていない名前へコピーする
cp bin/rules-update.sh bin/rules-update-run.sh

# ② コピーを走らせる（走っているのはコピーなので、本体が上書きされても最後まで走る）
bash bin/rules-update-run.sh --apply

# ③ 後片付け（本体 bin/rules-update.sh は②で新しくなっている）
rm -f bin/rules-update-run.sh
```

- **なぜ効くか**：配布物に入っているのは `bin/rules-update.sh`。走らせているのは
  `bin/rules-update-run.sh` で**配布物に無い**ので、②はこのファイルを上書きしない。
- 🚨 **`--force` もコミットも要らない**（実測済み）。②で版・控え・ルールがそろって新しくなり、
  本体スクリプトも差し替わって、以後は `bash bin/rules-update.sh` が普通に動く。
- 🚨 **curl で配布物を取り直す手順に書き換えないこと。** トークンを
  `-H "Authorization: Bearer …"` で渡すと **curl の argv に乗り、`ps` / `/proc` から同じマシンの
  他の利用者に見える**（このスクリプトが `--config` 経由にしているのはそのため）。`.env` の読み取りも
  **CRLF・`export` 付き・`=` の周りの空白・引用符・`RULE_UPDATE_URL` が無い案件での導出**に
  対応が要る＝**自分で書き直さない。上のコピーなら、その処理ごとそのまま使える。**
- ⚠️ **`bin/rules-update.sh` を直接上書きして `--apply` しない。** 控えと中身が違うので
  「配布後に編集された配布ファイル」で止まり、未コミットなら git の検査でも止まる（どちらも実測）。
- この手順は**人に伝えてから**行う（ルールが変わる＝作業の前提が変わるので §2 の原則は同じ）。

---

## 7. やってはいけないこと

- ❌ **人に確認せずに `--apply` する**（作業の前提が黙って変わる）
- ❌ **作業の途中（カードの実装中）に適用する**
- ❌ `.claude/rules-version` を手で書き換える（報告の版が嘘になる。しかも**次の `--apply` で戻る**＝§0）
- ❌ 配布されたルールファイルを手で編集して黙っている（更新で上書きされて消える。直したいことは
  `documents/rule-improvements.md` に書き、`bash bin/rule-report.sh` で配布元へ送る。このプロジェクトだけの
  追加は `project-config.md`「固有の追加」へ）
- ❌ トークンをコミット・ログ・チャットに載せる
- ❌ 取れなかったのに「更新した」と報告する
- ❌ **適用後に `project-config.md` の節を突き合わせないまま終わる**（ルールが指す記入欄が手元に無いまま進む＝§4）
