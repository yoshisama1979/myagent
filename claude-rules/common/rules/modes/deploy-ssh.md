# SSH で上げる反映手順（リポジトリ経由のデプロイの簡易版）

> **いつ読むか**：本番（または検証環境）へファイルを上げる手順を提示するとき・上げるとき・`bash bin/deploy-ssh.sh` が止まったとき。
> **道具**：`bin/deploy-ssh.sh`（このルールと一緒に配られる）。設定は `.deploy/<対象>.conf`（見本＝`.deploy/production.conf.sample`）。

---

## 0. この手順の位置づけと、使えるかどうかの判断

**正式な反映は、リポジトリを通したデプロイ**（自動デプロイ、またはサーバーがリポジトリから取得する方式）。
この手順は、その整備が規模に見合わない案件（ウェブサイトの小さな修正が中心、など）のための**簡易版**。
FTP で手元のファイルを上げていた運用を置き換える。

簡易版でも次の2つは省かない。これがあるので、後でリポジトリ経由に移るときもそのまま移れる。

- **上げてよいのは push 済みのコミットだけ**（手元にしか無い内容は上げない）
- **本番との食い違いは機械で見つけて止める**（人の目視に頼らない）

### 使える条件（すべて満たすこと）

| 条件 | 確かめ方 |
|---|---|
| Git のリポジトリがあり、リモート（共有リポジトリ）に push できる | `git remote -v` |
| `main`（設定の `BRANCH`）に直接コミットする運用 | `git branch --show-current` |
| サーバーに SSH の**鍵**でログインできる（パスワード入力なし） | `ssh <ホスト名> true` が何も聞かれずに終わる |
| サーバーで `sh`・`find`・`tar`・`sha256sum`（または `shasum`）が使える | `bash bin/deploy-ssh.sh preflight` |
| 上げる内容がリポジトリのファイルそのもの（ビルド不要）、またはビルド結果をコミットしている | ― |

### 使えない場合（この手順を使わない）

| 状況 | どうするか |
|---|---|
| SSH が使えない（FTP・SFTP のみ） | 従来の手順で上げる。`check.md` J（ウェブ）／`deploy.md`（システム）に従う |
| 上げる成果物を毎回ビルドして作る（コミットしていない） | リポジトリ経由のデプロイを整える（`deploy.md`）。または成果物をコミットする運用に変えてから使う |
| データベースの変更を伴う | **この手順の対象外**。DB の変更は別手順で行い、ファイルの反映と順序を決めてから進める（システムは `deploy.md` §3） |
| 自動デプロイ・コンテナでのデプロイ | 対象外（それぞれの仕組みに従う） |

### どちらを使うかの既定

- **リポジトリ経由**：システム案件、ビルドが要る案件、複数人が頻繁に反映する案件
- **この簡易版**：上記以外のウェブサイト
- 迷ったら簡易版で始めてよい。反映の回数や人数が増えたら移る。

## 1. 全体の流れと分担

```
（PC）直す → コミット → push
（PC）bash bin/deploy-ssh.sh preview      … 何が変わるかを出して止まる（サーバーは変わらない）
（PC）bash bin/deploy-ssh.sh apply <番号>  … preview で見た内容だけを上げる
（ブラウザ）公開 URL で変更を確かめる（§8）
```

| コマンド | サーバーを変えるか | 誰が打つか |
|---|---|---|
| `preflight` | 変えない | AI が流してよい |
| `preview` | 変えない | AI が流してよい |
| `status` | 変えない | AI が流してよい |
| `undo`（番号なし）／`baseline`（番号なし） | 変えない（何をするかを見せるだけ） | AI が流してよい |
| `apply <番号>` | **変える** | **人がターミナルで打つ** |
| `undo <番号>`／`baseline <番号>`／`unlock` | **変える** | **人がターミナルで打つ** |

- **必須**：AI は `apply`・`undo <番号>`・`baseline <番号>`・`unlock` を実行しない。理由＝本番の変更は人が内容を見て決める。
  スクリプトも、端末（人が打つ画面）以外から呼ばれると止まる。ただしこれは**AI が誤って打つのを防ぐ仕組みで、本人確認ではない**
  （端末を用意すれば通れてしまう）。守る根拠はこのルールであって、スクリプトの止まり方ではない。
- **必須**：AI は push もしない（`project-config.md` の「AI がやらないこと」）。push は人が行い、その後に AI が `preview` を流して結果を見せる。
- 番号（TOKEN）は「preview で見た内容」を表す。preview の後に何かが変わる（誰かが push した・本番が変わった）と、`apply` は番号が合わずに止まる。
  **リポジトリ側で見ていない内容が上がることはない**。
- **必須**：`apply` の間（多くは数十秒）は、WordPress の管理画面や FTP で本番を編集しない。スクリプトは書き込む直前にも本番を確かめ直すが、
  その後の数秒に入った編集までは防げない。お客様が日常的に管理画面を触る案件は、反映する時間を伝えておく。

## 2. PC の準備（PC ごとに1回）

| PC | やること |
|---|---|
| **Windows（既定）** | WSL（Windows の中で Linux のコマンドを使う仕組み）を入れ、**WSL のターミナルで**作業する。`git`・`ssh` が入っていることを確かめる（`git --version`・`ssh -V`）。リポジトリは WSL から見える場所に置く（`/mnt/c/...` でも可） |
| **Mac** | 追加の導入は不要（`git`・`ssh`・`shasum` が標準で入っている） |

- **推奨**：コミット時の改行コードを `.gitattributes` で決める（例＝`* text=auto eol=lf`）。理由＝Windows の設定次第で CRLF のまま上がり、本番の改行コードが変わる。
  スクリプトは改行コードだけの違いを `LINE ENDINGS ONLY` と名指しするので、見たら止まって確かめる。

## 3. 案件ごとの準備（1回）

1. **鍵を登録する**（人）：サーバーの管理画面またはサーバー担当者に、自分の公開鍵（`~/.ssh/id_ed25519.pub` 等）を登録してもらう。
   🚨 **秘密鍵（`.pub` の付かない方）の中身は誰にも渡さない・チャットに貼らない・AI に読ませない。**
2. **接続先に名前を付ける**（人）：`~/.ssh/config` にホスト名を書く。接続先・ユーザー・鍵の場所はここにだけ書く（リポジトリには入れない）。
   ```
   Host example-prod
       HostName  server.example.invalid
       User      exampleuser
       Port      22
       IdentityFile ~/.ssh/id_ed25519
   ```
   AI はこのファイルを読まない。名前（`example-prod`）だけ教えてもらう。
3. **設定ファイルを作る**：`.deploy/production.conf.sample` を `.deploy/production.conf` にコピーして埋める（§4）。**コミットする**（全員が同じ設定で上げるため。中身はホスト名とパスだけで、秘密は入らない）。
4. **確かめる**：`bash bin/deploy-ssh.sh preflight`。サーバーのユーザー名・公開フォルダの所有者と権限・足りないコマンドが出る。
   - **必須**：構成や権限は推測しない。preflight の出力（読み取りだけ）を見てから手順を決める。
   - 公開フォルダに書き込めない（`ROOTW=no`）と出たら止まる。**`sudo` や権限の変更で回避しない**。サーバー担当者に、どのユーザーで上げるのが正しいかを聞く。
5. **初回の記録を作る**（§5）。

検証環境もあるなら `.deploy/staging.conf` を作り、`-t staging` を付けて同じ手順で使う（例＝`bash bin/deploy-ssh.sh -t staging preview`）。
複数台へ同じ内容を上げる場合も、1台ごとに設定ファイルを作って順に行う。

## 4. 設定ファイル（`.deploy/<対象>.conf`）

1行に `キー=値`。`#` で始まる行はコメント。**未記入（`CHANGE_ME` が残っている）・同じキーが2回・知らないキーがあると止まる**（推測で進めない）。

| キー | 必須 | 意味 |
|---|---|---|
| `SSH_HOST` | 必須 | `~/.ssh/config` に付けたホスト名 |
| `REMOTE_ROOT` | 必須 | 反映先のフォルダ（サーバー上の絶対パス）。**この中は、リポジトリの `SOURCE_DIR` と同じ内容に揃えられる**＝リポジトリに無いファイルは消える（除外したものを除く） |
| `STATE_DIR` | 必須 | 記録・バックアップの置き場（絶対パス）。**公開フォルダの外**にする（中にすると止まる） |
| `SOURCE_DIR` | 任意 | リポジトリのどのフォルダを上げるか。既定＝`.`（リポジトリ全体） |
| `BRANCH`／`REMOTE` | 任意 | 既定＝`main`／`origin` |
| `BACKUP_KEEP` | 任意 | バックアップを何回分残すか。既定＝`10` |
| `EXCLUDE` | 任意・複数可 | **上げない・消さない・比べない**もの（`REMOTE_ROOT` からの相対パス。`*` が使える。`uploads/*` でフォルダごと） |
| `CHECK_URL` | 任意・複数可 | 反映後に状態を取得する URL |

### 除外（`EXCLUDE`）に入れるもの

**必須**：本番にだけあるべきもの・本番で増えるものは必ず除外する。除外しないと「リポジトリに無い」として**消える**。

- 接続情報を含む設定ファイル（`wp-config.php`・`config.php` 等）
- アップロードされたファイル（`wp-content/uploads/*` 等）・キャッシュ・ログ
- 本番と開発で中身が違うファイル（`.htaccess` を環境ごとに変えているなら）
- 他の仕組みが管理しているもの（WordPress 本体・プラグイン。WordPress は**テーマのフォルダだけ**を `REMOTE_ROOT`／`SOURCE_DIR` にするのが基本）

次は**常に除外される**（設定不要・外せない）：`.git*`・`.deploy/`・`.claude/`・`.env`／`.env.*`・`*.md`（ルール・記録類）・`*.sh`（このスクリプト等）。
`*.md` を公開したい場合はこの手順では上げられない（別途の手で上げる）。

Git で管理していないファイルは上がらない。上げたいなら**コミットする**。上げたくないなら `.gitignore` に入れる（未追跡のまま置いてあると preview が止まる）。

## 5. 初回：本番を記録する（`baseline`）

FTP で運用してきた案件は、本番とリポジトリが食い違っているのが普通。最初に1回、揃えてから使い始める。

1. `bash bin/deploy-ssh.sh baseline`（AI が流してよい）。本番とコミットの違いが3種類で出る。
   - `differ`：両方にあって中身が違う
   - `only on server`：本番にだけある
   - `only in repo`：リポジトリにだけある
   本番側の現物は、画面の `server copies:` に出た場所（`.git/deploy-ssh/<対象>/run-<日時>-<番号>/server/`）に取ってある。
2. **1件ずつ決める**（人。AI は案を出してよい）：
   - **本番が正しい**（FTP で直接直した等）→ その現物をリポジトリに取り込んでコミット・push する。
   - **本番にだけあって残すべき**（設定・アップロード等）→ `EXCLUDE` に足してコミット・push する。
   - **リポジトリが正しい** → そのままでよい（次の preview で「上書きする変更」として出る）。
3. もう一度 `baseline` を流し、残った違いが「リポジトリが正しい」ものだけになったら、人が `baseline <番号>` を打つ。
   本番のファイルには触らず、「いまの本番を起点にする」記録だけを作る。
4. `preview` を流す。残した違いが変更として出るので、内容を見て `apply`。

## 6. 止まったときの判断

スクリプトは**止まったときにサーバーを変えていない**（終了コード 2）。表示の `STOP:` の行と `NEXT:` の行を読む。

| 表示（要点） | 意味 | 次の手 |
|---|---|---|
| `uncommitted or untracked files` | 上げる範囲に未コミット・未追跡のファイルがある | コミットする／`.gitignore` か `EXCLUDE` に入れる |
| `not pushed yet. Push first` | 手元にしか無いコミットがある | 人が push してから preview |
| `behind ... (someone pushed)` | 他の人の push を取り込んでいない | `git pull --ff-only` してから preview（**古い内容で上書きしない**ため） |
| `diverged` | 手元とリモートが分かれた | pull（必要ならリベース）で1本にしてから |
| `Production was changed after the last deploy` | **本番が、前回の反映の後にこの手順以外で変わった** | 下の「本番の直接変更」 |
| `not part of main. Deploying would roll it back` | 本番に、`main` に無いコミットが上がっている | `status` で誰が上げたか見て、その人と話す。黙って上書きしない |
| `something changed since the preview` | preview の後に push や本番の変化があった | preview からやり直して読み直す |
| `another deploy is running` | 他の人が反映中、または前回が途中で切れた | 待つ／その人に聞く。**切れたと確かめられたときだけ** `unlock` |
| `a previous apply did not finish` | 前回の反映が途中で失敗している | §9 の undo |
| `symbolic links ... not supported` | シンボリックリンクがある | 自分の管理物でなければ `EXCLUDE`。管理物ならこの手順は使えない |
| `a file and a folder with the same path`／`CONFLICT` | 同じパスが、本番ではフォルダ、コミットではファイル（またはその逆） | この手順では切り替えられない。人が手で直し（サーバー担当者と相談）、`baseline` から作り直す |
| `production changed during the upload` | 転送の間に本番が変わった | 何も書き込んでいない。preview からやり直す |
| `undo would touch files that are now in EXCLUDE` | 戻す対象に、後から除外したファイルが入っている | 除外したものは手で扱う。バックアップの場所が表示されるので、人が判断して戻す |
| `no backup of the current deploy` | いまの本番は `baseline` で記録したもの、またはバックアップが整理済み | undo はできない。直すコミットを作って反映する |
| `is not filled in`／`unknown key` | 設定ファイルの未記入・誤記 | 設定ファイルを直す（推測で埋めない） |

### 本番の直接変更（drift）

**必須**：想定外の差分を見たら、原因を決めつける前に**リモートの履歴と照合する**。
preview の上部に「前回の反映以降のコミット」が出る。そこに無い変化は、この手順以外（WordPress の管理画面・FTP・他の仕組み）で入った変化。
本番の現物は、画面の `server copies:` に出た場所（`.git/deploy-ssh/<対象>/run-<日時>-<番号>/drift-server/`）に取ってある。

判断（人。迷ったら変更した可能性のある人＝お客様・同僚に確かめる）：

- **本番の変更を残す** → 現物をリポジトリに取り込んでコミット・push → `baseline` → `baseline <番号>` → preview
- **本番の変更は不要**（上書きしてよい）→ `baseline` → `baseline <番号>` → preview（その変更が「上書きされる」として出る）→ apply

どちらも、決めたことを作業記録（`documents/handoff.md` 等）に1行残す。

## 7. 反映の手順（毎回）

**必須**：コマンドを示すときは、**どこで・誰が打つか・何が出れば正しいか・違ったらどうするか**を必ず添える。複数行を貼らせない（1行ずつ）。

| # | どこで・誰が | コマンド | 正しい結果 | 違ったら |
|---|---|---|---|---|
| 1 | PC・人／AI | `git status --short` | 何も出ない（または除外対象だけ） | コミットするか片づける |
| 2 | PC・人 | `git push origin main` | エラーなし | 拒否されたら pull してから |
| 3 | PC・AI でも可 | `bash bin/deploy-ssh.sh preview` | 変更一覧・差分・`TOKEN:` が出る | §6 の表 |
| 4 | 人が読む | （差分を読む） | 意図した変更だけ。`D`（削除）と `A`（新規のパス）は特に見る | 止める。直してコミットからやり直す |
| 5 | PC・**人がターミナルで** | `bash bin/deploy-ssh.sh apply <TOKEN>` | `OK: deployed ... Verified` | 終了コード 3 なら §9 |
| 6 | ブラウザ・人／AI | 公開 URL を開く | §8 の完了条件を満たす | §9 の undo を検討 |

- `apply` がやること：排他（同時に1人）→ 最新状態で preview と同じ確認をやり直す → 番号の一致を確かめる → 公開フォルダの外へ転送して中身を照合 → 上書き・削除するファイルをバックアップ → コピー・削除 → **本番がコミットと一致したことを確かめる** → 記録 → 古いバックアップを整理 → `CHECK_URL` の状態を表示。
- 既存ファイルの所有者と権限は変えない（上書きは中身だけ）。新規ファイルはサーバーの既定の権限になる。実行権限などが要る場合は、上げた後に人が設定し、作業記録に残す。
- 空になったフォルダは消えずに残る（害はない）。
- `apply` の間は本番を編集しない（WordPress の管理画面・FTP とも。§1）。

## 8. 反映後の確認（変更の種類ごとの完了条件）

「上げた」と「公開 URL で確認できた」は別。**確認したと書けるのは、実際に開いた／取得したときだけ**。
スクリプトの URL チェックは状態コードだけ＝それだけでは完了にしない。

| 変更の種類 | 完了条件 |
|---|---|
| 静的ファイル（HTML・CSS・画像） | 公開 URL で**変更した箇所そのもの**が見える。CSS・画像はキャッシュを外して（強制再読み込み・別ブラウザ）確かめる |
| サーバー側のコード（PHP 等） | そのページが表示される（500 等が出ない）＋変更した動作を1回通す。エラーログが見られるなら新しいエラーが無い |
| メール送信・外部連携など外へ作用する機能 | **実際に1回動かして、届いた／反映されたことを確かめる**（テスト用の宛先で）。ページが表示されるだけでは完了にしない |
| WordPress（テーマ） | 変更したテンプレートを使うページを開く。管理画面でエラー通知が出ていない |
| キャッシュ・CDN を使っている | キャッシュの削除が要るなら行い、確認した時刻を記録に書く |
| 再起動が要る構成 | この簡易版の対象外（リポジトリ経由のデプロイへ） |

## 9. 失敗したとき・戻したいとき

### 最初にすること

1. **それ以上コマンドを重ねない**。表示をそのまま残す（コピーして記録へ）。
2. `bash bin/deploy-ssh.sh status` で状態を見る（`unfinished` に ID があれば途中で止まっている）。
3. 戻すなら undo へ。わからなければ人（サーバー担当者）に、表示と status の結果を渡して相談する。

### undo

```
bash bin/deploy-ssh.sh undo            … 何を戻すかを見せる（AI が流してよい）
bash bin/deploy-ssh.sh undo <TOKEN>    … 人がターミナルで打つ
```

- 直前の反映を戻す。上書きしたファイルを戻し、**新しく作ったファイルも消し**、削除したファイルを復元する。戻した後に本番が反映前と一致することを確かめる。
- 途中で失敗した反映（終了コード 3）も同じ手順で戻せる。
- **undo 自体が途中で失敗しても**（権限エラー等）、原因を直してもう一度 `undo` → `undo <番号>` を打てば、同じ戻しをやり直す。
  途中の間は preview・apply が止まる（中途半端な本番に重ねて上げないため）。
- 反映の後に本番が別の理由で変わっていると、上書きを避けるため止まる → preview で状況を見て人が判断。
- undo しても、コミットは `main` に残っている。**直すコミット（`git revert` 等）を作って push し、preview からやり直す**（そのまま preview すると同じ内容がまた出る）。

## 10. 緊急時

急いでいても**省略してはいけない**：

- push 済みのコミットから上げる（手元の未 push の内容を上げない）
- preview を読む（とくに削除と新規）
- 本番の直接変更で止まったら、取り込むか捨てるかを決めてから進む
- apply は人が打つ

**省略してよい**：§8 の確認のうち、変更箇所に関係しない部分。作業記録への詳細な記述（後で書く。ただし当日中）。

この手順どおりにできない（サーバーが落ちて SSH がつながらない等）ときは、**この手順の外で作業したことを記録し**、復旧後に `baseline` から記録を作り直す。

## 11. 記録・バックアップ・後始末

| 何が | どこに | いつまで |
|---|---|---|
| 反映の記録（日時・誰・コミット・件数） | サーバーの `STATE_DIR/log` | 消さない（`status` で直近10件が見える） |
| いま本番にあるコミット | サーバーの `STATE_DIR/deployed` | 反映ごとに更新 |
| バックアップ（上書き・削除したファイル） | サーバーの `STATE_DIR/backups/<ID>/` | 新しい順に `BACKUP_KEEP` 回分。古いものは自動で消える |
| 転送したファイル | サーバーの `STATE_DIR/incoming/<ID>/` | 反映が終わると自動で消える。失敗時は残る（undo の後に消える） |
| 手元の確認用ファイル（差分・本番の現物） | `.git/deploy-ssh/<対象>/run-<日時>-<番号>/`（実行ごとに別。場所は画面に出る） | 1日たつと次の実行のときに消える（Git には入らない） |

- **推奨**：共用サーバーで容量が小さいなら `BACKUP_KEEP` を減らす（大きな画像を何度も差し替える案件など）。
- 作業記録（`documents/handoff.md` 等）に、反映したコミットと確認した URL・時刻を1行残す。

---

## 12. 複数人で反映するとき

- 同時に反映できるのは1人（サーバー側で排他。もう1人は `another deploy is running` で止まる）。
- 他の人の反映を古い内容で上書きすることは、push 済み・最新・巻き戻し防止の3つの確認で止まる。
- **推奨**：反映する人を `project-config.md` の「デプロイ先・手順」に書いておく（お客様が WordPress を直接編集するかどうかも）。

## 13. やってはいけないこと

- ❌ AI が `apply`・`undo <番号>`・`baseline <番号>`・`unlock` を打つ／push する
- ❌ スクリプトが止まったのを、FTP や手作業のコピーで回避する（記録と本番がずれ、次から全員が止まる）。やむを得ず回避したら、記録に残して `baseline` から作り直す
- ❌ `sudo`・権限や所有者の変更で書き込めない問題を回避する
- ❌ 秘密鍵・パスワード・`~/.ssh/config`・接続情報を含む設定ファイルの中身を読む・貼る
- ❌ 本番の直接変更を「たぶん不要」で上書きする（取り込むか捨てるかは人が決める）
- ❌ `bin/deploy-ssh.sh` をこの案件で書き換える（配布物は更新で上書きされる。不具合や不足は `rules/modes/rules-update.md` の流れで配布元へ返す）
