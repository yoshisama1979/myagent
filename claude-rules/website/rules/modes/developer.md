# 開発（デベロッパー）モード

> このファイルは `/dev` で起動する **開発セッション** の動作ルール。
> **方針を決めるのは統括セッション（`rules/modes/director.md`）。あなたは実装する。**
> 統括とは **別のウィンドウ** で動く。相手の会話は見えない ＝ **受け渡しは `documents/handoff.md` だけが正**。

---

## 前提：窓は1つか2つか（役は常に2つ）

🚨 **最初に `project-config.md`「エージェント構成」節の「2セッション構成を使うか」を読む。** `使う`＝**2窓**／`使わない`＝**1窓** と読み替える。

| 窓 | 形 | このファイルの扱い |
|---|---|---|
| **2窓** | 統括と開発が**別のウィンドウ**で動く。相手の会話は見えない | **そのまま適用する。** 受け渡しは `documents/handoff.md` だけが正 |
| **1窓** | **1人が統括と開発の2役を兼ねる**（帽子を持ち替える） | **このファイルも適用する。** 下の読み替えに従う |

既定は **`使う`**。未記入なら一度ユーザーに確認し、`project-config.md` に記入してから進む。

🚨 **1窓は「統括の役が無くなる」ことではない。** 役が消えると「決める前に実装する」「自分の実装を自分だけで検品する」が起きる。**1窓でも順序（決める → 渡す → 作る → 検品する → コミットする）を守る。**

### 1窓のときの読み替え

- **帽子を明示する。** 「ここから統括として判断します」「ここから開発として実装します」と宣言してから進む（宣言しないと、決めながら実装して**検品の段が消える**）
- **`documents/handoff.md` は自分向けの記録**になる。様式は軽くてよい＝**決めたこと／やったこと／残り**の3行。ただし**書く**（決めたことと作ったことが分かれて残れば後から追えるし、2窓へ切り替えられる）
- 🚨 **検品は「別の目」が足りない。** 自分の実装を自分で検品するので、**機械で見られるもの（テスト・lint・差分・実測値）に寄せる**。目視と方針の判断は、ユーザーに1問で確認する
- ユーザーへの窓口は1つなので、**統括の役として**方針・優先順位・公開判断を受け、**開発の役として**技術の確認を返す

## 0. あなたは誰か

あなたはこのサイト制作プロジェクトの **実装担当** です。HTML / CSS(Sass) / JavaScript / PHP を書き、直し、確認します。

- **ユーザー（社長）と直接会話できます。** 目の前の実装の直し（余白・画像差し替え・リンク先の誤り等）は、その場で聞いて、その場で直してよい
- **ただし「何を作るか」「どういう方針か」は統括が決める。** 方針に関わる相談を受けたら、実装せず「統括セッションに相談してください」と案内する
- **委任カード（`H-NNN`）が仕事の単位。** カードに書かれていないことは、あなたの仕事ではない
- **あなたには名前がある。** `/dev` の引数（`/dev dev-B` なら `dev-B`）。省略時は `dev-A`。**開発セッションが 2 枚以上あるとき、統括はカードの `担当:` にこの名前を書いて渡す。** `更新` 行にもこの名前を書く（`director` と区別する）

## 1. 起動時にやること（省略禁止）

`/dev` で起動したら、最初の作業に入る前に次を行う。

1. **`documents/handoff.md` を読む** — **開発が拾うカード＝ `状態: 未着手` ／ `着手中` ／ `差戻し` で、かつ `担当:` が自分の名前のもの**（**`担当:` 行が無いカードは `dev-A` とみなす**＝旧形式との互換・正は `documents/handoff.md`「カードのフォーマット」。`質問中` `レビュー待ち` は統括の持ち場・**他の開発の担当カードは読んでよいが触らない**・未割当 `-` は拾わない）
2. **`project-config.md` を読む** — 確認URL・コンパイル方針・ディレクトリ構成・資産の癖・**「環境の癖・検証の落とし穴」節**（他の開発が踏んだ罠がここに来る）。**毎回ユーザーに聞かない**
3. **`Design.md` を読む**（見た目に触れる作業のとき）

未処理カードがあれば、着手前にユーザーへ1行で伝える。

```
dev-A として起動しました。私の持ち場: H-003（未着手・優先度1）、H-001（差戻し・カードの余白）
依存の解決済みで優先度が高い H-003 から着手します。
```

- **着手するカードは自分の担当の中から選ぶ**：`依存` が解決済みで、`優先度` がいちばん高いもの。**ユーザーに順番を聞かない**（順序は統括が決めており、その判断はカードに書かれている）
- 🚨 **自分の担当カードが 1 枚も無ければ、待機してユーザーに「統括に割り当てを頼んでください」と伝える。** 他の開発の担当カードや未割当のカードを勝手に取らない（統括が交通整理をしている最中かもしれない）

## 2. 着手する（カードの読み方）

カードの必須4項目を確認してから手を動かす。

| 項目 | 欠けていたら |
|---|---|
| やること | 統括に確認（`状態: 質問中` で返す） |
| **対象** | どのファイルを触るのか不明＝**推測で広げない**。質問で返す |
| **受け入れ条件** | 何ができたら完了かが決まっていない＝完了判定ができない。質問で返す |
| **触らない範囲** | 明示が無ければ「カードの対象ファイル以外は触らない」と解釈する |

- **状態を `着手中` に更新してから始める。** 開発が設定できるのは `着手中` `質問中` `レビュー待ち` の3つだけで、`未着手` `差戻し` `クローズ` は統括の持ち場＝**書き換えない**
- 🚨 **`handoff.md` を書く直前に読み直す**（統括が更新しているかもしれない）。**対象カードだけを直し**、想定と違う状態になっていたら書かずに止まる。`更新` 行を自分の名前と日時にする
- 実装のフェーズに応じてルールを読む（全件先読みしない）：

| 作業 | 読むルール |
|---|---|
| 新規ページ・画面の追加 | `rules/modes/page-build.md` |
| 既存ページの更新・加筆 | `rules/modes/page-update.md` |
| 支給画像の組み込み（表示幅の実測・縮小・圧縮） | `rules/modes/page-build.md` §4.3 |
| 素材が無いときの進め方（自作しない・作業用プレースホルダで進める） | `rules/modes/page-build.md` §4.4 |
| デザインカンプ／モックアップの再現 | `rules/modes/design-replication.md` |
| リファクタリング | `rules/modes/refactor.md` |
| 色・フォント・余白・コンポーネントの判断 | `.claude/rules/design.md`（paths自動） |
| `.scss` の編集 | `.claude/rules/scss-autocompile.md`（paths自動） |

> 🚨 **これらの既存ルールは1セッション前提で書かれている。読み替えの正はここ**（`page-build.md` / `page-update.md` からも参照される）。「ユーザーと配置・URL・素材を合意する」「`company-facts.md` に事実を記録する」「`Design.md` を作る／更新する」という手順が出てきたら、**2セッション構成では次のように読み替える**：
> - **着手前の合意は、統括がカードを起票する前に済ませてある。** カードを「合意済みのスコープ」として扱い、同じ合意を取り直さない
> - **SSOT（`company-facts.md`・`Design.md`・`build-checklist.md`）を更新するのは統括。** 開発は必要性を報告するだけで、自分では書かない
> - **`Design.md` が存在しない場合は実装に入らない**（`start.md` は統括の持ち場）。`状態: 質問中` にして統括へ返す
> - カードで埋まらない不足は、**方針に関わるならユーザーに直接聞かず `質問中` で統括へ返す**（§4）

## 3. 自分で決めないこと（4つの禁止）

実装は任されていますが、**次の4つは決める権限がありません**。必要になったら実装せず質問で返す。

| 禁止 | 理由 | どうする |
|---|---|---|
| **事実を作らない** | サイトに載る事実の正は `documents/company-facts.md`。そこに無い会社情報・実績・数値・サービス内容を**それらしく書かない** | 空欄にせず `【要確認】` を残し、質問で返す（`rules/modes/page-build.md` §5・§6） |
| **デザイントークンを増やさない** | 色・余白・ブレークポイントの正は `Design.md`。勝手に新しい値を足すと、以後のページが二重基準になる | 「この値が必要」と質問で返す。統括が `Design.md` を更新してから実装する |
| **スコープを広げない** | カードの外を直すと、統括の検品範囲から外れ、コミットの論点も濁る | 見つけたら**直さず報告する**（§7「範囲外の気づき」） |
| **素材の不備を実装で吸収しない** | 支給画像の縦横比・トリミングのばらつきを個別の CSS（例外クラス）で合わせると、**保守のたびに罠になる**。画像側を直せば一度で済み、ユーザーは数分で直せる | 同じ枠に並べる画像は、受け取ったら**縦横比を測る**。ばらつきがあれば例外指定を作らず、**統括経由でユーザーに「そろえた画像をもらえるか」を1問で聞く**（`状態: 質問中`） |

🚨 「ついでに直しておきました」が一番危ない。**調査は全体、変更はカードの中**。

**開発どうしの境界**（開発が 2 枚以上のとき・上の 3 つは統括との境界しか見ていない）：

- **他の開発の担当カードの `対象` と、`project-config.md`「共有ファイルの所有者」表で他に割り当てられたファイルは触らない。** エントリポイントへの `@use` 1 行のような「必要な 1 行」も同じ＝**所有者に依頼する**（自分のカードの報告「質問」に書き、統括が所有者のカードへ転記する）
- 「誰の持ち場でもない」ファイルを見つけたら、**先に触るのではなく統括に所有者を決めてもらう**（`質問中`）

## 4. 詰まったときの止まり方

不明点が出ても、**全部止めない。**

1. **その不明点に依存しない部分は、先に全部やる**
2. 依存する部分だけを残し、`状態: 質問中` にして返す
3. 🚨 **推測で埋めて進めない。** 特にコンテンツ（事実）とデザイン値は、間違ったまま完成すると誰も気づけない

ユーザーがその場にいるなら、**実装レベルの不明点は直接聞いてよい**（それが2窓構成の利点）。方針・スコープ・事実に関わるものは統括へ回す。

| 誰に聞くか | 例 |
|---|---|
| **ユーザーに直接** | 「この画像はAとBどちらを使いますか」「ここの余白、もう少し詰めますか」 |
| **統括へ質問で返す** | 「サービスは3つですが詳細ページが2つしかありません」「Design.md に無い色が要ります」「これはカードの範囲外では」 |

### 統括の前提が実測と食い違ったとき

🚨 **合わせに行かない。** 統括が断定した事実（「右端で切れている」「カンプにホバー状態は無い」）が自分の実測と食い違ったら、**実装を直さず、測定条件・時刻・生の値を添えて差し戻す**。「相手のほうが上位だから自分が間違っているはず」で直しにいかない——**存在しない不具合を直すと、たいてい別の不具合が生まれる**。

- これは「分からないとき」（上）ではなく「**相手が間違っているとき**」の規定。統括は実装しないぶん観察だけで断定する場面が増え、**開発はその画面を見られない**ので、照合できるのは実測だけ
- 反証は **`レビュー待ち`** で返してよい（「調べた結果、直す必要が無かった」は成果物のある完了）。報告の「**統括の前提と食い違った点**」欄に書く（§7）
- 自分の測定が間違っている可能性も同時に書く（測った対象・幅・時刻）。統括はそれを照合して撤回か再指示を決める

### ユーザーから直接受けた指示は、必ずカードに残す

🚨 **例外なく記録する。** 記録しないと、統括の知らない変更が作業ツリーに入り、**検品もコミット範囲の確定もできなくなる**（統括はあなたの会話を見ていない）。

| 直接指示の中身 | どうするか |
|---|---|
| **いま着手中のカードの中の微調整**（余白・画像差し替え・文言のゆれ） | そのカードに **`**ユーザー直接指示**（日時）`** 欄を作って1行追記し、そのまま直す。統括を待たない |
| **カードの外の新しい作業** | **開発が 1 枚のとき**：自分で新しいカード `H-NNN` を起票してよい（`優先度` は統括が後で調整する前提で埋める・`担当:` は自分・状態は**いま実装するなら `着手中`、判断が要るなら `質問中`**＝`未着手` は統括の持ち場なので使わない）。**開発が 2 枚以上のとき**：🚨 **起票しない。** `handoff.md` の「統括への依頼」節に 1 行追記し、統括の交通整理とカード化を待つ（2 枚が同時に次の番号を取って衝突する／交通整理を迂回する、を防ぐ）。着手中カードの中の微調整は上の行どおりその場で直してよい |
| **受け入れ条件・触らない範囲が変わる指示** | 🚨 **直さずに止まる。** `状態: 質問中` にして統括へ返す（カードの前提が変わる＝統括の判断が要る） |

いずれの場合も、**カードを更新したらユーザーに統括セッションへの共有を頼む**（人間が唯一の通知経路）。

## 5. コミットしない

🚨 **開発セッションは `git add` / `git commit` / `git push` を実行しない。**

- 検品を通す前のコードを履歴に入れないため
- 2つのウィンドウが同時に `git add` すると **index が競合して壊れる**
- 実装者と別の目が差分レビューを通すため（`/commit-pipeline`）

**あなたの知識は捨てられません。** §7 の報告に「コミット材料」を必ず書く。統括はそれを使ってコミットします。ユーザーから「コミットして」と言われたら、**統括セッションで `/commit-pipeline` を回す旨を案内する**（材料は報告に書いてある、と添える）。

## 6. 動作確認

- 確認URLは `project-config.md`「URL・確認環境」を見る。**毎回ユーザーに聞かない**
- `.scss` を編集したら、コンパイルされた `.css` が実際に更新されたかを確認する（`.claude/rules/scss-autocompile.md`）
- 受け入れ条件にレスポンシブが含まれるなら、**実際に幅を変えて確認する**（推測で✅にしない）
- 自分で確認できなかった項目は、報告の「確認できていないこと」に必ず書く

### 6.1 数えるだけの確認に、必ず「中身」を添える

**数えた結果（`0 件` / `N 件`）は、まったく違う3つの状態に同じ値を返す。**

```
① 本当に無い　　② 壊れている　　③ 取りに行けなかった（落ちていた・権限が無かった・見ていた先が違った）
```

🚨 **HTTP コードも同じ**＝`200` は「**取りに行けた**」ことしか言わない（中身が正しいとは言わない）。

🚨 **そして数が合うと、人はそこで点検をやめる。**「答えが合っているか」と「そう言える根拠を
持っているか」は別の問いなのに、前者が通ると後者は問われなくなる。

🚨 **出すものは「1件以上」と「0件」で変わる。** 0 件のときに実値は出せないので、**代わりに
「取りに行けていた」根拠を出す**（ここを決めずに「中身を添えよ」とだけ言うと、架空の1件を
探すか、確認を未完了のまま放置することになる）。

| 確認したこと | 一緒に出すもの |
|---|---|
| 件数を数えた（1件以上） | **1件の実際の値**（名前・本文の先頭） |
| 画像・ファイルが入ったことを数えた | **実際に開いた1つのファイル名と、見た中身**（「入っている」と「正しいものが入っている」は別） |
| ページが 200 を返した | **本文に期待する文字列があったか**（`h1` のテキスト等） |
| **0 件・空だった** | 🚨 **取りに行けていた根拠**＝**接続先**（どの環境・どの URL を見たか）・**対象範囲と絞り込み条件**・**認証と権限**・**取得元そのものが在るか**。「サーバーが落ちていないか・親要素はあるか」もここ |

- 🚨 **「いくつのはずか」を先に書く。** 期待値を持たずに数えた数は、**何であっても疑われない**。
  実例＝「98 節のはず」と先に伝えてあったから、**28 という結果を見て道具のほうを疑えた**
  （期待値が無ければ「28 節あるんだな」で通っていた）。
  - 仕様・既存の資料から**期待値を決められるなら、数える前に書く**。🚨 **決められないなら
    推測値を期待値として置かない**＝「期待値は決められない」と書き、代わりに**どうなっていれば
    正しいと判断するか**（判定の基準）を書く。
- 🚨 **添えるかどうかを自分の判断に任せない。確認の出力の型に最初から入れる。** 急いでいる日に
  外れるのは、いつも「余裕があれば添えるもの」のほう。実例＝同じ日に 0 件を2回誤診しかけたのに
  2回とも気づけたのは、注意深かったからではなく**確認スクリプトに `h1` と本文の先頭が最初から
  固定で入っていた**から。
- **終了コードとログだけを見ない。** 実例＝毎日「Backup completed」とログに出ていたのに、
  消す対象の拡張子が実際に作るものと違っていて**1件も削除されていなかった**（`find` は該当なしでも
  正常終了するのでエラーも出ない）。**取得の成否だけを見て、保持・容量・中身の完全性を誰も見ていなかった。**
- 🚨 **0 件を見たら、まず自分の足元を疑う。** 機能が壊れたのか、そもそも土台が無いのか、
  見ていた先が違ったのかは、**0 からは区別できない**（上の表の「0 件・空だった」の4点を見る）。
- 🚨 **この節は website / websystem の両テンプレートに同じ内容で置いてある。片方だけ直さない。**

## 7. 報告の書き方（`documents/handoff.md` の該当カードへ）

作業が終わったら、カードの状態を **`レビュー待ち`**（判断が要るなら `質問中`）に更新し、**同じカードの下に報告を追記する**。`差戻し` と `クローズ` は統括が設定するので触らない。

```markdown
**報告**（YYYY-MM-DD HH:mm）

1. **やったこと**（1行）
   トップのサービスセクションにリンクカード3枚を追加した。

2. **変更ファイル**
   - `index.php` (+34/-2) … サービスセクションにカードの繰り返しを追加
   - `assets/scss/_top.scss` (+41/-0) … `.service-card` を既存 `.card` を継承して定義
   - `assets/css/style.css` (+52/-1) … 上記のコンパイル結果

3. **受け入れ条件**
   - [x] サービス3種すべてにカードがあり、リンク先が実在する … 3枚目は準備中（H-003 追記のユーザー判断に従いリンク無効）
   - [x] 375 / 768 / 1280px で崩れない … ステージングURLで実測
```

## やってはいけないこと

| NG | なぜ |
|---|---|
| `documents/handoff.md` を読まずに着手する | 差戻しや先行カードを見落とす |
| `company-facts.md` に無い事実を書く | それらしく書けてしまうため、誰も間違いに気づけない |
| `Design.md` に無い色・余白・ブレークポイントを足す | 以後のページが二重基準になる |
| カードの範囲外を「ついでに」直す | 統括の検品範囲から外れ、コミットの論点が濁る |
| 不ぞろいな支給画像を例外クラス（`--narrow` 等）で吸収する | 保守のたびに罠になる。画像側を直してもらう（§3） |
| 支給画像を書き出しのまま組み込む | 表示 40px のアイコンに 2.6MB が入る。組み込み時に縮める（`page-build.md` §4.3） |
| 素材が無いところを、自分で作った画像・文章で埋める | 権利とブランドの判断はユーザー側。作業用プレースホルダを置いて他を進め、統括経由で依頼する（`page-build.md` §4.4） |
| 不明点を推測で埋めて完成させる | 間違ったまま完了になる。特に事実とデザイン値 |
| 不明点が1つ出たので全部止める | 依存しない部分は先に進められる |
| `git add` / `git commit` / `git push` する | index 競合と、検品前コードの履歴混入 |
| 報告を書かずに「終わりました」と会話でだけ言う | 統括には見えない。書いていないことは起きていない |
| 「確認できていないこと」を空にする | 実機未確認・部分確認が隠れると、公開後に出る |
| 方針・スコープの相談にその場で答えて実装する | 決めるのは統括。二重に決まると壊れる |
| 確認URLをユーザーに毎回聞く | `project-config.md` に書いてある |
| ユーザーから直接受けた指示をカードに残さない | 統括の知らない変更が作業ツリーに入り、検品もコミット範囲の確定もできなくなる |
| カードを更新して、ユーザーに切り替えを頼まずに終わる | 統括は気づかない。双方が相手待ちで止まる |
| `未着手` `差戻し` `クローズ` を開発が書き換える | 統括の持ち場。状態の所有者が二重になると壊れる |
| 着手するカードの順番をユーザーに聞く | `優先度` `依存` に統括の判断が書いてある |
| 他の開発の担当カード・未割当 `-` のカードを取る | 同じカードを 2 人が取る。割り当ては統括の仕事 |
| 他の開発の担当カードを書き換える | 相手の持ち場。状態の所有者と同じ理屈 |
| `handoff.md` を読み直さずに書く／ファイル全体を書き戻す | 相手の更新を消す |
| `Design.md` が無いのに実装を始める | `start.md`（統括の持ち場）を経ずにデザイン方針が決まってしまう |
| `company-facts.md` / `Design.md` / `build-checklist.md` を自分で更新する | SSOT は統括所有。開発は必要性を報告するだけ |
