# コンテンツ設計の手順（相談を受けてから、載せる内容が決まるまで）

> クライアントから制作・リニューアルの相談を受けてから、サイトに載せるコンテンツが決まり、デザイン・実装に渡せるまでの進め方。
> **`rules/modes/start.md`（Design.md・company-facts.md・台帳の準備）より前から始まり、`rules/modes/page-build.md`（ページの実装）に引き渡す。**
> 台帳としては `documents/build-checklist.md` の**フェーズ0（前提の確定）・1（情報設計）・2（素材・原稿）を埋める作業**にあたる（§8 の対応表）。
> 出自＝2026-10-28、現場（コーポレートサイトのリニューアル）からの指示書。実案件の内容検討を振り返って作られたものを、テンプレート側で役の割り当てと既存ルールとの整合を加えて採用した。

---

## 0. この手順の使い方（最初に読む）

### 誰がやるか — **統括の持ち場**

🚨 **この手順を回すのは統括**（`/director`）。開発セッションが先走って始めない。

| 役 | すること |
|---|---|
| **ユーザー**（制作者） | クライアントと話す。**聞き出し、決定を持ち帰る**。統括の案を見て良し悪しを判断する |
| **統括** | 聞くことのリストを作る／必要なコンテンツを立てる／競合を調べる／サイトマップと構成を案にする／確認事項を台帳とリストに起こす |
| **開発** | **§7-4 のモック実装から**。カードで受けて作る（それ以前の段には入らない） |

- 🚨 **統括がクライアントと直接やり取りすることはない。** 窓口はユーザー
- 1窓運用（`project-config.md`「エージェント構成」が `使わない`）でも**この順序と持ち場は守る**（冒頭の読み替え＝`rules/modes/director.md`）

### 原則1：決めるのはクライアント

- **統括とユーザーはアドバイザー**として案を出す
- **具体的な情報（事実・数字）と最終決定は、クライアントからヒアリングする**
- 統括が出す「読者の不安」「追加の提案」「不要の提案」は、すべて**仮説**。クライアントが確認するまで確定にしない
- 確定した事実の置き場は `documents/company-facts.md`（正は `rules/modes/start.md` §2）

### 原則2：この手順は「最低線」であって「上限」ではない

| 種類 | 中身 | 扱い |
|---|---|---|
| **守ること** | 下の4つだけ | 外さない |
| **進め方の例** | それ以外のすべて（一覧・順番・観点・まとめ方） | 出発点。もっと良いやり方があれば、**理由を添えて**変えてよい |

**守ること**
1. 決めるのはクライアント（原則1）
2. 事実と仮説を分ける。確認が済んでいない内容は、見た目でも記録でも「未確認」とわかるようにする（見た目の作法は `rules/modes/page-build.md` §6・§6.2）
3. 情報の出所を付ける（要望／基本／競合／手元の資料／統括の提案）
4. 必要なコンテンツを出すときは、§2-4 の「追加の提案」「不要の提案」の欄を必ず埋める

ベースに無い観点や、もっと良い進め方を思いついたら、遠慮せず提案する。理由を添えるのは縛るためではなく、ユーザーが良し悪しを判断できるようにするため。

> ⚠️ **この原則2 はこのファイルの中だけの話。** 他のルールファイルの 🚨 付きの規定（安全ゲート・公開前チェック・事実を作らない 等）には及ばない。あちらは「理由を添えれば変えてよい」ものではない（テンプレート設計原則③）。

### 全体の流れ

| # | 段階 | 出てくるもの | 埋まる台帳 |
|---|---|---|---|
| 1 | ヒアリング | 要望メモ | フェーズ0 |
| 2 | 必要なコンテンツを洗い出す（手元の情報を見ずに） | コンテンツ候補の一覧 | — |
| 3 | 手元の情報と照らし合わせる | ある／古い・食い違う／無い の印 | — |
| 4 | 足りない情報を聞く | `documents/client-questions.md` | フェーズ0・2 |
| 5 | 優先順位と範囲を決める | 今回作る／後で作る／作らない | フェーズ0 |
| 6 | サイトマップ | サイトマップ | フェーズ1 |
| 7 | ページごとの内容設計 | モック上のドラフト | フェーズ1 |
| 8 | 確認事項の管理 | 台帳・確認リスト・ファクト集の更新 | フェーズ2 |

🚨 **順番の理由**：手元の情報から始めると、**もともと無い情報は候補にすら上がらない**。先に「本来あるべきもの」を出し、それから手元と照らし合わせると、無いものが「足りない」として見えるようになる（現場実例＝旧サイトから出発したため、旧サイトに無かった情報〔保証の上限額・引受先〕に、競合を調べるまで気づけなかった）。

## 1. ヒアリング

**考え方**：最初から細かく聞かない。初めから細かく考えているクライアントは少ない。初回は目的と大枠を聞き、細かい内容はモックを見せながら一緒に詰める。

| 回 | 聞くこと | 深さ |
|---|---|---|
| 初回 | 下の初回リスト | 広く浅く |
| 2回目以降 | モックを見せながら、ページごとの細かい内容（§4・§7） | 狭く深く |

**初回に聞くことのリスト**（統括が作り、ユーザーが聞き出す）
1. なぜ今、作る（作り直す）のか。何を変えたいか
2. 誰に見てほしいか
3. 見た人に何をしてほしいか（問い合わせ・資料請求・応募など）
4. 今のサイトで困っていること
5. 必要だと思うページ
6. 手元にある資料（パンフレット・会社案内・写真・原稿）
7. 気になっている同業他社や、参考にしたいサイト（名前だけでよい）
8. 公開したい時期
9. 公開後、誰がサイトを更新するか（お知らせやブログを社内で書くか。ページ構成に影響する）
10. 今回は作らないが、将来増やしたいもの

2と3は、目的を聞く中で自然に出てくれば、別に聞かなくてよい。聞いた結果は `documents/build-checklist.md` フェーズ0 に反映する。

## 2. 必要なコンテンツを洗い出す

**手元の情報（旧サイト・パンフレット）はまだ見ない。** 次の3つから「本来あるべきもの」を出す。

### 2-1. 目的から導く

1. 目的（例：取引先からの依頼を増やしたい）
2. 読者（例：取引先の担当者）
3. 読者が決める前に知りたいこと・不安（例：「本当に大丈夫か」「何かあったら誰が責任を持つのか」「うちの地域にも来てくれるのか」）
4. それに答えるコンテンツ（例：判断の根拠・保証・対応エリア）

3は**統括の仮説**。ユーザーと検討し、クライアントに「実際によく聞かれるのはどれか」を確認する。見出しや吹き出しとして、そのままページの見せ方に使えることも多い。

### 2-2. 基本コンテンツ（ベース一覧）

コーポレートサイトを前提にしたベース。**出発点であって、そのまま使うものではない**（§2-4）。

**A. どの会社にも要るもの**

| ページ | 中に入れる情報 |
|---|---|
| トップ | 何の会社か、誰向けか、主な事業への入口、お問い合わせへの導線 |
| 事業・サービス紹介 | 何をしているか、対象、進め方の流れ、料金や目安（出せる範囲で） |
| 会社概要 | 社名・所在地・代表者・設立・資本金・従業員数・事業内容・許認可や登録番号・連絡先・地図 |
| お問い合わせ | フォーム・電話番号・受付時間・返信までの目安 |
| プライバシーポリシー | フォームで個人情報を受け取るなら必須 |

**B. 信頼してもらうために、ほぼ要るもの**

| ページ・情報 | 理由 |
|---|---|
| 実績・事例 | 「本当にやっているか」の証拠 |
| 代表あいさつ・理念 | 会社の考え方や人柄が伝わる |
| 沿革 | 続いてきた年数そのものが信頼になる |
| 資格・認証・加盟団体 | 第三者からの裏付け |
| よくある質問 | 問い合わせ前の不安を減らす |
| お知らせ | 「今も動いている会社」だとわかる |

**C. 業種や目的によって要るもの**

採用情報／拠点一覧／読み物（ブログ・コラム・セミナー）／資料ダウンロード／保証・アフターサービス／SDGs・社会貢献／特定商取引法に基づく表記（ネットで物を売る場合は法律上必要）／サイトの利用規約

サイトの種類（会社向け・一般向け・お店・ランディングページなど）によって、重さも中身も変わる。**種類ごとの一覧は持たない。その都度統括が見立てて調整する**（§2-4）。法的表記の要否は `documents/build-checklist.md` フェーズ2 で確定させる。

### 2-3. 同業他社の分析

**どこを見るか**：クライアントが挙げた会社（§1 の7）に加え、統括が選んだ会社（同じ業種で検索上位・同じ地域）。合わせて3〜5社。クライアントが挙げなければ統括が選んでよい。

**何を見るか**：ページ構成／載せている情報（数字・料金・保証の条件・実績・資格）／強みの打ち出し方／問い合わせへの導線

| 分類 | 意味 | 使い方 |
|---|---|---|
| どこも載せている | 業界の当たり前 | 無いと不利。クライアントに情報があるか確認する |
| 一部だけが載せている | 差をつける材料 | 載せれば強みになるか検討する |
| どこも載せていない | 空白 | クライアントが持っていれば独自の打ち出しになる |

**気をつけること**
- 🚨 **他社の数字はクライアントの事実ではない。** 「業界ではこれが普通」という参考にとどめ、クライアントの条件を聞くための材料に使う（事実の正は `documents/company-facts.md`）
- 調べた日と出典のURLを残す
- 🚨 **他社の文章や見せ方をそのまま写さない**
- 比較の結果はユーザーと統括の検討材料。クライアントには、それを踏まえた**提案**として出す

### 2-4. 提案の出し方（守ること4）

2-1〜2-3をまとめ、必ず次の形で出す。

| 区分 | 中身 |
|---|---|
| サイトの種類の見立て | 統括がどう判断したか（ずれていればユーザーがここで直す） |
| ベースから採用 | 基本一覧のうち、この案件でも使うもの |
| **追加の提案** | ベースに無いが要ると判断したもの。**理由を付ける** |
| **不要の提案** | ベースにあるが要らないと判断したもの。**理由を付ける** |

- 追加・不要の欄は、**該当がなくても「なし（理由）」と書く**。欄を埋める決まりにして、**ベースの丸写しで終わるのを防ぐ**
- 各候補には出所（要望／基本／競合／提案）を付ける

## 3. 手元の情報と照らし合わせる

§2の一覧に、手元の情報（旧サイト・パンフレット・会社案内など）を突き合わせて印を付ける。

| 印 | 意味 | 次にやること |
|---|---|---|
| ある | そのまま使える | 使う |
| 古い・食い違う | 古い、またはページ・資料によって違う | §4 の確認リストへ（**どれが正しいかはこちらで決めない**） |
| 無い | 本来あるべきなのに手元に無い | §4 の確認リストへ |
| 旧サイトにだけある | §2では出てこなかったが旧サイトにある | 残すかどうか検討する |

**リニューアルの場合は、旧サイトの棚卸しもここで行う**
- 全ページを一覧にする（URL・タイトル・中身の要約）。使える素材（数字・実績・写真・資格・沿革）を拾い出す
- 各ページに **残す／直す／捨てる／未定** の案を付ける。案は統括が作り、ユーザーと採否を決め、ユーザーがクライアントに伝える

**旧サイトで気をつけること**
- ページによって同じ数字が違う → 確認リストへ
- 外から中身が見えないページ（会員専用・外部システム）→ 存在を記録して扱いを聞く
- 書いてあることと実態が違う（例：「SSL通信を採用」とあるのに HTTPS につながらない）
- 作らないページの旧URLは公開時に消える → リダイレクト先を決める（`documents/build-checklist.md` フェーズ1「既存サイトからの移行方針」）

## 4. 足りない情報を聞く

§3で「古い・食い違う」「無い」になったものを、**クライアントにそのまま渡せる確認リスト**にする。置き場は **`documents/client-questions.md`**（ユーザーが口頭で聞くときの台本にもなる）。

- 1項目に **何を聞くか／なぜ必要か／回答欄** を持たせる
  - 例：「保証の上限額はありますか？（同業他社は金額を明記しているところが多く、比べる材料になるため）」
- **必須／あるとよい** に分ける。クライアントの負担を減らし、答えてほしい順番をはっきりさせる
- **クライアントが読める言葉で書く。** 社内の略語や台帳の番号だけで済ませない
- 🚨 **社内の台帳（`documents/build-checklist.md`）とは別ファイルにする**（台帳は社内用・確認リストはクライアントに渡すもの）。項目番号で対応させる
- **素材（写真・ロゴ・原稿）が足りない場合は `rules/modes/page-build.md` §4.4 と同じ扱い**＝1回でまとめて聞き、返事を待たずに作業用プレースホルダで先に進める

## 5. 優先順位と範囲を決める

| 区分 | 判断の目安 |
|---|---|
| 今回作る | 目的に直接つながる／情報がそろう見込みがある |
| 後で作る | 必要だが情報がまだ無い／更新する体制が整っていない |
| 作らない | 目的に合わない／他のページで足りる（例：関連リンクはフッターで足りる） |

- 区分の案は統括とユーザーで作り、🚨 **クライアントが決める**。予算・納期などクライアントの要望は、ユーザーが統括に伝える
- 「後で作る」「作らない」にしたものは、**理由と一緒に `documents/pending-issues.md` に記録する**。🚨 **誰がいつ「要らない」と言ったかも残す**（あとで「なぜ外したか」がわからなくなるのを防ぐ）
- 「後で作る」ものがあれば、ナビに後から項目を足せる余白を見ておく
- 制作範囲が変わるなら `documents/build-checklist.md` フェーズ0 の「制作範囲」を更新する

## 6. サイトマップ

- 「今回作る」ページを階層とナビに並べる
- 旧サイトから消えるページは、旧URLのリダイレクト先を決める
- 🚨 **ここでクライアントの合意を取る。合意してからページごとの内容設計（§7）に入る**
- 合意できたら `documents/build-checklist.md` フェーズ1 の「サイトマップの確定」「URL・ディレクトリ構成」「グローバルナビ・主要導線」を埋める

## 7. ページごとの内容設計

### 1ページの進め方

| # | すること | 持ち場 |
|---|---|---|
| 1 | **ページの目的と読者を一文で決める**（例：「全国をサポートする体制があることを、取引先に伝える」） | 統括 |
| 2 | **材料を並べる**：手元の情報・仮ワイヤー・原稿 | 統括 |
| 3 | **構成を考える**：読者が疑問に思う順にセクションを並べる | 統括 |
| 4 | **モックにドラフトを作る** | **開発**（委任カードで渡す） |
| 5 | **ユーザーと対話で詰める** | 統括 |
| 6 | **確認事項を記録する**（§8） | 統括 |

- 4で未確認の内容は、**見た目で区別して確認メモを付ける**。作法の正は `rules/modes/page-build.md` §6・§6.2（たたき台の4点セット）。ボタンで開閉できると打ち合わせで見せやすい
- 🚨 **最初から正式なファイル名で作る**（`draft.html` のような別名にしない）。理由と例外は `rules/modes/page-build.md` §2

### 詰めるときの観点

- **ユーザーがわからないところは、読者もわからない**：制度や仕組みの説明が要る（例：「そもそも○○保険とは」を足す）
- **ページの目的とずれる内容は置かない**：会社の信条など、大事でも別のページの話なら外す
- **内容の出所を分ける**：手元の資料にあった内容か、こちらが足した内容かを確認メモに書く。**足したものはクライアントの確認が要る**
- **見せ方も提案する**：地図とカードの連動や、関係を表す図など、文章以外で伝わる形を考える
- **補足の情報は補足とわかる見た目にする**：本筋と同じ強さで並べない

## 8. 確認事項の管理

| 置き場所 | 中身 | 誰が見るか |
|---|---|---|
| `documents/build-checklist.md` フェーズ0〜2 | 確定すべき項目と状態（`[ ]` `[?]` `[x]`） | ユーザーと統括 |
| `documents/client-questions.md` | 何を聞くか・なぜ必要か・回答欄 | **クライアント** |
| モックの確認メモ | そのセクションに関わる確認事項 | 打ち合わせで画面を見ながら |

🚨 **確認事項の台帳を新しく作らない。** `build-checklist.md` のフェーズ0〜2 がその台帳で、この手順はそこを埋める作業（進め方の正は `rules/modes/build-progress.md`）。

**回答が来たら**
1. ユーザーが回答を統括に伝える
2. 統括がモックへの反映をカードで渡す（未確認の印と確認メモを外す）
3. 🚨 **確定した事実は `documents/company-facts.md` に移す**（ページはそこから作る）
4. 台帳の状態を更新する。🚨 **推測で `[x]` にしない**（`rules/modes/build-progress.md`）

**経緯も残す**：決めたことの理由、外した内容の理由は `documents/pending-issues.md` に書く。

## 9. デザイン・実装に渡せる状態

1ページごとに、次の3つがそろったら渡せる。

- ページの目的と構成について、**クライアントの合意がある**
- **必須**の確認事項に回答がある（「あるとよい」は残っていてもよい）
- 未確認の内容がどこに残っているか、わかる（`page-build.md` §6.2 の4点セットに乗っている）

ここから先は `rules/modes/start.md`（Design.md の準備）と `rules/modes/page-build.md`（実装）へ。

## やってはいけないこと

| NG | なぜ |
|---|---|
| 手元の資料（旧サイト・パンフレット）から候補を作り始める | **もともと無い情報は候補にすら上がらない**。先に「本来あるべきもの」を出す（§2） |
| ベース一覧をそのまま提案に出す | 案件に合っていない。追加・不要の欄を埋めて初めて提案になる（§2-4） |
| 「追加の提案」「不要の提案」を空で出す | 該当なしでも「なし（理由）」と書く。空欄を許すと丸写しに戻る（守ること4） |
| 他社の数字をクライアントの事実として扱う | 事実の正は `company-facts.md`。他社の数字は参考にとどめる（§2-3） |
| 他社の文章・見せ方を写す | 権利の問題。参考にして自分で組む |
| 統括がクライアントと直接やり取りする | 窓口はユーザー（§0） |
| 開発セッションがヒアリングや競合調査を始める | この手順は統括の持ち場。開発が入るのは §7-4 から |
| どれが正しいかをこちらで決めて先に進む | 食い違いはクライアントに確認する（§3） |
| 「作らない」と決めた理由を残さない | あとで「なぜ外したか」がわからなくなる（§5） |
| サイトマップの合意を取らずに内容設計へ進む | 土台が動くと全ページ作り直しになる（§6） |
| `draft.html` のような別名でドラフトを作る | クライアントがナビから辿れない。正式アドレスへ移すときのリンク付け替え漏れも起きる（§7・`page-build.md` §2） |
| 確認事項の台帳を新しく作る | `build-checklist.md` フェーズ0〜2 が台帳。二重管理になる（§8） |
