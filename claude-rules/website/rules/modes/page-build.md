# 新規ページ作成ルール

> ## 🚨 2セッション構成での読み替え（`project-config.md`「エージェント構成」が `使う` のとき）
>
> このルールは**1セッション前提**で書かれている。本文に出てくる「ユーザーと配置・URL・素材を合意する」「`documents/company-facts.md` に事実を記録する」「`Design.md` を作る／更新する」は、
> 2セッション構成では**統括（`/director`）の持ち場**で、開発セッション（`/dev`）はそこへ入らない。
>
> **読み替えの正は [rules/modes/developer.md](./developer.md) §2。** ここには重複して書かない（片方だけ直して版がズレるのを防ぐため）。

ウェブサイトに **新しいページ（画面）を追加するとき** の実装手順をまとめたルール。

## このルールの位置付け

- 新規ページ／画面の追加依頼を受けたときに参照する
- 設計準備ルール（あれば `rules/modes/start.md` 等）と完成後チェックルール（あれば `rules/modes/check.md` 等）の **“間”＝実装フェーズ** を担う
- 大まかな流れ：**着手前合意 → 配置決定 → 雛形から作成 → 骨組み → コンテンツ確定 → 仕上げ確認 → 残課題記録**

> このルールは「新しくページを追加するときの手順」に絞る。ページ追加に限らない一般論（汎用的なコーディング規約・リファクタリング方針等）は `rules/modes/refactor.md` / `rules/modes/check.md` 側に委ねる。

---

## 0. 前提となる「置き場」を確認する（着手前）

このルールは 2 つの SSOT（単一の真実の源）を参照して動く。**着手前に有無を確認する。**

| 置き場 | 何の SSOT か | 無かったら |
|---|---|---|
| `Design.md` | **デザイン**（色・タイポ・余白・コンポーネント） | 勝手に作らず、作成を提案する（手順は `rules/modes/start.md`） |
| `documents/company-facts.md` | **コンテンツ（事実情報）**（会社・サービス・料金・実績・法的表記） | 雛形はテンプレートに同梱されている。記録が空なら、確定事実の記録から始める |

> 🚨 **「参照先が無い」は「推測で埋めてよい」ではない。**
> ファクト集が空なら、埋めるべきはページではなく**ファクト集のほう**。
> 一次情報が手元に無い項目は、**空欄のまま残してユーザーに要求する**（誤情報より空欄が安全）。

---

## 1. 着手前に合意する

推測で進めない。以下を **選択肢形式** でユーザーに確認し、合意してから着手する。

| 確認項目 | 例 |
|---|---|
| 雛形にする既存ページ | 「(例: サービス紹介ページ) を下敷きにしますか／ゼロから作りますか」 |
| 配置場所 | どのディレクトリ・階層に置くか |
| 素材の有無 | 原稿・画像・ロゴ・実績数値などが手元にあるか／後から差し替えるか |
| 画像で支給してもらう塊 | 装飾的な見出し・特典ボックス・バッジ・価格の飾り等を「文字で組むか／画像で支給か」（2セッション構成では統括が確認済み → `rules/modes/director.md` §4.1） |
| URL・ルーティング | 公開パス（URL）、ナビゲーションに載せるか、内部リンク元 |

不明点が複数あれば箇条書きで、答えやすい形にまとめて確認する。

---

## 2. 配置を決める

- 既存の **命名規則・ディレクトリ規則に揃える**（新しい流儀を持ち込まない）
- 理想的な構成と既存の構成が食い違う場合：
  - **新規ページは最適な配置にする**
  - **既存ページの移設は別課題として切り出す**（今回のページ追加に巻き込まない）。残課題として記録（後述 8）
- 🚨 **確認用のドラフトも、最初から正式なファイル名・正式な場所で作る**（`draft.html` `new.html` のような別名にしない）。
  理由：別名だと**ナビからたどれず、クライアントに見せられない**。さらに正式なアドレスへ移すときに**リンクの付け替え漏れ**が起きる（現場実例＝公開直前に移設とリンク修正が発生した）。
  前の版に戻したいときは**git の履歴で戻す**（ファイルを分けて持たない）。未確認の内容は名前ではなく**見た目と確認メモ**で区別する（後述 6.2）

---

## 3. 既存ページを雛形に作る

- 似た既存ページを下敷きにする。**複数ページの良い部分を取り入れる**（ヘッダ／フッタ／導線の優れた箇所を借りる）
- ヘッダー・フッター・パンくず等は **共通コンポーネント／テンプレート機構を使う**（例: インクルードやテンプレート部品）。同じ内容の **直書き・重複を避ける**
- 既存テンプレートに無い独自の流儀を新規ページだけに持ち込まない

---

## 4. 骨組みから作る

- まず **骨組み（構造）** を作る：ダミー文言・プレースホルダ素材・`TODO` コメントで、セクションの並びと階層を確定させる
- スタイルは **近い既存ページのものを暫定流用してよい**。ただし構成が固まったら **専用ファイルへ分離** する（暫定流用のまま放置しない → 残課題に記録）
- **ビルド／コンパイルの運用は [.claude/rules/scss-autocompile.md](../../.claude/rules/scss-autocompile.md)「自動コンパイル環境が有効なときの運用」に従う**（自動環境=フックが生成・依頼不要／無ければ開発者に依頼。AIは手動でビルドコマンドを叩かない）

### 4.2 コメントは配信出力の表に出さない

🚨 **HTML コメント（`<!-- -->`）は配信される HTML に残り、画面には描画されなくても
「ソースを表示」でクライアント・元請に読める。** 構造をなぞるだけの見出しコメント
（`<!-- ヘッダー -->` / `<!-- ここからメインビジュアル -->` 等）を機械的に並べない
＝**AI 生成を疑わせやすく、制作過程が必要以上に透けて見える**。
コメント自体は禁止ではない。意図・注意点・経緯は、**配信出力に残らない書き方**
（PHP／SCSS のコメント・開発者向け文書）で残す。

- **正は [.claude/rules/output-comments.md](../../.claude/rules/output-comments.md)**
  （逃がし先の一覧／消してよいコメントの4条件／🚨 **CMS・フレームワークが解釈するコメントは消さない**／作業用の後始末）。
  `paths:` で自動適用されるので、HTML・PHP・SCSS を触っていればこのファイルは読み込まれている
- 骨組み用の `TODO`（手順 4 冒頭）は**作業用**＝仕上げ前に配信出力から外す。
  🚨 **未解決のまま黙って消さない**（`documents/pending-issues.md` に移してから外す）

### 4.3 支給画像は、組み込むときに表示に必要十分なサイズへ縮める

🚨 **デザイナーの書き出しは、そのまま使わない前提で扱う。** デザインツール（Illustrator／Figma 等）は @2x〜@4x で書き出すのが普通なので、**支給画像が表示に対して大きすぎるのは案件を問わず毎回起きる**。実例＝**表示幅 約40px のアイコンに 1303×2516px・2.6MB** の画像が使われ、SP 用（`_sp`）はほぼ全数が表示幅の2倍を大きく超えていた（縮めた結果、使用中の画像が **合計 約25MB → 約14.6MB**）。

⚠️ **納品前チェックに任せると、公開直前か公開後まで放置される。** 公開後にまとめて直すと全画像の再アップが必要になる。
**目安の基準値は [rules/modes/check.md](check.md) A「解像度」が正**（ここには数値を書かない＝同じ基準を2箇所に持たない）。この節は**その基準を組み込みの時点で満たす手順**を定める。

- **表示幅は実測する。** CSS の指定値ではなく、ブラウザーで `getBoundingClientRect().width` を測る
  - PC は 1366px と大きめの幅（1920px 程度）、SP は 390〜430px 程度で測る
  - **背景画像（`background-image`）も同じ扱い。** `<picture>` の PC／SP 用は、**それぞれが実際に使われる幅**で測る
- **縮めたあとに圧縮もする。** 写真は形式どおりの圧縮。文字・イラスト中心の PNG は **減色（256色）も候補**にするが、**元の画像と並べて劣化が見えないものだけ**に適用する
- **元の書き出しは作業用の控えに残す**（後で大きく使い直せるように。公開ディレクトリには置かない）
- 🚨 **形式の変更はユーザーに確認してから。** 透過を使っている写真の PNG を JPG／WebP へ切り替えると、**見た目と参照の書き換えを伴う**

### 4.4 素材が無いときは自作せず、提供を聞いて、作業用プレースホルダで先に進める

🚨 **写真・ロゴ・アイコン・イラスト・原稿を、AI が作って埋めない。** 生成画像・拾ってきた代替画像・それらしく書いた文章で空欄を埋めると、**権利とブランドの判断をユーザーに代わって下したことになる**。しかも**見た目が成立しているので誰も気づけない**（公開されて初めて問題になる）。素材はユーザー／クライアントの持ち場（`documents/build-checklist.md` フェーズ2）。

**提供の可否は1回でまとめて聞く。**

- **何を・何点・どこに使うか**を具体的に挙げる（「トップのメインビジュアル1点」「サービス紹介3枚の写真」）
- **いつまでに要るか**と、**代案をセットで**添えて聞く＝①いただく ②**仮のまま公開して**後で差し替える ③このページを後回しにする（促し方の正は `rules/modes/build-progress.md` §5）。🚨 **②③はスコープの決定なので、選ぶのはユーザー**
- **SP 用が別に要るか**も一緒に聞く（§4.3）

**返事を待たずに他の部分を作る。** 素材待ちで全体を止めない（`rules/modes/build-progress.md`「フェーズは順番の目安」）。待っている間は**作業用プレースホルダ**を置く：

🚨 **これは上の②（仮のまま公開する）ではない。** 置くのは**差し替え前提の置き石**で、**待ちは閉じない**＝AI の判断で置いてよい。待ちを畳む「仮置き」との区別の正は `rules/modes/build-progress.md` §5 の表。

- **先に縦横比と表示幅を決めてから置く。** 決めずに置くと、**本物に差し替えた瞬間にレイアウトが崩れる**（差し替えは制作の終盤＝崩れに気づくのが一番遅い時期になる）
- **無地・単色**にし、**何が入る場所か**を文字で書く（例「メインビジュアル 1600×900」）。それらしい写真を置くと**本物と見分けられない**
- **プレースホルダを含むページの扱いは §6.2 の4点セットに乗せる**（単一フラグで切れる／「たたき台です」を表示する／視覚的に区別する／`noindex`）
- **残課題に記録する**（後述 8）

🚨 **プレースホルダは差し替え前提。置いても待ちは閉じない。** `documents/build-checklist.md` の該当項目は `[?]`（**誰の何待ちか**を書く）のままにし、**「対応済み」と書かない**。
**「仮のまま確定する（＝仮置き）」「今回は見送る」への切り替えは、AI の判断では決めずユーザーの明示合意を得る**（区別と理由の正は `rules/modes/build-progress.md` §5）。

## 5. コンテンツを正確に入れる（最重要）

骨組みのダミーを実コンテンツに置き換える段階。**ここで“もっともらしい嘘”を作らない。**

- **確定事実は `documents/company-facts.md`（事業ファクト集＝コンテンツの情報SSOT）から展開する**。ヒアリング等で確定した事実はページに直接書く前にまずファクト集へ記録し、そこを一次情報源にしてから展開する（**情報整理→展開** の順。会話履歴はセッションを跨いで消えるため）
- **もっともらしい仮の文章を「事実」として確定させない**
- **数値・仕様・固有情報は一次情報源（ファクト集）で裏取りする**（手元になければ推測で埋めず、ユーザーに要求）
- 実際に扱う対象の **“正しい出典”** で確認する
  - (例: 販売しているのが再販品／OEM なら、**再販元の公式情報**に合わせる。製造元や類似品のデータで代用しない)
- **根拠のない数値・主張は載せない**。載せるなら出典を確認する
- **ダミーと確定情報をコメント等で明示的に区別する**（例: `<!-- TODO: 仮値・要確認 -->`）＝**作業用の印なので仕上げ前に配信出力から外す**（前述 4.2。未解決のまま消さず残課題へ移す）
- 外部リンクは **公式情報を参照**し、新規タブで開く場合は `rel="noopener"` を付ける

### 5.2 外部の事実（制度・法令・第三者サービス）は扱いが違う

上記は **自社の事実**（ファクト集に集約できるもの）を想定している。
**助成制度・法令・他社サービスの仕様や料金など、一次情報源が社外にある事実**は、裏取りの方法が異なる。

- **一次情報＝運営者自身が公開している情報**（制度なら所管の官公庁、他社サービスならその提供元の公式サイト）。
  **まとめサイト・ブログ・比較サイトは一次情報ではない**
- 🚨 **AI（自分）の記憶を一次情報として扱わない。** 年度・制度・価格・法令・料金プランは陳腐化する。
  **「知っている」と「今も正しい」は別**。記憶から書いた時点で、それは裏取りではない
- **調べられないなら書かない。** 空欄・「詳細は公式サイトをご確認ください」のほうが、誤情報より安全
- 書くなら **出典（URL）と確認日** を残す（ページ内の注記、または `documents/company-facts.md`）
- **陳腐化しにくい書き方を優先する**：金額・期限・要件を本文に埋め込まず、
  **制度名＋公式リンク＋「最新の情報は公式サイトでご確認ください」** に寄せる
- **誰がいつ更新するかを決めてから載せる。** 更新の担い手が決まらない情報は、載せる前にユーザーに判断を仰ぐ
  （決めずに載せると、古い情報が残り続けて信頼を損なう）

---

## 6. 要確認情報は確定しない

依頼元（クライアント）の確認が必要な情報は、**確定で載せない**。

- 対象例：価格・料金、実績・導入数などの成果数値、法的表記（特商法・免責・資格・許認可番号 等）、お客様の声・固有名詞
- 仮置きする場合は **ダミーと明示** し、**残課題として記録**（後述 8）してユーザーに確認を依頼する
- **確認が取れて確定した事実は `documents/company-facts.md`（事業ファクト集）に記録する**（`公開可否`＝公開済み/公開可・未掲載/非公開 ＋ `出典` つき）。「**あえて非公開にする**」判断もファクト集に確定事項として残す（HTMLには痕跡が残らず、残さないと将来のセッションで再提案・誤掲載が起きる）

### 6.2 「たたき台」としてダミーを入れて作るときの作法

「議論のたたき台でいいからダミーで埋めて」という依頼は実務で頻出する。
このとき **HTML コメントでの区別だけでは足りない**（**通常の画面を見ている閲覧者にはダミーだと分からない**＝そのまま共有・公開されると誤情報になる。なお配信 HTML には残り、ソース表示では読める＝前述 4.2）。
次の 4 点をセットにする。

1. **単一のフラグで制御する** — ダミーの表示を 1 箇所のスイッチ（変数・定数・クラス）でまとめて切れるようにする。
   確定したらフラグを落とすだけで済み、消し忘れが構造的に起きない
2. **「たたき台です」と閲覧者に見える形で示す** — ページ上部の帯・バナー等。コメントではなく**表示**する
3. **ダミー部分を視覚的に区別する** — 背景色・破線枠など、確定部分と一目で見分けられるようにする
4. **`noindex` を付ける** — 検索結果に載せない

> ダミーを含むページは **残課題に必ず記録**する（後述 8）。「たたき台」のまま本番導線に載せない。

## 7. 仕上げ前の確認

- 使用している言語の **構文／Lint を確認**する（HTML/CSS/JS/テンプレート言語の文法エラー・タグ閉じ忘れ等）
- リンク先・画像パスが解決するか、プレースホルダ（`#` 等）が残っていないかを確認
- **完成後チェックのルールがあれば、そちらへ引き継ぐ**（`rules/modes/check.md` の画像／アクセシビリティ／レスポンシブ／SEO 等のゲートに通す）

### 7.2 導線（ナビ・リンク）とページは同時に公開する

**片方だけ反映すると必ず壊れる。**

- **導線だけ反映** → リンク切れ（404）
- **ページだけ作る** → どこからも辿り着けない（到達不能）

したがって **ナビゲーション登録は「あとで残課題」にしない**。ページ本体と同じタイミングで反映する。

- グローバルナビ等の**共通部品への追加は全ページに影響する**。手順 1 の合意対象に含める
- ⚠️ **順番に依存した CSS を壊していないか確認する**。ナビ項目を1つ増やすと
  `:nth-child(N)` / `:nth-of-type(N)` 指定は**指す相手がずれる**（増やした項目自体は正常に見えるのに、
  別の項目のスタイルが崩れる＝気づきにくい）。該当指定があれば、件数非依存のセレクタへ寄せる提案をする
- 段階公開が必要な場合（ページだけ先に用意する等）は、**到達不能にしない手当**
  （直リンクで共有する・`noindex` にする 等）をユーザーと合意してから行う

---

## 8. 残課題を記録

その場でやり切らなかった項目は、放置せず **残課題として記録**する（`CLAUDE.md`「残存課題の記録ルール」・`documents/pending-issues.md` 準拠）。

典型的な残課題：

- 暫定流用したスタイルの **専用ファイルへの分離**
- **サイトマップ・関連ページからの追加導線**（グローバルナビ本体の登録は残課題にしない → 手順 7.2）
- プレースホルダ素材・ダミー文言の **実素材への差し替え**
- 要確認情報（価格・実績・法的表記）の **クライアント確認**
- 別課題に切り出した **既存ページの移設**（手順 2）

各項目に「未対応の範囲・対象ファイル・確認すべき相手」を添える。

## やってはいけないこと

| NG | なぜ |
|----|------|
| ❌ 雛形・配置・URL を確認せず着手する | 手戻りの元。手順 1 の合意が先 |
| ❌ 仮の文章・数値を「事実」として確定する | 誤情報の公開。一次情報で裏取りする |
| ❌ 外部の事実（制度・法令・他社仕様）を **自分の記憶から** 書く | 記憶は陳腐化する。「知っている」と「今も正しい」は別。運営者の公式情報で確認するか、書かない |
| ❌ まとめサイト・ブログ・比較サイトを出典にする | 一次情報ではない。運営者自身が公開している情報に当たる |
| ❌ ダミーを HTML コメントの注記だけで区別する | 通常の画面を見ている閲覧者には分からない（一方で配信 HTML には残る）。表示される形（帯・視覚区別・`noindex`）とセットにする |
| ❌ 配信出力に残す必要のない説明用 HTML コメントを並べる | ソース表示でクライアント・元請に読める。実装メモは PHP／SCSS のコメント・開発者向け文書へ（手順 4.2） |
| ❌ 必要性を確認せず既存のコメントを消す | CMS・フレームワークが構文として使うコメント（WordPress ブロック等）を消すと壊れる（`.claude/rules/output-comments.md` 2.） |
| ❌ ページとナビ登録を別々のタイミングで反映する | リンク切れ or 到達不能。手順 7.2 |
| ❌ 別ブランド・類似品・製造元のデータを流用する | 対象（例: 再販品／OEM）の正しい出典と食い違う |
| ❌ 根拠のない数値・主張を載せる | 信頼性を損なう。出典を確認してから載せる |
| ❌ 要確認情報（価格・実績・法的表記）を確定で載せる | クライアント確認前。残課題にして確認を仰ぐ |
| ❌ ダミーと確定情報を区別せず混在させる | 後で「未確認なのに確定」になり判断を誤らせる |
| ❌ 共通部品を使わず同じ内容を直書きする | 重複・更新漏れの元。テンプレート機構を使う |
| ❌ 規約外の独自概念（色・命名・構造）を勝手に増やす | 既存の規則・Design.md に揃える |
| ❌ AIが手動でビルド／コンパイルコマンドを叩く | コンパイルは自動環境ならフック・無ければ開発者。生成済み `.css` は手編集しない |
| ❌ 残課題を口頭報告だけで済ませ記録しない | 取りこぼし。`documents/pending-issues.md` に残す |

## 自己チェック（仕上げ前に確認）

- [ ] 雛形・配置・URL・素材の有無をユーザーと合意したか？
- [ ] 既存の命名・ディレクトリ規則に揃えたか？（理想と既存の食い違いは別課題に切り出したか）
- [ ] 共通コンポーネント／テンプレート機構を使い、直書き重複を避けたか？
- [ ] `Design.md` と `documents/company-facts.md` の有無を確認したか？（無い／空なら、推測で埋めず作成・記録から始めたか）
- [ ] 数値・仕様・固有情報を一次情報源で裏取りしたか？（対象の正しい出典で確認したか）
- [ ] **外部の事実**（制度・法令・他社仕様）を自分の記憶で書いていないか？　出典URLと確認日を残したか？　陳腐化しにくい書き方（公式リンクへ寄せる）にしたか？
- [ ] ダミーを含むなら、単一フラグ・「たたき台」表示・視覚的区別・`noindex` をセットにしたか？
- [ ] ページ本体と導線（ナビ・内部リンク）を同時に反映したか？　順番依存の CSS（`:nth-child` 等）を壊していないか？
- [ ] ダミーと確定情報をコメント等で区別したか？
- [ ] 要確認情報（価格・実績・法的表記）を確定で載せず、残課題にしたか？
- [ ] 配信出力に残す必要のない説明用 HTML コメントを増やしていないか？　実装メモは出力に残らない書き方（PHP／SCSS のコメント・開発者向け文書）に置いたか？
- [ ] 消したコメントは説明用か？（CMS・フレームワークが解釈するものを消していないか。未解決の `TODO` を残課題へ移さず消していないか）
- [ ] 構文／Lint を確認し、完成後チェック（`rules/modes/check.md` 等）へ引き継いだか？
- [ ] 残課題（スタイル分離・ナビ登録・実素材差し替え 等）を `documents/pending-issues.md` に記録したか？
- [ ] コンパイルはプロジェクトの運用どおりか？（自動環境なら編集のみ／無ければ開発者に依頼。手動でビルドを叩いていないか）
