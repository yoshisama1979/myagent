# 制作進行モード — チェックリスト駆動でサイトを完成させる

制作中のサイトを **「あらかじめ用意したチェックリストを潰していく」** 形で完成まで運ぶためのルール。
AI は実装するだけでなく、**次に何が必要かをユーザーに促す進行役**を兼ねる。

`CLAUDE.md` の協働原則（不明点は都度質問 / より良い案は提案 / Design.md 優先）を土台とする。

## このルールの位置付け

```
start.md（開始ゲート）→ ★ build-progress.md（制作中の進行管理・繰り返し）→ check.md（公開前ゲート）→ seo-operation.md（公開後の運用）
                              │
                              └ 実装の作法は page-build.md / page-update.md / design-replication.md に従う
```

| 混同しやすいもの | 違い |
|---|---|
| `rules/modes/check.md` | **成果物の検品**。納品・公開の直前に通すゲート。「作ったものが正しいか」 |
| **このルール** | **未完成を完成へ運ぶ進行管理**。制作期間中ずっと繰り返す。「次に何が足りないか」 |
| `documents/pending-issues.md` | **判断が要る・今回は着手しない課題**の置き場（`PI-NNN`）。進捗の正本ではない（§7） |

## なぜ必要か

- サイトが完成しない理由の大半は **AI の手が止まったから**ではなく、**決め事・原稿・素材・アカウントが揃わないから**。誰かが「次にこれが要る」と言い続けないと止まる。
- 進捗を会話履歴に置くと **セッションを跨いで消える**（`documents/company-facts.md` が事実に対して担うのと同じ問題）。**進捗はファイルに置く**。
- 「あと何が残っているか」が一覧で見えないと、ユーザーは判断できず、AI は目についたところから場当たりに手を付ける。

---

## 原則

| 原則 | 中身 |
|------|------|
| **進捗はファイルが正** | 会話・記憶・印象で進捗を語らない。台帳（§1）を読んでから話す |
| **AI が次の一手を出す** | 毎回「次にやること」を提示して終わる。ユーザーの指示待ちで止まらない |
| **ひな形は出発点** | 同梱のひな形をそのまま使うのではなく、**案件に合わせて足し・落とす**（§1.2）。足りない工程に気づいたら提案する |
| **促すが、押し付けない** | 1回の提示は **合計3件まで**（AI作業・お願い・判断を合わせて）。判断は選択肢形式で答えやすくする |
| **担当を分ける** | AI ができない作業（原稿・写真・ロゴ・ドメイン・サーバー・各種アカウント・法務確認）は **依頼として明示**する |
| **待ちで止めない** | ユーザー待ちの項目がある間も、依存しない項目を先に進める |
| **確認できたものだけ完了にする** | 推測・実装した記憶で `[x]` にしない（§6） |
| **消さずに閉じる** | 該当しない項目は削除せず `[-]`（対象外）＋理由。消すと「最初から無かった」ことになる |
| **潰した都度に書く** | まとめて後で更新しない。1件終わるごとに台帳を更新する |

## §1 台帳（チェックリスト）の用意

### 1.1 置き場

| 状況 | 置き方 |
|---|---|
| **案件が1つ**（サイト1本） | `documents/build-checklist.md` の1ファイルで持つ（既定） |
| **案件が複数**（LPを都度制作、フェーズ分割納品 等） | `documents/build-checklist.md` を **ハブ（案件一覧＋サイト共通の項目）** にし、案件ごとに `documents/build-checklist/<案件ID>.md` を作る（§1.3） |

- 台帳が **このプロジェクトの進捗の SSOT**。`Design.md`（デザイン）・`documents/company-facts.md`（事実）と並ぶ3本目。
- テンプレートには **ひな形 `documents/build-checklist.md` が同梱**されている（標準工程の項目カタログ）。**ひな形は番号を持たない**。案件へ展開したときに `B-NNN` を採番する。

### 1.2 案件用に育てる（ひな形 → 台帳）

1. ひな形を読み、`project-config.md`・`Design.md`・サイトマップ（ページ一覧）と突き合わせる
2. **展開**：ページ数・LP本数など、この案件で複数になる項目は**実体の数だけ行を起こす**（例：ひな形「各ページ実装」→ `B-021 トップ` `B-022 会社概要` …）
3. **追加**：ひな形に無いこの案件固有の工程は **提案して合意のうえ足す**（例：多言語対応・予約システム連携・既存サイトからの移行）。**ひな形に無いことを「やらなくてよい」と解釈しない**
4. **対象外化**：当てはまらない項目は **削らずに `[-]`＋理由**
5. ドラフトをユーザーに提示し、**合意を得てから**書き込む（`start.md` §1 と同じ作法。勝手に作らない）

> 🚨 台帳が無いことを「制作フェーズではない」と解釈しない。制作中のプロジェクトで見つからなければ、まず用意を提案する。

### 1.3 1プロジェクトに複数案件があるとき

同じサイト・同じ顧客の中で、**LPを1本ずつ作って都度納品する**ような進み方に対応する。

- **分割の条件**：2件目の納品単位が発生した時点で、ハブ＋案件別ファイルへ移行する（1件のうちは分割しない）
- **ハブ `documents/build-checklist.md` が持つもの**
  - **案件一覧**：`案件ID / 名称 / 状態（進行中・公開確認中・完了）/ 台帳ファイルへのリンク / 一行の現在地`
  - **サイト共通の項目**：案件を跨いで一度だけ片付ける工程（`Design.md`、共通ヘッダー・フッター、計測タグ、`robots.txt` / `sitemap.xml`、フォーム基盤 等）。**2件目以降の案件で作り直さない**
- **案件別ファイルが持つもの**：その納品単位のフェーズ0〜8（`check.md` のゲートも案件ごとに通す）
- **番号 `B-NNN` はプロジェクト全体の通し番号**（ファイルを跨いでも重複させない）。理由：依存関係・`PI-NNN` からの参照が壊れないようにするため
- **完了した案件**：ハブの状態を「完了」にし、**台帳ファイルは残す**（消さない）。ハブの一覧は**進行中を上**に置く
- 報告は **案件単位**で出す（§出力フォーマット）。複数案件が同時進行なら、**次の一手はプロジェクト全体で合計3件まで**

## §2 標準工程（大分類）

**フェーズの大分類はこのルールが正。各フェーズの具体項目はひな形／台帳が正**（版ズレを避けるため、細目をこのルールに書かない）。

| # | フェーズ | 狙い | 主な担当 | 単位 |
|---|---|---|---|---|
| 0 | 前提の確定 | 目的・対象ユーザー・公開時期・公開先・触ってよい範囲 | ユーザー | 案件 |
| 1 | 情報設計 | サイトマップ（ページ一覧）・各ページの目的とゴール・導線 | AI + ユーザー | 案件 |
| 2 | 素材・原稿 | 原稿、写真、ロゴ、事業ファクト（`documents/company-facts.md` へ集約） | ユーザー / クライアント | 案件 |
| 3 | デザイン規約 | `Design.md` の作成・更新（`start.md` §1） | AI + ユーザー | **共通**（原則1回） |
| 4 | 実装 | ページ・共通部品・レスポンシブ（`page-build.md` / `page-update.md`） | AI | 案件（共通部品は共通） |
| 5 | コンテンツ確定 | 仮置き・ダミーの解消、要確認情報の裏取り | AI + ユーザー | 案件 |
| 6 | 公開準備 | 計測タグ、フォーム、`robots.txt` / `sitemap.xml`、404、favicon 等 | AI + ユーザー | **共通**（案件固有のOGP等は案件） |
| 7 | 公開前チェック | `check.md` の **A〜I** を通す（**飛ばせないゲート**） | AI | 案件 |
| 8 | 公開・公開後 | 反映 → **公開URLでの実測（`check.md` の J）** → 納品・引き渡し。以後は `seo-operation.md` へ | ユーザー（反映）+ AI | 案件 |

- **フェーズは順番の目安であって、直列に進める必要はない**（素材待ちの間に実装を進める等）。
- **確認先のURL（ローカル／ステージング／本番）は `project-config.md`「URL・確認環境」が正**。表示を見る・スクリーンショットを撮るたびにユーザーへ聞かず、まずそこを読む。未記入ならフェーズ0で埋める（納品単位が複数なら案件ごとに行を足す）。
- **`check.md` の J（反映）はフェーズ8で行う**。J は「反映後」にしか確認できないため、フェーズ7で通すのは A〜I。
- **CMS（WordPress 等）を使う案件**は、フェーズ6に CMS 固有の工程が加わる（検索エンジンのインデックス設定の戻し・管理画面の保護・管理者アカウントの整理・更新方針）。該当しなければまとめて `[-]` にする。
- **フェーズ7には「お客様（クライアント）確認とチェックバック対応」が入る**。内部チェック（`check.md`）を通しただけで納品にしない。

## §3 記法

各項目は1行。通し番号 `B-NNN`。

```markdown
- [ ] B-012 ｜ 会社概要ページの実装 ｜ 担当: AI ｜ 依存: B-005 ｜ 更新: 2026-09-01
- [?] B-007 ｜ 施工事例の写真3点 ｜ 担当: ユーザー ｜ 依頼先: クライアント ｜ 更新: 2026-08-25 ｜ 督促: 2
```

| 状態 | 意味 |
|---|---|
| `[ ]` | 未着手 |
| `[~]` | 進行中 |
| `[?]` | **待ち**（回答・素材・アカウント等の待ち）。**誰の何待ちかを必ず書く** |
| `[x]` | 完了（**確認できたものだけ** — §6） |
| `[-]` | **閉じた**（対象外／今回のスコープ外。**理由必須**。見送り合意なら `PI-NNN` を併記） |

- **これは機械可読の記法であって、Markdown 標準のチェックボックスではない**（`[~]` `[?]` `[-]` はビューアでチェックボックスとして描画されない）。台帳はテキストとして読む前提で扱う。
- **担当は必ず一者**（`AI` / `ユーザー`）。クライアント作業もユーザー経由で依頼するため担当は `ユーザー`、実際の作業者は `依頼先:` に書く。
- **依存**：先に終わっていないと着手できない項目の番号（あれば）。
- **督促**：`[?]` の項目にだけ付くカウンタ（§5）。
- **採番規律**：新規は「既存の最大番号＋1」。**欠番を再利用しない・一度付けた番号を変えない・並べ替えても振り直さない**（依存と `PI-NNN` からの参照が壊れるため）。

## §4 毎回の回し方

### Step 0. 台帳を読む

`documents/build-checklist.md`（複数案件ならハブ＋対象案件のファイル）を読む。**会話の記憶から進捗を語らない**。

### Step 1. 実状態と突き合わせる（軽く）

台帳と実物がズレていないかを確認する（詳細は §6）。ズレていたら **先に台帳を直す**。

### Step 2. 次の一手を選ぶ

1. **他を止めているブロッカー**（依存元になっている項目）
2. **ユーザー待ちで動いていない項目**（＝促す。§5）
3. **フェーズの早い項目**（0→8 の順）
4. 効果が大きく工数が小さい項目

### Step 3. 提示する

**合計3件まで**に絞り、「AI がやること」「ユーザーにお願いすること」「決めてほしいこと」に分けて出す。

> 🚨 **2セッション構成（`rules/modes/director.md`）で運用している場合**、この「AI がやること」は **統括が自分で実装することではない**。制作ファイルの変更は委任カード `H-NNN` にして `documents/handoff.md` へ渡す（閾値は `director.md` §4）。提示のしかたは変わらないが、**実行者が開発セッションになる**点だけ読み替える。

### Step 4. 実施する（合意後）

- 実装は `page-build.md` / `page-update.md` / `design-replication.md` に従う
- 事実（数値・料金・実績等）を扱うときは `documents/company-facts.md` を一次情報源にする
- **本番反映・外部送信・破壊的操作は AI が実行しない**（`project-config.md`「デプロイ先・手順」）

### Step 5. 台帳を更新して報告する

- 終わった項目を **その都度**更新（状態・更新日）
- **新たに判明した工程の追加は2種類に分ける**
  - **合意済みの完成条件に必要なもの**（抜けていた工程・見つかった不具合）＝ **その場で追加してよい**。追加したことを報告に含める
  - **スコープを広げるもの・任意の改善**（あると良い機能、デザインの作り直し等）＝ **勝手に足さない**。ユーザーの合意を得てから `B-NNN` にするか、`documents/pending-issues.md` へ回す
- 報告フォーマット（後述）で締め、**必ず「次の一手」を含める**

## §5 促し方（このモードの本体）

- **毎回の締めに、ユーザー担当の項目を再掲する**（何のために必要かを1行添える）。
- **督促の判定は機械的に行う**：
  - 「1回」＝ **このモードで進捗レポートを出した回**（`/progress` の実行やまとまった作業の区切り）
  - `[?]` を再掲したら、その項目の **`督促:` を +1** する
  - **`督促:` が2以上の項目は、報告の冒頭に出す**（印象で判断しない）
  - その項目が動いたら（受領・回答・状態変化）**`督促:` を 0 に戻す**
- 促すときは **代案とセット**にする。「原稿が来ないと止まります」ではなく「①いただければ差し替えます ②仮原稿で先に組んで後で差し替えます ③このページを後回しにします」。
- **仮置きへの切り替え・`[-]`（今回は見送り）への変更は、いずれもユーザーの明示合意が要る**（AI の判断だけで待ちを畳まない）。仮置きにした場合は `page-build.md` §6.2「たたき台の4点セット」に従う（フラグ・閲覧者に見える帯・視覚的区別・`noindex`）。
- 促しはあくまで進行のため。**期限・スケジュールを AI が決めない**（示すのは「何が止まっているか」まで）。

---

## §6 「完了」の判定（推測で ✅ にしない）

`[x]` にしてよいのは、**確認した**ときだけ。

| 種類 | 完了と言ってよい根拠 |
|---|---|
| 実装 | 対象ファイルが実在し、ブラウザ（またはローカル）で表示を確認した |
| 反映（デプロイ） | **公開URLを実際に取得して確認した**。「アップした」と「公開URLで確認できた」は別（`check.md` J） |
| 素材・原稿 | 受領した実物を確認した（「送ると言われた」は `[?]` のまま） |
| ユーザー判断 | ユーザーの **明示的な回答**があった。沈黙・話題の移動を承認と解釈しない |

- 台帳が実態より **進んでいる**ときは戻す（`[x]` → `[~]`）。**遅れている**ときは根拠を添えて進める。

### ゲートと締め

- **フェーズ0〜6の該当項目**（`[x]` または `[-]`）が片付いたら、フェーズ7＝`check.md` の A〜I へ進む。
  台帳の**全項目**が片付くのを待たない（フェーズ7・8自体が台帳の項目のため、それでは進めない）。
- **`check.md` で指摘が出たら**：フェーズ7の項目は `[~]` のままにし、**指摘ごとに修正用の `B-NNN` を追加**する。修正後に該当チェックを再実施して初めて `[x]`。
- **案件の締め**：フェーズ8まで終わったら、その案件の状態を「完了」にする（複数案件ならハブの一覧も）。
  以後の改善は台帳に `B-NNN` を足さず、`seo-operation.md`（運用・SEO）と `documents/pending-issues.md` 側で扱う。

## §7 他ファイルとの棲み分け

| ファイル | 役割 | 境界 |
|---|---|---|
| 台帳（`documents/build-checklist.md` ほか） | **完成・納品までに片付ける工程**の正本 | 進捗の状態を持つのはここだけ |
| `documents/pending-issues.md` | 判断が要る・今回は着手しない課題（`PI-NNN`。`CLAUDE.md`「残存課題の記録ルール」準拠） | **同じ作業を両方に載せない**。台帳の項目を見送ると決めたら `[-]`＋`PI-NNN` を書き、以後の正本は PI 側 |
| `documents/company-facts.md` | 確定事実（`F-NNN`） | 事実そのものは台帳に書かない。**参照する** |
| `Design.md` | デザインの SSOT | デザイン判断を台帳で決めない |
| `documents/rule-improvements.md` | ルールへの気づき（`RI-NNN`） | 進行の詰まりが **ルール起因**なら、ここにも1行残す。**ひな形に足りない汎用工程**に気づいたら `[テンプレ還元]` 印で記録する |

## 出力フォーマット

### 進捗レポート（作業の区切りごと）

```markdown
## 制作進捗：<案件名>

**現在地**: フェーズ4 実装（完了 18 / 対象 29・別途 対象外 3）
**今回進めたこと**: B-012 会社概要ページ実装 / B-014 共通ヘッダー差し替え

### 🔴 止まっています（2回以上お待ちしています）
- B-007 施工事例の写真3点 — 事例ページの実装がこれ待ちです（①いただく ②仮画像で組む ③後回し）

### 🙋 お願いしたいこと
- B-019 料金改定の有無 — 料金ページに載せる数値が確定できません

### 次の一手（AI）
次は「B-015 お問い合わせフォームの実装」に進むのが効果的です。着手してよいですか？
```

- **集計の分母**：`対象` ＝ `[ ] [~] [?] [x]` の合計（**`[-]` は分母に入れず、別に件数だけ書く**）。
- 冗長にしない。長い経緯を再説明しない（`CLAUDE.md`「3. 作業のまとまりごとに…報告をする」と同じ姿勢）。

## やってはいけないこと

| NG | なぜ |
|----|------|
| ❌ 台帳を読まずに進捗を語る | 記憶はセッションで消える。ファイルが正 |
| ❌ 実装した記憶だけで `[x]` にする | 反映漏れ・未確認の完了報告になる（§6） |
| ❌ 該当しない項目を削除する | 消えた項目は「最初から無かった」ことになる。`[-]`＋理由で閉じる |
| ❌ ひな形をそのまま台帳にする | 案件固有の工程が抜ける。展開・追加・対象外化をして初めて台帳になる（§1.2） |
| ❌ ひな形に無い工程を「やらなくてよい」と解釈する | ひな形は出発点であって完成条件ではない |
| ❌ 任意の改善を AI 判断で `B-NNN` に足し続ける | 完成条件が膨らみ、いつまでも終わらない（§4 Step 5） |
| ❌ 残項目を全部並べて「どれをやりますか」と聞く | 判断を丸投げしている。合計3件に絞って提案する |
| ❌ ユーザー待ちを理由に手を止める | 依存しない項目を先に進める。待ちは代案とセットで促す |
| ❌ AI の判断だけで仮置き・見送りに切り替える | スコープの変更はユーザーの決定事項（§5） |
| ❌ 期限・スケジュールを勝手に決める | 期日はユーザーが決める。AI は「何が止まっているか」を示す |
| ❌ 台帳が埋まったことを「公開してよい」と報告する | 公開前ゲートは `check.md`。フェーズ7を飛ばさない |
| ❌ 2件目の案件を1件目の台帳に混ぜて追記する | どの納品単位の進捗か分からなくなる。§1.3 で分割する |
| ❌ 本番反映を AI が実行する | デプロイはユーザーの担当（`project-config.md`） |
