# 見積もり作成ルール（クライアント向け見積書）

クライアントへ出す **見積もりを作る／改定する／精査する** ときのルール。
サイト制作（ページ制作＋付随システム）を想定し、**金額表そのものの作り方**（項目立て・積み方・出力形式・検算）を定義する。

> **[rules/modes/deck-format.md](./deck-format.md) との分担（重複定義しない）**：あちらは見積もりを **どう提示するか**（スライド資料・PDF）。本ファイルは **どう作るか**（積算・出力・検算）。
> **固有値は本文に書かない**：人日単価・割引方針・宛先・請負範囲・過去見積の置き場・消費税は `project-config.md`「見積もり」節が正。

## いつ参照するか

- 見積もりの作成・改定・精査を依頼されたとき
- 過去見積を参照して新規見積を組むとき
- クライアント支給の仕様書・RFP・要綱を読んで金額に落とすとき

---

## 0. 大前提：値付けはユーザー（人間）が決める

- AI が作るのは **項目立て・数量・工数・計算・検算まで**。**単価・割引率・最終金額の決定と、クライアントへの提示はユーザー**が行う。
- 手元にない数字を推測で埋めない。不明は `【要確認】` として残す（空欄のまま流さない）。
- 見積書ドラフトを **クライアントへ直接送らない**（ユーザー確認用ドラフトまで）。

---

## 1. 支給資料の読み取り（推測で報告しない）

仕様書・要綱・過去見積などクライアント支給ファイルは、**中身を語る前に「読めたか」を判定する**。

- PDF は `pdftotext -layout` を試す。**日本語が落ちる**（英数字だけ抽出できる）場合は、フォントに文字マッピング情報（ToUnicode CMap）が無く、OCR が無ければ本文は読めていない。
- 🚨 **判定は文書全体でなく「見積もりの根拠にするページ」単位で行う。** 一部ページだけ日本語が取れる PDF や、本文は取れるが**表だけ画像**の PDF は、全体では「読めた」ように見える。`pdftotext -f N -l N` でページごとに抽出し、**根拠にするページ・表が空か極端に短ければ、そのページは未読として扱う**（総ページ数と抽出できたページ数を照合する）。
- 🚨 **読めていない資料から、抽出できた断片（数字・単語）を拾って内容を推測して報告しない。**
  - 実例：`225 / 21 / 14 / 154 / 17` という数字列を「ページ数の内訳らしき数字」として報告したが、実際は応募資格に書かれた **法令番号**（民事再生法 平成11年法律第225号 第21条／会社更生法 平成14年法律第154号 第17条）だった。誤読のまま見積もりを組めば、**前提から崩れる**。
- **読めないと分かった時点で、ユーザーに本文の提供（会話への貼り付け・テキスト書き出し）を依頼する。** 貼り付けてもらえば確実に読める。待ちが発生しても、推測で進めて作り直すより安い。
- やむを得ず断片に触れるときは「**推測**」と明示し、確定情報として扱わない・**金額の根拠にしない**。
- **Excel（.xlsx）の過去見積**は、「正本にしない」（§4）と「参考として読めるか」を**分けて扱う**。読み取りを試すのは構わないが、**変換結果を検証できたときだけ**参考にする＝行数・列数が原本と一致し、`#DIV/0!` 等のエラー値が無く、小計と総額が再計算と一致すること。検証できなければ「読めない資料」として本文の提供を依頼する。

## 2. 積み方の原則 — 測り方を対象に合わせる

**同じ案件でも、作業の性質ごとに測り方を変える。**

| 作業の性質 | 測り方 | 例 |
|---|---|---|
| 繰り返しがある（同型の量産） | **単価 × 数量** | 下層ページ制作、バナー、記事の流し込み |
| 繰り返しがない（機能・設計・調査） | **機能単位の人日** | フォームシステム、CMS 組み込み、要件整理、既存改修 |

- 🚨 **ページ数が少なく、システム比重が高い案件に「ページ単価」だけを当てない。** 制作費はページ数に比例しても、システムの工数は比例しない。
- 🚨 **同名の項目でも中身が違う。** 過去の「フォーム設置 0.8人日」（メール送信のみ）と、今回の「フォームシステム一式」（DB蓄積・管理画面・CSV出力・自動返信・スパム対策・メール到達性検証）は別物。**名前が一致しても、内容欄（§6）まで突き合わせてから流用する。** そのまま当てれば大幅な過小見積もり＝赤字受注になる。
- 実装だけでなく **仕様整理・確認作業・修正対応・公開作業** も行として立てる（実装に埋もれると無償労働になる）。
- 工数が振れる項目は、**分岐条件を備考に書く**（例：「支給素材が無い場合 +N人日」）。

## 3. 過去見積の扱い

過去見積は **参考であって根拠ではない**。

- **個数 0 だった行の単価は、実際には検証されていない**（一度も請求されていない＝実績がない）。初めて使うときは実態から積み直す。
- **割引率をそのまま当てない**（§7）。
- **比較は同条件で行う（最重要）**：
  - 🚨 「ページ単価は据え置き」等の結論を出す前に、**比較する 2 つの範囲が揃っているか**を確認する。今回の「ページ制作費のみ」と過去の「システム・オプション込みの総額」を比べると、**AI が自信をもって誤った結論を出す**（訂正が必要になり、クライアントに説明した後なら信用を失う）。
  - 比較は **総額どうし／制作費どうし** で行い、**何と何を比べたかを必ず併記する**。
  - 乖離があれば「構造の違い（今回はシステム比重が高い 等）」で説明し、見積書の冒頭や送付文に 2〜3 行添える。

## 4. 出力形式

- **CSV / UTF-8（BOM 付き）** で書き出す。
  - BOM 無しは Excel で開くと文字化けする。
  - **Excel（.xlsx）で正本を作らない**＝AI が読み書きできず、改定のたびに人手が要る（過去見積が .xlsx だったために作業を依頼できず、ユーザー自身が「CSV で書いてもらうのがよいか」と提案する事態になった実例がある）。CSV なら積算・検算・改定まで AI が担当できる。
- **計算する数式を入れず、値だけを書く。**
  - 🚨 **エラー文字列（`#DIV/0!` `#REF!` `#N/A` 等）を出力に混入させない。** 個数 0 の行で「実質単価＝料金÷個数」が 0 除算になり、`#DIV/0!` が 21 箇所そのまま印字された見積書がクライアントへ提出されていた実例がある。**0 除算になる欄は空欄にする。**
  - **例外は「文字列を固定する目的の `="…"`」だけ。** 🚨 `1-1` `2-2-1` のような**階層番号を素のまま書くと、Excel で開いた瞬間に日付へ変換される**（`1-1` → `1月1日`）。§6 のとおり**発注者の仕様書の業務項目番号をそのまま区分にする**ので、この形はこのテンプレートの標準構成で実際に起きる。該当する列は **`="1-1"` の形**（文字列を返す式）で書き、**実際に Excel で開いて確認する**。計算する式（`=B2*C2` 等）は入れない＝上のエラー値が印字される経路はこちら。
- 書き込みが `EPERM: operation not permitted` で失敗したときの手順（**Excel で開かれている、と決めつけない**。権限・同期ソフト（OneDrive 等）・別プロセスでも同じエラーになる）：
  1. **原因を確認する**：ファイルの権限、同名の一時ファイル（`~$*.xlsx`）の有無、同期ソフトの動作。分からなければユーザーに「そのファイルを開いていますか」と聞く。
  2. **別名保存は一時退避**として扱う（`*-tmp` 等、正本と紛れない名前にする）。**これで完了にしない。**
  3. **ロックが解けたら、`project-config.md` の見積書の正本パスへ反映し、一時ファイルを消す。**
  4. 🚨 **正本が 1 本になったことを確認するまで、作業を完了と報告しない。** 別名保存したまま報告すると、どれが正のファイルか分からなくなる（黙って版を増やさない）。

## 5. 標準の列構成（12列）

```
区分, 大項目, 中項目, 小項目, 内容・含まれるもの, 個数, 単位, 工数(日/件), 単価, 定価, お見積額, 備考
```

- **項目を大／中／小の 3 段階に分ける**と、Excel 側でフィルタ・ピボットが効き、クライアントも階層で読める。
- **列を増やすのは構わないが、上記 12 列は削らない**（とくに「内容・含まれるもの」「備考」＝§6・§9 が成り立たなくなる）。
- **金額の列はこの 2 つ（`定価`・`お見積額`）だけにする**（割引の途中経過を何列も並べると読み手が混乱する）。**割引が無い案件でも `お見積額` 列は置き、`定価` と同額を入れる**（総額を常に1列で追えるようにする＝案件ごとに列数が変わらない）。
- 🚨 **金額セルは桁区切りを入れない**（`1,200,000` ではなく `1200000`）。カンマは CSV の区切りと衝突し、数値としても読めなくなる。表示上の桁区切りは Excel 側の書式で付ける。

## 6. 区分の決め方と内容欄

### 区分

- **発注者の仕様書・RFP があるなら、その業務項目番号をそのまま区分にする。** 評価者が仕様書と見積書を 1 対 1 で突き合わせられる（採点のある案件で有利）。
- 無ければ費用の性質で分ける（例：制作費／システム／コンテンツ／共通費用）。
- 🚨 **共通費用（ディレクション・進行管理・サーバー設定 等）は制作費の外に出す。** 制作費に混ぜるとページ単価の計算が狂い、§3 の比較もできなくなる。

### 内容欄（「内容・含まれるもの」）

**1 行で必ず書く。空欄にしない。** 効用は 3 つ：

1. 値引き交渉で「この機能を外せばいくら下がる」が即答できる
2. 過去案件との差を説明できる（§2 の「同名でも別物」を防ぐ）
3. 受注後の「これも入っていると思った」を防ぐ

### 範囲外の項目（正規形を固定する）

**削除せず、個数 0 の行として残し、理由を備考に書く。** 漏れではなく **意図的な除外** であることが伝わる。

🚨 **範囲外行の書き方は 1 通りに固定する**（エージェントごとに解釈が割れると §8 の検算が通らない）：

| 列 | 範囲外行の値 |
|---|---|
| `個数` | **`0`** |
| `工数(日/件)` `単価` `定価` `お見積額` | **すべて空欄**（`0` を入れない＝0 円で受けると読まれる。0 除算も起きない） |
| `備考` | **除外の理由を必ず書く**（例：「今回は対象外（元請け担当）」） |

- 範囲外行は **§8 の行計算チェック（`個数 × 単価 = 定価`）の対象外**とする。
- 逆に、**範囲外行の金額セルに `0` や数値が入っていたらエラー**として検出する（機械判定できる）。

## 7. 割引

- 割引率は `project-config.md`「見積もり」節の方針に従う。**AI が勝手に決めない**（§0）。
- 🚨 **割引後の「実効人日単価」を出し、採算下限を下回っていないか必ず確認する**（原価割れの検知）。

  ```
  実効人日単価 ＝ 割引後の総額（税別・共通費用を除く制作分） ÷ 積み上げた必要工数（人日）
  判定：実効人日単価 ＞= 採算下限の人日単価   → OK
        実効人日単価 ＜ 採算下限の人日単価   → 🚨 原価割れ。ユーザーに報告して判断を仰ぐ
  ```

  - **「標準の人日単価」と「採算下限の人日単価」は別の値**。両方 `project-config.md`「見積もり」節にある。**標準単価で割ってはいけない**＝1%でも割り引けば必ず「必要工数を下回る」ことになり、正常な割引まで赤字判定してしまう（判定が意味を失う）。
  - **採算下限が未記入なら、判定できない。** 勝手に決めず、ユーザーに一度確認して `project-config.md` に記入してから進む（次回以降は聞かない）。
  - 金額のまま眺めても気づけない。**必ず人日単価に割り戻して比べる。**
- 🚨 **過去案件の割引率をそのまま当てない。** 大幅割引はページ数が多く量に余裕があったから成立したもので、**ページ数が少なくシステム比重が高い案件に同率を当てると原価割れする**。
- 割引の理由（数量・継続・戦略）を備考に残す。

## 8. 検算（省略禁止）

金額を出す前に、**必ずスクリプトで再計算し、集計と一致することを確認する**。目視で足し算しない。

### 金額の検算

- [ ] 行ごとの `個数 × 単価 = 定価` が一致する（**範囲外行＝個数0 は対象外**・§6）
- [ ] 区分ごとの小計の合計 ＝ 総額
- [ ] 割引後の金額 ＝ 定価 ×（1 − 割引率）／端数処理の方針も明記する
- [ ] 消費税（`project-config.md` の税率）と、税別／税込の表記が一致している
- [ ] **実効人日単価が採算下限を下回っていない**（§7）

### CSV 構造の検証（列崩れを目で見つけるのは不可能）

- 🚨 **CSV は文字列連結で書かない。** 必ず CSV ライブラリ（Python の `csv` モジュール等）で書き出す。`内容・含まれるもの` と `備考` には**カンマ・引用符・改行が確実に入る**ため、手書き連結すると列がずれる。ずれた CSV は Excel で開いても一見それらしく見え、**金額の行が1列横にずれたまま提出される**。
- 書き出したあと、**同じファイルを読み直して検証する**（書きっぱなしにしない）：
  - [ ] **全行の列数が 12（§5 の列数）で揃っている**
  - [ ] 金額・個数・工数の列が**数値として読める**（桁区切りカンマ・全角数字・単位文字が混ざっていない）
  - [ ] 先頭に **BOM** が付いている（`\xef\xbb\xbf`）
  - [ ] エラー文字列（`#DIV/0!` `#REF!` `#N/A`）が 1 つも無い
  - [ ] 範囲外行以外に、意図しない空の数値セルが無い

🚨 **検算していない数字を報告に書かない。**

## 9. 未確定項目の扱い

- 金額・数量が確定していない行は、**備考に `★` を付ける**。
- `★` の行には「**金額が動く方向**」を書く（例：「ページ数確定で増減」「支給素材が無い場合は増」）。
- **仮置きを確定値のように扱わない。** 総額を示すときは「★ を含む」と明記し、★ が総額をどう動かすかを併記する（§10）。

---

## 10. 報告に含めること

見積もりドラフトをユーザーに出すときは、金額表だけでなく次を添える。

1. **区分ごとの金額と人日**
2. **前版からの差分と、その理由**（改定の場合）
3. **★（未確定）項目が総額をどう動かすか**
4. **割引後の人日換算の妥当性**（原価割れしていないこと・§7）
5. **過去見積との比較と、説明の組み立て**（何と何を比べたかを明示・§3）
6. **仮置きした前提**（何を仮定したか）

## やってはいけないこと

| NG | なぜ |
|---|---|
| ❌ 単価・割引率・最終金額を AI が決める／クライアントへ直接送る | 値付けと提示は経営判断（§0） |
| ❌ 検算せずに数字を出す | 集計ミスがそのままクライアントに出る（§8） |
| ❌ 比較する範囲を揃えずに「据え置き／上がった」と結論する | **AI が自信をもって誤った結論を出す**典型。訂正は信用を損なう（§3） |
| ❌ 過去見積の単価・割引率をそのまま流用する | 同名でも中身が違う・個数 0 の単価は未検証・量の前提が違えば原価割れ（§2・§3・§7） |
| ❌ 範囲外の項目を行ごと削除する | 漏れなのか意図的な除外なのか読み手に伝わらない（§6） |
| ❌ 内容欄を空にする | 交渉・差分説明・受注後の認識合わせが全部できなくなる（§6） |
| ❌ エラー文字列（`#DIV/0!` 等）を含む表を出す | 提出書類の信頼性を損なう（§4） |
| ❌ Excel（.xlsx）を見積書の正本にする | AI が読み書きできず、改定のたびに人手が要る（§4） |
| ❌ 日本語が抽出できない PDF から断片を拾い、内容を推測して報告する | 誤った前提のまま作業が進む、最も危険な失敗のひとつ（§1） |
| ❌ 根拠を説明できない比率・係数を使う | 聞かれて答えられない金額は交渉で崩れる |
| ❌ 別名保存したまま「完了」と報告する | 正本が 1 本になっていない。ロック解除後に正本へ反映するまでが作業（§4） |
| ❌ CSV を文字列連結で書き出す／書きっぱなしにする | 内容欄・備考のカンマで列がずれ、金額が横にずれたまま提出される（§8） |
| ❌ 標準の人日単価で割って原価割れを判定する | 1%の割引でも赤字判定になり、判定が意味を失う。**採算下限の人日単価**で見る（§7） |
| ❌ 範囲外行の金額セルに `0` を入れる | 「0 円で受ける」と読まれる。個数 0・金額セルは空欄が正規形（§6） |

## 自己チェック（ドラフトを出す前に）

- [ ] 支給資料を **実際に読めた**か？（読めない PDF から推測していないか・§1）
- [ ] 繰り返し作業と非繰り返し作業で、測り方を変えたか？（§2）
- [ ] 過去見積の項目を、**内容欄まで突き合わせて**流用したか？（同名別物になっていないか・§2）
- [ ] 共通費用を制作費の外に出したか？（§6）
- [ ] 内容欄をすべて埋めたか？ 範囲外は **個数 0・金額セル空欄・備考に理由**の正規形で残したか？（§6）
- [ ] **実効人日単価**（割引後総額 ÷ 必要工数）が、`project-config.md` の**採算下限の人日単価**を下回っていないか？（§7）
- [ ] スクリプトで検算し、集計と一致したか？（§8）
- [ ] CSV を**読み直して**、全行 12 列・数値が数値として読める・BOM 付きを確認したか？（§8）
