# コメントは配信出力の表に出さない

🚨 **HTML コメント（`<!-- -->`）は配信される HTML に残る。** 画面には描画されないが、ブラウザの
「ソースを表示」や開発者ツールからクライアント・元請に読める。構造をなぞるだけの見出しコメント
（`<!-- ヘッダー -->` / `<!-- ここからメインビジュアル -->` / `<!-- /section -->`）を機械的に並べると、
**AI 生成を疑わせやすく、制作過程が必要以上に透けて見える**＝制作会社としての印象を損ねる。

**コメントを書くこと自体は禁止ではない。** 意図・注意点・経緯（なぜこう実装したか）はむしろ残す。
**配信出力に残らない書き方**を選ぶ。

## 1. 逃がし先（どこに書けば出力に残らないか）

| 書き方 | 一般的な設定で配信出力に残るか | 使いどころ |
|--------|--------------------------------|-----------|
| `<!-- ... -->`（HTML） | **残る** | 配信 HTML に残す必要のない説明はここに書かない |
| `//` / `/* ... */`（PHP・`<?php ?>` の中） | 残らない | 実装メモ・注意書きはこちら |
| `// ...`（SCSS） | 残らない | SCSS のメモはこちら |
| `/* ... */`（SCSS / CSS） | 通常は残る（圧縮設定では除去され、`/*! ... */` は保持されやすい） | 出力に残してよい注記だけ |
| `// ...`（バンドル・圧縮する JS） | 落ちる | ただし**そのまま配信する生 `.js` は残る**（下記 3 の推奨対象） |

- 出力されないコメントの置き場が無い場面（PHP を使わない静的 HTML 案件など）は、
  **開発者向け文書に書く**（残課題は `documents/pending-issues.md`、確定事実は `documents/company-facts.md`）

## 2. 消してよいコメント／消してはいけないコメント

🚨 **機械が解釈するコメントを消さない。** 見た目は同じ `<!-- -->` でも、消すと壊れるものがある。

- CMS・テンプレートエンジン・フレームワークが構文として使うもの
  （例: WordPress ブロックの `<!-- wp:paragraph -->`、Knockout の `<!-- ko ... -->`、条件コメント）
- ビルド・外部連携・計測タグが目印にするもの
- ライセンス表記（`/*! ... */` 等）

**消してよい**＝次の**すべて**に当てはまる説明用コメント：

1. 直前・直後のタグ名やクラス名を言い換えているだけ
2. 実装理由・制約・例外条件を説明していない
3. CMS・テンプレート・フレームワークが解釈しない
4. 消しても保守時の判断材料が失われない

**残す例**：なぜ通常と違う実装にしたか／外部仕様・ブラウザ制約・変更禁止の理由／機械処理用のマーカー／
一時対応の期限と追跡先（未解決事項は `documents/pending-issues.md` にも記録する）

## 3. 作業用コメントの後始末

- 骨組み用の `TODO`・ダミーの印（`<!-- TODO: 仮値・要確認 -->` 等）は**作業用**。仕上げ前に配信出力から外す
- 🚨 **未解決の `TODO` を黙って消さない。** 消すと課題そのものが消える。
  `documents/pending-issues.md` に移してから出力から外す
- **HTML が必須の対象。** 配信する `.css` / `.js` もクライアントは開けるので、**同じ考え方を当てる推奨対象**
  （ファイル内にメモを残すのは構わないが、分量と書きぶりには配慮する）

- [ ] 実装メモを、出力に残らない書き方（PHP／SCSS のコメント・開発者向け文書）に置いたか？
- [ ] 必要性を確認せずに既存コメント（CMS・フレームワークが解釈するもの）を消していないか？
- [ ] 未解決の `TODO` を `documents/pending-issues.md` に移さずに消していないか？
