> 🚨 **`project-config.md`「エージェント構成」で 2セッション構成を「使う」場合、このコマンドは統括セッション（`/director`）で実行する。** 開発セッションは `git add` / `commit` / `push` を行わない（`rules/modes/developer.md` §5 ＝ 検品前のコードを履歴に入れない・2つのウィンドウが同時に `git add` すると index が競合する）。開発セッションで呼ばれたら、実行せず**統括セッションで回すよう案内する**（コミット材料は開発の報告に書いてある）。「使わない」＝1セッション運用なら、この制限は適用されない。

以下の手順を**一つずつ順番に**実行してください。
各ステップで何をしたかを報告すること。
**問題がある場合のみユーザーに確認を取って停止すること。**

---

## ステップ1: ステージングと差分確認

変更したファイルを `git add <path>` でステージングする。
- `git add .` / `git add -A` は使わない(バックアップやビルド生成物を巻き込むため)。必要なファイルだけ個別パスで指定する
- **`.scss` を編集したら生成された `.css` もセットでステージする**(既定。配信・復元される実体は `.css`)。差分が暴れる場合は `.css` を外すのではなく生成系を一本化して解決する(`scss-autocompile.md` §4)。暫定で外す運用のプロジェクトは `project-config.md` にその旨が記入されているので従う(`staging.md` 参照)

`git diff --staged` を実行し、ステージング差分を確認する。

以下に該当する問題があれば指摘して**停止**:

- バグ・仕様違反
- セキュリティリスク(XSS、入力サニタイズ漏れ、ハードコードされた認証情報等)
- 不要な変更(デバッグ用 `console.log` `var_dump`、コメントアウトされた古いコード)
- **コンパイル済み `.css` の直接編集**＝対応する `.scss` の変更を伴わない `.css` 単独の差分(`.scss` 側を直すべき。**`.scss` とセットで入っている `.css` はコンパイル結果なので正常**＝これを問題として止めない)
- **`.scss` を変更したのに `.css` が差分に無い**(コンパイル未実施か、ステージ漏れ)（例外＝**開発が 2 枚以上で、他のカードの未コミット `.scss` が作業ツリーにあるため統括が意図的に `.css` を保留する場合**は問題として止めない。条件の正は `rules/modes/director.md` §7）
- **画像・バイナリの誤コミット**(過大サイズ、`*.BAK` 等)

問題がなければステップ1.5へ。

## ステップ1.5: Design.md 整合性チェック

差分に CSS / SCSS / HTML / PHP の変更が含まれる場合のみ実施。それ以外はスキップしてステップ2へ。

`Design.md` が存在しないプロジェクトでは本ステップをスキップし、`start.md` §1 での作成を別途提案する。

`Design.md` を読み込み、差分が以下のルールから逸脱していないか確認する:

- **色**: 新規追加された色値が Design.md の Color Tokens にあるか、または近い既存値に寄せられないか
- **タイポ**: フォントサイズ・行間が Design.md のタイポスケール（換算ルール含む）に沿っているか
- **レイアウト**: Design.md のグリッド単位・コンテナ幅・ブレークポイントを崩していないか
- **コンポーネント**: ボタン・リスト等の既存ユーティリティを使っているか
- **Don't違反**: Design.md の §9 Do/Don't（グラデーション・`!important` 新規追加・規約外の CSS変数導入等）に反していないか

逸脱が見つかれば、対応を**併記してステップ2に進む**(自動で修正しない):

```
### Design.md との不一致
- [ファイル:行] [問題内容]
  - 推奨対応: [どう直すか / Design.md を更新するか]
```

逸脱がなければ「Design.md整合: OK」と報告してステップ1.6へ。

## ステップ1.6: Codex クロスレビュー

ユーザー全体スコープのスラッシュコマンド `/codex-review` の手順に従い、
ステージング済みの差分を Codex(OpenAI GPT-5系)に投げてクロスレビューを実施する。
`/codex-review` コマンドが未導入の環境では `mcp__codex__codex`（sandbox: read-only / approval-policy: never）を直接呼ぶ。それも不可なら、本ステップの観点リストで Claude 単独レビューに切り替えた旨を報告して進める。

**使用モデル**：`model` パラメータは原則指定しない＝実行環境の `~/.codex/config.toml`（CODEX_HOME）の `model` 既定に従う(2026-07-14 時点の推奨既定＝`gpt-5.6-sol`。新版が出たら config.toml の1行を更新すれば全経路に効く)。明示指定する場合もサフィックス無し系列を使う(`-codex` 付きモデルは「未サポート」エラーになることがある)。**実際に使われたモデル名をレビュー報告に明記**する(裏取りは `~/.codex/sessions/<日付>/rollout-*.jsonl` の `"model":` 記録)。

Web制作の差分なので、特に以下の観点を重点的に見てもらう:

- XSS・入力サニタイズ漏れ・ハードコードされた認証情報
- 外部リンクの `rel="noopener"`・フォームの送信先/バリデーション
- アクセシビリティ(alt 欠落・ラベル紐付け・コントラスト)、SEO(title/meta/見出し階層)の退行
- レスポンシブ崩れ・コンパイル済み `.css` の直接編集

レビュー結果は次のステップでコミットメッセージ提案と一緒にユーザーに報告する。

**Codex の指摘の扱い:**

- 🔴 Critical(バグ・セキュリティ)が出た場合は、コミットメッセージ提案より先に
  問題点を強調してユーザーに報告し、対応するか・無視するかを確認する
- 🟡 Warning や 🟢 Suggestion は参考情報として併記し、ユーザーが判断する
- ✅ Approved の場合はその旨を簡潔に報告する

Codex MCP が利用不可の場合(接続エラー等)はその旨を伝えて、Claude のレビューのみで進める。

**Codex が「対象を読めない／プロンプトが届かない」ときの回避手順**（症状ごとに切り分ける。確定した回避策は**環境メモ**＝`.claude/rules/private.md` があればそこ、無ければ `project-config.md` に記録して次回以降迷わないようにする）:

| 症状 | 原因 | 対処 |
|---|---|---|
| モデルが「not supported」で弾かれる | 実行環境のアカウント種別で、`config.toml` の既定モデル系列が使えない | **サフィックス無し系列を `model` に明示指定**する。「既定に従う」を絶対視しない |
| `fatal: not a git repository`／リポジトリのファイルを読めない | `workingDirectory` がそのシェルで解決できないパス(例: WSL 上のリポジトリを Windows 側から扱う構成の UNC パス) | **Codex 自身に `git diff` を実行させない**。`git diff --staged` の出力を **BOM 付き UTF-8** でスクラッチパッドへ書き出し、そのディレクトリを `workingDirectory` に指定して「このファイルを読め」と伝える<br>`{ printf '\xEF\xBB\xBF'; git --no-pager diff --staged; } > "$SCRATCHPAD/staged.diff"` |
| 貼り付けた本文が届かない | 長いプロンプトが途中で欠落する | **プロンプトは「このディレクトリの N ファイルを読んで指示に従え」の一行に絞る**。レビュー観点・出力フォーマットはファイル側に置く |

**差分に現れない前提**(公開URL・本番反映の有無・既知の未対応事項等)は、プロンプトに「差分に現れないコンテキスト」節として明記する。書かないと、既に担保されている点を指摘され直す。

## ステップ2: 報告とコミットメッセージ提案

以下をまとめて報告し**停止**:

- ステージしたファイル一覧
- 差分確認結果
- Design.md整合性チェック結果(ステップ1.5 の出力)
- Codex クロスレビュー結果(ステップ1.6 の出力)
- コミットメッセージ提案

コミットメッセージは日本語で **見出し1行 + 必要に応じて箇条書きの本文** で提案すること。
過去のコミット履歴(`git log --oneline -10`)のフォーマットに合わせること。

ユーザーの承認を得てから次へ進む。

---

## ステップ3: コミット実行

承認されたコミットメッセージでコミットを実行し、`git status` で結果を報告する。

- コミットメッセージは HEREDOC で渡す(改行を保持するため)
- `--no-verify` 等のフックスキップは使わない

## ステップ4: リファクタリング検討

`rules/modes/refactor.md` を読み込んでガイドラインを確認する。

`git diff HEAD~1` で直前のコミット差分を確認し、ガイドラインに従って **リファクタリング候補を列挙** する:

- 重複・マジックナンバー・未使用クラス等の検出
- その場で書き換えず、候補を提案する

### ステップ4.1: Codex クロスレビュー(条件付き)

ステップ1.6 の Codex レビュー結果を確認する:

- 🔴 Critical または 🟡 Warning が出ていた場合 → 続行
- 🟢 Suggestion のみ・または ✅ Approved の場合 → スキップして候補列挙へ

**Suggestion 単独では起動しない**(軽微な改善提案だけで Codex を再度呼ぶのはコストに見合わないため)。

続行する場合、`mcp__codex__codex` を以下のパラメータで呼び出す:

- `prompt`: `git diff HEAD~1` の内容と `rules/modes/refactor.md` の原則(重複・マジックナンバー・未使用クラス・命名・可読性)を含める。「リファクタリング不要なら NO_ACTION、提案があれば具体的な箇所と内容を返す」と指示する
- `sandbox`: `read-only`
- `approval-policy`: `never`
- `model`: 指定しない(実行環境の `~/.codex/config.toml` の既定に従う。ステップ1.6「使用モデル」参照)

Codex の提案を Claude 自身の評価と統合し、下記のリファクタリング候補リストに反映する。

### 候補なしの場合
「リファクタリング不要」と報告して完了。

### 候補ありの場合
ガイドラインの「Step 2. 提案を列挙する」フォーマットで提案して**停止**。
ユーザーが承認した項目のみ、ステップ1に戻って小さなコミットとして実行する。

> 🚨 **2セッション構成の場合**：統括は承認されたリファクタリングを**自分で実装しない**。**委任カード `H-NNN` を起票してこのパイプラインを終える**。開発の実装 → 報告 → 統括の検品を経てから、**改めて `/commit-pipeline` を最初から回す**（`rules/modes/director.md` §7）。

## SCSS変更時の最終確認

ステップ1〜4 を通して `.scss` を編集した場合、最後に以下を明示する:

- コンパイル運用は `.claude/rules/scss-autocompile.md`「自動コンパイル環境が有効なときの運用」に従う（自動環境=フックが生成済み・依頼不要／無ければ開発者にコンパイルを依頼。AIは手動でビルドを叩かない）。いずれの場合も該当ページの目視確認を依頼する: [URL or ファイルパス]

なお **`.css` は `.scss` とセットでコミットに含める**のが既定（`project-config.md` の方針に従う）。🚨 **開発が 2 枚以上のときは、作業ツリーに他の未コミット `.scss` 変更が無いことを確認してから `.css` をステージする**（あれば他の開発の未検品の編集が焼き込まれている＝`.scss` だけ先にコミットする。`rules/modes/director.md` §7）。二系統コンパイラでプレフィックスが暴れる場合は、`.css` を外すのではなく生成元を一本化して解決する（`scss-autocompile.md` の「ベンダープレフィックス方針」参照）。
