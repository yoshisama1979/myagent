# CLAUDE.md

このプロジェクトは **通常のホームページ**（コーポレートサイト・ランディングページ・小規模Webサイト等）を想定したサイト制作プロジェクト。

## プロジェクト概要

- 想定対象: HTML / CSS（Sass） / JavaScript で構築する一般的なホームページ
- 制作物の例: コーポレートサイト、サービス紹介サイト、ランディングページ、ブランドサイト等
- 前提とするツールチェーン: 静的HTML or PHPテンプレート + Sass。Webアプリケーションフレームワーク（React/Vue/Next.js 等）は対象外
- 対象フェーズ: 新規制作だけでなく、**公開後の運用・SEO改善**（使いながら育てる継続的な改善サイクル）も対象に含む
- 事業ファクト集: `documents/company-facts.md`（サイトに載せる**確定事実**の SSOT。`Design.md`＝デザインのSSOT と対になる**コンテンツの情報SSOT**。ヒアリングで確定した事実を公開可否・出典つきで集約し、ページはここから展開する。`rules/modes/page-build.md`/`rules/modes/page-update.md` §5・§6 参照）
- 制作チェックリスト: `documents/build-checklist.md`（**制作中の進捗の SSOT**。完成・納品までに片付ける工程を `B-NNN` で持ち、潰しながら完成させる。配布時点は**ひな形＝標準工程の項目カタログ**なので、案件に合わせて展開・追加・対象外化して台帳にする。納品単位が複数あるプロジェクトはハブ＋`documents/build-checklist/<案件ID>.md` に分割。`rules/modes/build-progress.md` 参照）
- 委任台帳: `documents/handoff.md`（**統括セッションと開発セッションの受け渡しの SSOT**。委任カード `H-NNN` と開発の報告がここに集まる。パスは**固定**＝両セッションが別ファイルを見る事故を防ぐため `project-config.md` では変更できない。下記「エージェント構成」参照）
- 残存課題: `documents/pending-issues.md`（その場で対応しきれない未解決課題の記録先。下記「残存課題の記録ルール」参照）
- ルール改善メモ: `documents/rule-improvements.md`（ルールファイルへの気づき・改善案の記録先。下記「コラボレーションの原則 2」参照）
- プロジェクト固有の定義（サイト名・ディレクトリ構成・デプロイ先・確認/公開URL・ブランチ運用・環境・コンパイル方針など）: `project-config.md`（コピー後まず記入する）

> プロジェクト固有の情報（サイト名・ディレクトリ構成・デプロイ先・公開URL・ブランチ運用など）は `project-config.md` に記入する（CLAUDE.md 本文に直書きしない）。
> **表示を確認する URL（ローカル／ステージング／本番）も `project-config.md` の「URL・確認環境」節が正**。確認が要るたびにユーザーへ聞かず、まずそこを読む（未記入＝空欄または `（記入。例: …）` のままなら、一度確認して記入する）。

## 残存課題の記録ルール

会話・制作・運用の中で **その場で対応しきれず未解決のまま残った課題** は `documents/pending-issues.md` に記録すること。すぐ対応できるものは対応し、そうでないものを取りこぼさないための仕組み。

- ユーザーから「残存課題として記録して」と依頼された場合は必ず `pending-issues.md` に追記する
- 制作フェーズ（バグ・未実装・保留した設計判断）でも、運用・SEOフェーズ（今回は見送る改善・要計測の施策）でも、**同じファイルに記録する**
- 各課題には「**経緯**」「**未対応**（何が残っているか）」「**今後の判断ポイント**」を明記する
- 解決した課題は `pending-issues.md` から削除し、必要なら確定仕様・記録側へ転記する

## エージェント構成（統括 1 ＋ 開発 N・別ウィンドウ）

🚨 **この構成を使うかどうかは `project-config.md`「エージェント構成」節の「2セッション構成を使うか」が正。**
`使わない` なら以下は適用せず、**1セッションで全部やる**（下のルール表にそのまま従う）。`使う`（既定）／未記入なら以下に従う。

この構成（統括 1 ＋ 開発 N〔上限 3〕。切り替えのキーは互換のため「2セッション構成を使うか」のまま）では、役割を分けることで全体を見る視点と手元の実装を両立させる。

| セッション | 起動 | 役割 | ルール |
|---|---|---|---|
| **統括（ディレクター）** | `/director` | ユーザーの **方針の窓口**。全体を見て、決め、委任し、検品し、コミットし、報告する。**実装はしない** | `rules/modes/director.md` |
| **開発（デベロッパー）** | `/dev` | **実装担当**。HTML/CSS(Sass)/JS/PHP を書き、直し、確認する。**コミットはしない** | `rules/modes/developer.md` |

- **受け渡しは `documents/handoff.md` だけが正。** 2つのセッションは互いの会話が見えない＝**そこに書かれていないことは相手にとって存在しない**
- 🚨 **ファイルに書いただけでは相手は気づかない。** カードを更新したら、**ユーザーに相手セッションへの切り替えを頼む**（人間が唯一の通知経路。頼まないと双方が相手待ちで止まる）
- **状態と所有者は `documents/handoff.md`「状態と所有者」が正**（統括＝`未着手`/`差戻し`/`クローズ`、開発＝`着手中`/`質問中`/`レビュー待ち`。相手の持ち場の状態は書き換えない）
- **ユーザーはまず統括を開く。** 統括は起動時に環境点検を行い、開発セッションが開かれていなければ**開き方を提示して促す**（`rules/modes/director.md` §1）
- 統括から他のウィンドウは見えない。開発セッションが開いているかは**仕組みで追わず、ユーザーに聞く**
- **どちらに話しかけるか**：方針・優先順位・公開判断・見積もり → 統括／目の前の実装の直し → 開発／**迷ったら統括**
- 実環境ごとの起動手順は `project-config.md`「エージェント構成」節が正
- 🚨 **下のルール表の既存ルールは1セッション前提で書かれている。** 2セッション構成では、着手前の合意・SSOT（`company-facts.md`／`Design.md`／`build-checklist.md`）の更新・外部への書き込みと報告（`mailbox.md`／`hana-memo.md`／`hp-loop-dialogue.md`）は**すべて統括の持ち場**で、開発は実装と技術報告まで。各ルール冒頭の読み替え注記に従う

## ルールファイル（2層構成）

**方針**: トークン消費を抑えるため、ルールファイルは**タスクに関連するもののみ必要に応じて読み込む**。作業のフェーズに入った時点で、下表から該当するファイルを選んで読み込むこと。

置き場所は**読み込まれ方**で2層に分かれる（2026-07-24 再編）：

| 層 | 置き場所 | 読み込まれ方 |
|---|---|---|
| 条件付き | `.claude/rules/`（`paths:` フロントマター付き） | **globに合致するファイルを扱うときだけ自動適用**（読み忘れが起きない） |
| 読み込み式 | `rules/modes/` | 自動ロードされない。下表の「いつ参照するか」に該当したら **Read で読む** |

| ファイル | いつ参照するか |
|---------|--------------|
| `rules/modes/director.md` | **統括セッション（`/director`）の動作ルール。** 起動時の環境点検（開発セッションが開いているかをユーザーに聞く・`project-config.md` の未記入・`Design.md` の有無）、ユーザーとの窓口の線引き、委任の閾値、**委任カードの様式**、開発から戻った質問への大局の付け方（統括で答えられるものを消し、残りに推奨と理由を添える）、検品とコミット |
| `rules/modes/developer.md` | **開発セッション（`/dev`）の動作ルール。** 委任カードの読み方、**自分で決めない3つ**（事実を作らない・デザイントークンを増やさない・スコープを広げない）、詰まったときの止まり方、**コミットしない**理由、報告8項目（「確認できていないこと」「コミット材料」を空にしない・統括の前提と食い違ったら合わせに行かず8番に書く）、開発が2枚以上のときの開発どうしの境界（共有ファイルの所有者以外は触らない） |
| `rules/modes/start.md` | **プロジェクト開始時 / 新規ページ・UI作成依頼を受けた時。** `Design.md` の有無確認など、制作に入る前のゲート |
| `rules/modes/build-progress.md` | **制作中の進行管理（`/progress`）。`documents/build-checklist.md` がある案件では、制作タスクの着手時・区切り時に必ず読む**（読まないと台帳が更新されず、促しが止まる）。あらかじめ用意したチェックリストを潰して完成させる進め方＝ひな形の育て方・複数案件の持ち方・次の一手の選び方・促し方・完了判定（推測で `[x]` にしない）。公開前の検品は `check.md`、こちらは**制作期間中ずっと繰り返す** |
| `.claude/rules/design.md`（paths自動） | **色・フォント・余白・コンポーネント等のデザイン判断をする時。** `Design.md`=SSOT の扱い方、Design.md が持つべきセクション構成、プロジェクト非依存の普遍的な Do/Don't（固有値は各プロジェクトの `Design.md` 側） |
| `rules/modes/design-replication.md` | **デザインカンプ／モックアップ（特にAI生成画像）を渡されてUIを再現する時。** 推測を実測に変え、実ブラウザ描画で照合する周回（色の実測・同一幅スクショ・寸法は意図から設計しSSOTに記録） |
| `rules/modes/page-build.md` | 新規ページ・画面の追加依頼を受けた時。既存ページを雛形に実装する手順とコンテンツの正確性担保 |
| `rules/modes/page-update.md` | 既存ページを更新して内容を充実させる依頼を受けた時。既存を壊さず加筆・改善する手順とコンテンツの正確性担保 |

## デザインルールの単一の真実の源 (Design.md)

プロジェクトルートに `Design.md` がある場合、それが **デザインに関する Single Source of Truth**。
色・フォント・余白・コンポーネント仕様は SCSS 変数より Design.md を優先する。

- 新規 UI 実装の前に必ず `Design.md` を読む
- Design.md と既存コードが食い違う場合は Design.md に合わせて既存コードを直す(漸進的に)
- Design.md に無い概念(新しい色トークン、ブレークポイント等)を勝手に増やさない。先に Design.md を更新する提案をする
- `Design.md` が存在しない場合は `rules/modes/start.md` の「1. Design.md の準備」セクションに従って作成手順を踏む

> **汎用ルールと固有値の分離**：「Design.md をどう扱うか／どのプロジェクトでも守る普遍的なデザイン規律」は `.claude/rules/design.md`（汎用）にある。**各プロジェクト固有の値**（色 hex・フォント・幅・換算ルール等）は、そのプロジェクトの `Design.md` 側に書く。本リポジトリには YCOM の値で書いた記入例 `Design.sample.md` を同梱している（実プロジェクトではこれを `Design.md` にコピーして値を差し替える）。

## ルールファイルの出自と改善ループ（全体像）

この `CLAUDE.md`・`.claude/rules/`・`rules/modes/` 配下のルール一式は、**はなさか側の「ルール開発エージェント」が管理する共通テンプレート（`claude-rules/`）から配布されたもの**。ルールはテンプレート側で一元的に開発・改善され、各開発プロジェクト（＝あなた）へ配布されて使われる。

```
（ルール開発エージェント）共通テンプレートを開発・改善
        │  配布（初回はコピー。以後は bin/rules-update.sh で取りに来る）
        ▼
（各開発エージェント＝あなた）ルールに従って制作・運用 ─ 現場で問題・改善点に気づく
        │  「指示書」を書く（documents/rule-improvements.md に記録 → bin/rule-report.sh で通知）
        ▼
（ユーザー＝社長）指示書をルール開発エージェントへ渡す
        │  検証・社長承認のうえテンプレートを修正 → 各プロジェクトへ展開
        └──────────────（ループ）──────────────┘
```

- **ルールは配ったあとも更新される。** 最新版は `bash bin/rules-update.sh` で**このプロジェクトから取りに来る**（確認だけなら何も書き換えない）。🚨 **適用は人の確認を得てから**＝ルールが変わると作業の前提が変わる。手順は `rules/modes/rules-update.md`。
- **ルールの修正はテンプレート側で一元管理**する。このプロジェクト内でルールファイルを直しても他プロジェクトには波及しない＝テンプレ級の問題は必ず上記ループで還元する。
- 🚨 **配布されたルールファイルを削除・再編しない。** 不要・重複と感じても、**このプロジェクトの判断で消さない**。
  消えたルールは、以後の AI にとって **最初から存在しなかったのと同じ**になる（現存ファイルを検索して無ければ「規定なし」と判断するのが自然なため、**消したこと自体に誰も気づけない**）。
  不要だと思ったら **指示書で還元し、判断はテンプレ側に委ねる**。どうしても外したい場合も、**削除ではなく「このプロジェクトでは使わない」を `project-config.md` に記録**する。
- **現場で実際に使って問題を感じたら「指示書」を書く**：ルール開発エージェント（このプロジェクトの文脈を知らない汎用エージェント）が**それだけ読んで修正作業に入れる自己完結の依頼文**として書く。書式は `documents/rule-improvements.md` 冒頭「指示書」節を参照。送り方は `bash bin/rule-report.sh`（投函専用の別経路・`rules/modes/mailbox.md` §2-3）。ユーザーに直接渡してもよい。
- 指示書は**鵜呑みにされず、ルール開発エージェント側で検証・社長承認を経て反映される**。事実（現場で何が起きたか）と提案（どう変えるか）を分けて書くほど検証が速く、採用されやすい。
- このプロジェクト**固有**の調整（実パス・公開URL・ブランド色等）はテンプレに送らず `project-config.md`／`Design.md` 側で解決する。

## コラボレーションの原則

### 1. 不明点・提案は都度質問する

ユーザーからの指示や記述をそのまま鵜呑みにして実装に進まないこと。

- **不明点があれば**: 仕様の解釈に複数パターンがある、デザインの意図が読み取れない、既存ページとの整合性が不明、などの場合は実装前に必ず質問する
- **より良い案があれば**: 提示された方針より適切な選択肢が見える場合は、推奨案と理由を添えて提案する（最終判断はユーザー）
- **判断が分かれる設計事項**: ファイル構成・命名・画像形式・スコープなどは、実装前に選択肢を整理して合意を取る

推測で進めて手戻りするより、一手前で確認する方がコストが低い。

### 2. ルールファイル自体の改善も提案する

`.claude/rules/` 配下のルールファイルや `CLAUDE.md` を参照していて、以下に気付いた場合は実装作業の合間でも提案する。

- 実態と乖離している記述
- 抜け落ちている運用ルール
- 矛盾している記述（複数のルールファイル間で食い違う指示）
- 改善できる構成・粒度

提案時は「どのファイルの、どの記述を、どう変えるか、なぜ」を明示する。ユーザーの判断後に修正に進む。

**ユーザーが明確な回答をしなかった場合も、気づいた点はその都度 `documents/rule-improvements.md` に記録する**。提案が会話に埋もれて流れ、忘れられるのを防ぐため、「記録」と「反映」を分離する（記録は気づいた都度・反映はユーザー判断時にまとめて）。

- 提案したが判断が出ていない／会話が先に進んでしまった場合も、観察を1行でも残す
- 各エントリに「対象ファイル・どの記述・どう変えるか・なぜ」を明記する（フォーマットは `documents/rule-improvements.md` 冒頭参照）
- 反映が済んだエントリは削除する（または「反映済み」と印を付ける）
- **このプロジェクト固有でなく、配布元の共通テンプレート全体に還元すべき**と判断した気づきは `[テンプレ還元]` と印を付け、`bash bin/rule-report.sh` でテンプレ更新側（はなさかAI）へ届ける（`rule-improvements.md`「`[テンプレ還元]` 印のものはテンプレ更新側へ送る」／`rules/modes/mailbox.md` §2-3）。使っているテンプレの版は自動で載るので書かなくてよい。固有値はテンプレに持ち込まず `project-config.md`／`Design.md` 側に置く

### 3. 作業のまとまりごとに「頭の切り替えを助ける報告」をする

ユーザーはエージェントの作業中に別の作業をしていることが多い。ひとまとまりの作業（ページ作成・改善・運用対応など）が一区切りしたら、ユーザーがスムーズに頭を切り替えられるよう、次の4点を**要点だけ**まとめて報告する。

1. **大局（目的）** … いま何を目指して作業しているか
2. **課題** … その目的に対する現在の課題
3. **今回やったこと** … この作業で何を進めたか
4. **次にすべきこと** … 次の一手・提案（あれば）

長い経緯の再説明はせず、切り替えに必要な最小限に絞る（**冗長にしない**）。軽微なやり取りには不要＝実質的な作業の区切りで出す。
