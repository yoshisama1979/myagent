# 設定値の扱い（単一の正）

設定値（しきい値・上限・期限・フラグ等）は **正を 1 箇所だけ決める**。同じ値がサーバー・クライアント・ドキュメント・テストに複製されていると、**1 箇所を変えた瞬間に食い違い、しかも表面化しない**（複製が偶然すべて同じ値の間は誰も気づかない）。

- **既定値をコードの 2 箇所以上に書かない。** config の既定値と `.env.example` の値が両方あるなら、**必ず一致させ、片方に「もう片方と一致させること」と注記**する
- **クライアントは既定値を推測しない。** サーバーから設定を取得する作りなら、取得に失敗したときに「たぶんこの値だろう」で埋めない。**値が無い状態を正しく表現し（機能を出さない）、理由を利用者に伝える**
- **最終的な可否判定は必ずサーバー側で行う。** クライアント側の判定は UI の出し分けにすぎず、サーバーは常に自分で検証して弾く
- **コメントに数値を書いたら、その数値が実値と一致しているか確認する。** コメントは検証されないため、最も早く腐る
- **設定値を追加・変更したら、その値が他に何箇所書かれているか検索する**（`.env` / `.env.example` / config / クライアント / テスト / 仕様書）。2 箇所以上あるなら、どれが正かを決めて残りを従属させる

## 環境変数を読むときの型

`.env` から読んだ値は**必ず文字列**である。型の指定を忘れると、API が `"10000"` と文字列で返り、フロント側の型定義（TypeScript の `number` 等）と食い違う。

**単純な数値キャストで済ませない。** 多くの言語のキャストは「先頭の数値部分だけを採る」ため、`10abc` が `10` として通る。**正の整数として妥当かを検証し、不正なら既定値へ落とす**（PHP の例: `filter_var($v, FILTER_VALIDATE_INT, ['options' => ['min_range' => 1]])`）。

## テストするとき

設定の解決規則（未設定なら既定値／不正値なら既定値／設定されていればその値）をテストするときは、
**必ず「既定値とは異なる値」でも 1 ケース検証する**。既定値を期待するケースだけだと、
差し込み自体が効いていなくても全部通り、**何も検証していないテスト**が完成する
（`rules/modes/tdd.md` 3.0.1「テストが素通りしていないか疑う」）。
