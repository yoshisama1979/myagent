# API 実装規約

API は 1 プロジェクトで数十本作る。**同じ判断を毎回やり直すとブレる**ため、判断の型をここに置く。
固有値（実パス・middleware 名・config キー・モデル名・個別の性能事情）は書かない
＝ `project-config.md`／そのプロジェクトの API 規約ドキュメント側に置く。

---

## 1. 認証系統を明示する

- 新規エンドポイントは**必ずどれかの認証系統に属させる**（管理画面セッション／利用者トークン／サーバー間連携 等）。
  「どれでもない」エンドポイントを作らない
- **認証方式を推測しない。** ヘッダ名・スキーム（`Authorization: Bearer` なのか独自ヘッダなのか）は
  **既存の middleware を読んで確認**する。推測でテストを書くと、テストごと間違った前提で固まる

## 2. 管理用と公開用は最初から分ける

- 実装時点で**中身が同一でも分ける**。分離の目的は、後からレスポンス項目・権限・レート制限を
  片側だけ変えられるようにすること
- 分けずに始めると、後で分けるときに既存クライアントを壊す

## 3. 同一機能に複数経路があるなら、差分は認証だけにする

管理経路とサーバー間連携経路のように「入口が 2 つある同じ機能」では、
**バリデーション値・リクエストクラスのルール・ドメイン処理・レスポンス整形の 4 層を共有**する。

- 4 層すべてを経路ごとに書くと、**片方だけ直して片方が腐る**
- 差分は「誰が呼べるか」だけに閉じる

## 4. 内部表現をそのまま外に出さない

- **中間テーブル（pivot）の生の属性をレスポンスに載せない。** 整形済みのフィールドに詰め替える
- 詰め替えるキーには**接頭辞を付けて親テーブルのカラムと衝突させない**
  （`note` のような汎用名は高確率で衝突し、片方が消える）
- DB のカラム名・内部 ID をそのまま公開契約にすると、リファクタのたびに API が壊れる

## 5. ラベル解決はサーバー側で行う

コード値 → 表示名の対応表をフロントに持たせない（**二重管理になり必ずズレる**）。
サーバーがラベルを解決して返す。

## 6. バリデーションを DB 制約より緩くしない

- 特に**文字数・数値範囲**。緩いと**テストは通るのに本番でだけ 500** になる
- 上限値は**モデルの定数**として DB 定義と対応させて置き、**全入口（通常の登録・更新・一括インポート）から参照**する
- 一括インポート専用のバリデーションを別に書かない（必ず本体より緩くなる）

## 7. 部分更新は「リクエスト値 ＋ 既存値」で検証する

送られてこなかった項目を検証対象から外すと、**組み合わせとして不正な状態を保存できてしまう**
（例: 開始日だけ更新して、既存の終了日より後になる）。
**更新後の状態**を組み立ててから検証する。

## 8. 一括インポートは部分成功を許さない

- **全件ロールバック**。途中まで入った状態を残さない
- エラーは **行番号・列名・理由**を返す（「失敗しました」だけでは直せない）
- 存在判定を**更新の affected rows で行わない**。同一内容の再投入では affected rows が 0 になり、
  「存在しない」と誤判定して二重登録 → 一意制約違反で 500 になる。**明示的に検索して存在を判定する**

## 9. テスト DB と本番 DB が違うなら、差が出る点を実機確認する

テストが SQLite・本番が MySQL/PostgreSQL のような構成では、**テストが通っても本番でだけ落ちる**。
SQLite が差を吸収してしまう代表例：

| 観点 | 何が起きるか |
|---|---|
| **カラム長** | 上限超過が SQLite では通り、本番で切り詰め or エラー |
| **数値範囲** | `smallint` 等の範囲外が SQLite では通る |
| **更新の affected rows** | 同値更新の扱いが異なり、存在判定が壊れる（上記 8） |
| **SQL 関数の方言** | 日付・文字列関数がエンジンごとに違う |

**これらに触れる変更をしたら、本番と同じエンジンで 1 度確認する**（確認できないなら、その旨を
ユーザー確認事項として明示する）。
