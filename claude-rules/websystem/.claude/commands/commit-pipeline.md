> 🚨 **`project-config.md`「エージェント構成」で 2セッション構成を `使う` 場合、このコマンドは開発セッション（`/dev`）で実行する。** 統括セッションは `git add` / `commit` / `push` を行わない（`rules/modes/director.md` §7 ＝ Autopilot の安全装置がコミットを開発側に前提しており、2つのウィンドウが同時に `git add` すると index が競合する）。統括セッションで呼ばれたら、実行せず**開発セッションで回すよう案内する**。`使わない`（既定）＝1セッション運用なら、この制限は適用されない。

以下の手順を**一つずつ順番に**実行してください。
各ステップで何をしたかを報告すること。
**問題がある場合のみユーザーに確認を取って停止すること。**

プロジェクトルートは `project-config.md` を参照すること。

---

## ステップ1: ステージングと差分確認

変更したファイルをステージングする。
プロジェクトルートで `git diff --staged` を実行し、ステージングされた差分を確認する。

問題がある場合（バグ・仕様違反・セキュリティリスク・不要な変更）は問題点を指摘して**停止**。

問題がない場合はステップ1.5（Codex クロスレビュー）に進む。

---

## ステップ1.5: Codex クロスレビュー

ユーザー全体スコープのスラッシュコマンド `/codex-review` の手順に従い、
ステージング済みの差分を Codex（OpenAI GPT-5系）に投げてクロスレビューを実施する。

レビュー結果は次のステップでコミットメッセージ提案と一緒にユーザーに報告する。

**Codex の指摘の扱い:**
- 🔴 Critical（バグ・セキュリティ）が出た場合は、コミットメッセージ提案より先に
  問題点を強調してユーザーに報告し、対応するか・無視するかを確認する
- 🟡 Warning や 🟢 Suggestion は参考情報として併記し、ユーザーが判断する
- ✅ Approved の場合はその旨を簡潔に報告する

`/codex-review` コマンドが未導入の環境では `mcp__codex__codex`（sandbox: read-only / approval-policy: never）を直接呼ぶ。それも不可なら Claude 単独レビューで進める旨を報告する。

**使用モデル**：`rules/modes/dialogue-mode.md` Step 5 の「使用モデル」に従う（本ファイルには**書き写さない**＝二重定義は片方だけ古くなるため）。要点は「`model` は原則指定せず実行環境の `~/.codex/config.toml` の既定に従う／明示するならサフィックス無し系列／**実際に使われたモデル名をレビュー報告に明記**する」。

Codex MCP が利用不可の場合（接続エラー等）はその旨を伝えて、Claude のレビューのみで進める。

**Codex が対象を読めない／プロンプトが届かない場合**（モデル未サポート・`fatal: not a git repository`・貼った本文が届かない）は、
`rules/modes/dialogue-mode.md` Step 5「Codex が『対象を読めない／プロンプトが届かない』ときの回避手順」に従う。
要点：**Codex 自身に `git diff` を実行させない**。`git diff --staged` の出力を BOM 付き UTF-8 でスクラッチパッドへ書き出し、
そのディレクトリを `workingDirectory` に指定して「このファイルを読め」と伝える。
**差分に現れない前提**（サーバー側で最終判定している・既知のベースライン失敗が何件ある等）は
プロンプトに「差分に現れないコンテキスト」節として明記する。

---

## ステップ2: 報告とコミットメッセージ提案

以下をまとめて報告し**停止**:

- ファイル一覧
- Claude による差分確認結果
- Codex クロスレビュー結果（ステップ1.5 の出力）
- **ユーザー確認事項**（今回の差分で確認・判断してほしいこと。`rules/modes/create-test.md`「記録（test.csv）と提示（プロンプト）は別物」の5項目に従う。ユーザーはプロンプト画面しか見ていないため、test.csv に書いただけでは確認されない）
- コミットメッセージ提案

コミットメッセージは日本語で見出しと項目で提案すること。
コミットメッセージは `rules/modes/commit.md` の `[領域]` 規約（プレフィックス必須・領域分割・50/72）に準拠すること。
過去のコミット履歴（`git log --oneline -5`）のフォーマットに合わせること。

ユーザーの承認を得てから次へ進む。

---

## ステップ3: コミット実行

承認されたコミットメッセージでコミットを実行し、結果を報告する。

---

## ステップ4: リファクタリング

> ※ agent.md の9段階フロー（都度承認）ではコミット**前**の staged 差分をリファクタ対象とする。本パイプラインはコミット**後**に `HEAD~1` 差分で行う。どちらもフローに応じた正で、リファクタ変更は必ず別コミットにする点は共通（rules/modes/commit.md）。

まず `rules/modes/refactoring.md` を読み込んでガイドラインを確認する。

プロジェクトルートで `git diff HEAD~1` を実行し、直前のコミットの差分を確認する。
ガイドラインに従って Claude 自身の評価でリファクタリング判断を行う。

### ステップ4.1: Codex クロスレビュー（条件付き）

ステップ1.5 の Codex レビュー結果を確認する:

- 🔴 Critical または 🟡 Warning のいずれかが**非空**だった場合 → 続行
- 上記が空の場合（🟢 Suggestion のみ・または完全に ✅ Approved）→ スキップしてステップ4.2 へ

**🟢 Suggestion 単独では起動しない**（軽微な改善提案だけで Codex を再度呼ぶのはコストに見合わないため）。
ステップ1.5 で「ユーザーに参考情報として併記する」止まりだった指摘は、ステップ4.1 でも自動アクションは取らない。

続行する場合、`mcp__codex__codex` を以下のパラメータで呼び出す:

- `prompt`: `git diff HEAD~1` の内容と `rules/modes/refactoring.md` の原則（重複コード・
  可読性・責務分離・命名・マジックナンバー・型安全性・パフォーマンス）を含める。
  「リファクタリング不要なら NO_ACTION、提案があれば具体的な箇所と内容を JSON で返す」と指示する
- `sandbox`: `read-only`
- `approval-policy`: `never`
- `model`: 指定しない（実行環境の `~/.codex/config.toml` の既定に従う。ステップ1.5「使用モデル」参照）

Codex の提案を Claude 自身の評価と統合し、以下のいずれかで報告:

- 両者ともリファクタリング不要 → そのまま完了報告
- どちらかが提案 → 統合してユーザーに報告して**停止**
- 両者の判断が競合 → Claude の判断と Codex の指摘を並列に提示してユーザー判断を仰ぐ

### ステップ4.2: 実行と確認

リファクタリングを行った場合は、ガイドラインで指示されている通り関連するテストを実行して動作確認を行うこと。

リファクタリングが不要な場合はその旨を報告して完了。
リファクタリングを行った場合は、変更内容を報告して**停止**。ユーザーの確認後、ステップ1に戻って再度パイプラインを実行すること。
