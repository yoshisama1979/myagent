- **共有ファイルの所有者**（🚨 **開発を 2 枚以上にするとき必ず埋める**。所有者以外の開発は触らない＝必要な変更は所有者に依頼する〔`rules/modes/developer.md` §3〕。埋めずに走ると、事故が起きかけてから統括の口頭裁定で決めることになる）

  | 共有ファイル | 例 | 所有者 |
  |---|---|---|
  | DB スキーマ・マイグレーション | `database/migrations/` | （記入。既定＝**単独カードで先に確定**〔`rules/modes/director.md` §5.3〕。並行中は誰も触らない） |
  | API の契約 | ルート定義・リクエスト／レスポンスの型・認証 middleware | （記入。同上） |
  | 共通コンポーネント | `components/ui/*`・共通レイアウト | （記入。例: `dev-A`） |
  | 設定値の既定 | config／`.env.example` | （記入。`.claude/rules/config-values.md`＝正は 1 箇所） |
  | **生成物** | lockfile・ビルド成果物・自動生成の型定義 | 所有者では解けない。既定＝**生成物はコミットに入れる前に、生成元がすべてコミット済みであることを確認する**（他の開発の未コミット分が焼き込まれていないか） |

> 🚨 **`使う` にした場合の git の持ち場**（website テンプレートとは**逆**なので注意）
> - **コミットを打つのは開発セッション**（`develop` 等の作業ブランチ上）。Autopilot の安全装置（`git revert` 前提の細かいコミット・コミット数上限・`autopilot_start_head` を起点にしたレビュー範囲）がそれを前提にしているため
> - **統括は `git add` / `commit` / `push` をしない。** `git log` / `git diff` で**読む**（検品）ところまで
> - `push` / PR 作成 / マージ / 本番コマンドは、どちらのセッションも実行しない（ユーザーの手動作業）
> - **この分担の理由の正は `rules/modes/director.md` §7**（ここには結論だけを書く）

> 🚨 **`使う` にした場合、`/inbox`（Inbox モード）は起動しない。** あれは「自走中にユーザーが話しかける先が無い」ことへの対処であり、統括のウィンドウが常時開いているなら不要。ユーザーの「次やってほしいこと」は統括が受ける。

- **既定の確認先**: （記入。例: 実装中＝ローカル／受け入れ確認＝ステージング／反映後の実測＝本番）。**今回どれを見るか迷ったらこの欄に従う**（複数記入済みでも確認先が決まる）
- **確認用アカウントの扱い**: （記入。例: ロール別のテストアカウントあり／保管場所は 1Password。🚨 **ID・パスワードの実値はここに書かない**）

- **「ブランチ運用・デプロイ」節との違い**: あちらは**反映の経路**（どのブランチをどう上げるか）、この節は**ブラウザで見るアクセス先**。同じ情報を両方に書かない

## 固有の追加（配布ファイルに書き足す代わりの置き場。`CLAUDE.md`「配布ファイルに書き足さない」が参照）

> `CLAUDE.md`・`rules/`・`.claude/rules/`・`.claude/commands/` は配布物で、ルールを更新すると**上書きされる**（書き足した行は黙って消える）。このプロジェクトだけのコマンド・ルール・規約は、**実体を新しいファイルとして置き**、**一覧への登録はこの節に書く**。AI は `CLAUDE.md` の表と合わせてこの節も読む。
