# メールボックス連携ルール（拠点横断エージェント間メッセージ）

別マシンにいる他のエージェント（特に **はなさかAI HP分析ループ**。ループはマルチサイト化で **サイト別の `hp-loop-<site>`** に分かれており、**このプロジェクトの担当インスタンス（`<site>`・宛名）は [project-config.md](../../project-config.md)「HP分析ループ連携」を正とする**）と、**ネットワーク越しに非同期でメッセージをやり取り**するための共有受信箱「メールボックス」の使い方。
あなた（実装＝Managing側エージェント）が hp-loop から提案を受け取り・報告を返す経路の一つがこれ。

`rules/modes/hp-loop-dialogue.md`（提案の検証 → 対応 → 報告の **中身** の作り方）と対になる。
**本ファイル＝「報告を運ぶ土管（送受信の操作）」／ `rules/modes/hp-loop-dialogue.md`＝「報告に何を書くか」**。
報告本文の要件（観測可能な「旧→新」の値・GET確認済みか・commitハッシュに頼らない・対応 `R-NNN` 併記）は引き続き [rules/modes/hp-loop-dialogue.md](./hp-loop-dialogue.md) §5-2 に従う。

> **すべての websystem プロジェクトが対象ではない**：対の分析ループ（`hp-loop-<site>`）が存在し、社長からこのマシン用のトークンが配布されたプロジェクトだけがメールボックスを使う。無い／未配線のプロジェクトはこのファイルの出番なし（テンプレ改善の還元は `rule-improvements.md` 記録＋社長の持ち帰りでよい）。

## いつ参照するか

- hp-loop から提案・質問が **メールボックス経由で届く** 運用になっているとき
- 実装した結果の **報告・質問・受領確認を hp-loop へ返す** とき
- **ルールファイル自体の改善提案をテンプレ更新側（`rule-kaizen`）へ送る** とき（→ 2-3.）
- 他エージェント（社長＝`president` 等）と非同期でやり取りするとき

## なぜメールボックスか（前提）

エージェントは **同じマシンにいない**（VPS・事務所PC・自宅PC）。ファイルを直接共有できないので、
常時起動の **VPS をハブ** にした HTTP API（**Tailscale 内からのみ到達**）で読み書きする。
あなたの拠点は **自分のマシンが起動し・あなたが動いている間だけ** 受信箱を処理できる **間欠応答** が前提（重い常駐処理は VPS 側の担当）。

## 0. セットアップ（最初に1回・ユーザーが用意）

メールボックスを使うには、このマシンに次が要る。無ければ **ユーザー（社長）に依頼する**（**勝手にトークンを作らない・実値を表示しない**）：

| 要るもの | 中身 |
|---|---|
| クライアント `bin/mailbox.sh` | 送受信スクリプト（はなさか VPS のリポジトリから配布される） |
| `.env`（gitignore 必須） | `MAILBOX_URL=http://<VPSのTailscale IP>/tools/mailbox/` と `MAILBOX_TOKEN=<このマシン用トークン>` の2行 |
| Tailscale | VPS に到達するための前提（tailnet 内からのみ届く） |

- **あなたのエージェントID（`from`）は、トークンからサーバが決める**。本文でどう名乗っても詐称はできない（例：このマシンが `foo-dev` のトークンなら送信元は必ず `foo-dev`）。
- トークンは **画面・ログ・コミットに出さない**。`.env` は `bin/mailbox.sh` が必要キーだけ読む（全体を `source` しない）。

---

## ★ 送受信の仕組み（操作で迷ったらまずここ）

混乱しやすい核心を先に1つだけ：**「あなたが誰か」は `.env` のトークンが決める**。`MAILBOX_TOKEN` が「このマシン＝○○」を表し、サーバはトークンだけであなたを識別する。**1マシン＝1エージェント＝1トークン**。だから操作のたびに自分の名前を入力する必要はない。

| 操作 | コマンド | 仕組み（誤解しやすい点） |
|---|---|---|
| **受信** | `bash bin/mailbox.sh inbox` | **自分の名前は引数に付けない。** トークンが自分を識別し、**自分宛（`to` があなた）の未読だけ**が返る＝あなたは「自分専用の受信箱」だけを見る。引数で他人の箱を指定できるのは admin だけ |
| **処理済み化** | `bash bin/mailbox.sh done <id>` | 読んで着手したら `cur/` へ移す。本文は編集しない |
| **送信** | `bash bin/mailbox.sh send --to <宛先> ...` | **`--from` は存在しない・書けない。** 送信元 `from` はトークンから**自動付与**され詐称できない（あなたのマシンから送れば必ずあなたが `from` になる）。あなたが指定するのは **`--to`（宛先）だけ**。宛先＝対になる分析ループ `hp-loop-<site>`（→ 2.） |

> まとめると：**受信＝自分の箱を見るだけ（名乗り不要）／送信＝宛先だけ書けば `from` は自動であなたになる**。「受信は自分のメールボックスを見る・送信すると from に自分が付く」という理解で正しい。

## 1. サイクル先頭：受信箱を読む

作業を始める前に、自分宛の未読を取りに行く：

```bash
bash bin/mailbox.sh inbox
```

- hp-loop からの **改善提案（`R-NNN`）・質問（`Q-NNN`）・認識合わせ** などが届く。
- 読んで対応に着手したら **処理済みにする**：`bash bin/mailbox.sh done <id>`（`cur/` へ移るだけ。**本文は編集しない＝履歴を消さない**）。
- 提案の検証・実装・報告の進め方は [rules/modes/hp-loop-dialogue.md](./hp-loop-dialogue.md) に従う（鵜呑みにせず実コードと突き合わせ → 影響範囲を合意 → 実装 → 報告）。

## 2. 報告・質問を送る

実装結果の報告や、分析ループへの質問・受領確認は：（**宛先はサイト別の `hp-loop-<site>`**。`<site>`・宛名は [project-config.md](../../project-config.md)「HP分析ループ連携」を正とする。はなさか側のマルチサイト化で旧無印 `hp-loop` から移行済み・**サイト無印の `hp-loop` 宛では現行ループが拾えない**）

```bash
bash bin/mailbox.sh send --to hp-loop-<site> --type report --thread <会話ID> \
  --subject "R-014a 実装報告" "本文（rules/modes/hp-loop-dialogue.md §5-2 の形式で）"
```

> **宛先 `<site>` の確定（ここで詰まりやすい）**：`hp-loop-<site>` の `<site>`（正式な宛名）は必ず [project-config.md](../../project-config.md) の「HP分析ループ連携」を見て使う。**もし project-config.md が未記入（`（記入。例：…）` のまま）なら、推測で送らず・無印 `hp-loop` にも送らず、社長に「このプロジェクトの分析ループ宛名」を確認する**。無印 `hp-loop` は複数サイト化で廃止済み＝現行ループが拾えず、送っても届かない。

| `--type` | 使うとき |
|---|---|
| `report`  | 実装結果・進捗・完了の報告 |
| `request` | 依頼・質問（データ補完のお願い等） |
| `ack`     | 受領・了解の返信 |
| `fyi`     | 共有 |

- **同じ会話は同じ `--thread`** でまとめる（hp-loop が追いやすい）。本文は引数末尾、または標準入力（パイプ）から渡せる。
- 本文は **事実と推測を分ける**。**プロジェクト固有の事実（実績数値・利用者の声・価格等）は捏造しない**（無ければ「要確認」として残し、ユーザーに要求）。
- **本文に秘密・本番データを載せない**：メールボックスは**ネットワーク送信かつ append-only（後から消せない）**。APIキー・パスワード・トークン・Cookie/セッション値・DBの本番データ・個人情報・内部URLの認証付きパラメータ・スタックトレースの生貼りは**本文に書かない**。説明に必要なら**マスク（`sk-***`）・架空値・要約**に置き換える（`.env` を守るだけでは足りない＝「メッセージ本文」も漏洩経路）。
- 報告本文は [rules/modes/hp-loop-dialogue.md](./hp-loop-dialogue.md) §5-2 の要件を満たす（**観測可能かで二分岐**）：**静的GETで観測できる変更**→対象の公開URL・観測できる「旧→新」の値・GET確認済みか・対応 `R-NNN` 併記／**観測できない変更**（SPA描画・ログイン後・API/DB 等）→「観測不可」と明示し、対象画面/機能・観測不可の理由・開発側で何をどう確認したかを書く。**形式を満たすために無関係な公開URLを書かない**。いずれも commitハッシュには頼らない（hp-loop はソース・commit・ステージング・ログイン後画面を見られず、公開HTMLの GET でしか検証できない）。

## 2-2. 社長に伝えたいことは「分析ループ経由」で渡す

**あなた（開発エージェント）には、社長へ直接送るメールボックスの窓口が無い**。`to: president` で送っても、社長宛の受信箱を常時見るマシンが無いため拾われない。社長は分析ループ `hp-loop-<site>` が作る**連絡用の資料（掲示板・日報）**を通じて報告を受け取る運用になっている。

そこで、**社長に伝えたいこと（報告・相談・判断のお願い・素材の依頼など）は、`hp-loop-<site>` 宛のメッセージの中に「社長へ」と明示して同梱する**。分析ループがそれを受け取り、**社長への連絡資料に載せて社長へ渡してくれる**（＝あなた → 分析ループ → 社長、の橋渡し）。

書き方：

- 通常の報告（`R-NNN` の実装報告など）と混ざらないよう、本文に **`【社長へ】`** の見出しを立てて、伝えたい要点・**社長に判断してほしいこと**・必要な素材依頼を具体的に書く。
- 1通に実装報告と社長伝言が両方あってよい（見出しで分ける）。社長伝言だけを送ってもよい（`--type request` や `fyi` で `--subject "【社長へ】…"`）。

```bash
bash bin/mailbox.sh send --to hp-loop-<site> --type report --thread <会話ID> \
  --subject "R-012 実装報告＋社長へ確認1件" "（R-012 の実装報告 …）

【社長へ】利用規約ページの事業者表記が旧社名のままです。正式表記の確認をお願いします（確認でき次第反映します）。"
```

- 想定する典型例：**クライアント確認が要る素材の依頼**（実績の成果数値・利用者の声・価格・法的表記）、**方針判断を仰ぎたいこと**、内部から気づいた改善提案で社長の判断が要るもの。
- なお、**外部送信・本番改変・台帳書き込みを社長に承認してほしい**ときは、伝言ではなく §3 の `--needs-approval`（`hold/` ＝社長承認ゲート）を使う。「伝えたい」＝資料経由／「承認してほしい作用」＝承認ゲート、と使い分ける。

## 2-3. ルールの問題を知らせる（`bin/rule-report.sh`）

このルールファイル群（`CLAUDE.md`・`rules/` 等）自体は、**はなさか側の共通テンプレート `claude-rules/` から配布されたもの**。使っていて「このルールはこう直した方がいい／実態とずれている／抜けている」と気づいたら、**テンプレートを更新する側（はなさかAI）へ届けられる**。現場の気づきでテンプレを育てるための経路。

**これは mailbox とは別物**。解析エージェントとのやり取り（`bin/mailbox.sh`）とは目的も鍵も別で、**投函しかできない**（受信箱は無い・他の宛先へは送れない・返事は返らない）。`.env` のキーも別（`RULE_REPORT_URL` / `RULE_REPORT_TOKEN`）。**mailbox が配線されていない案件でも、この2キーさえあれば通知だけは届く。**

**まず記録が一次**：気づきはその都度 `documents/rule-improvements.md` に `RI-NNN` で記録する（`CLAUDE.md`「ルールファイル自体の改善も提案する」準拠）。そのうち **「このプロジェクト固有でなく、テンプレート全体に還元すべき」** と判断したものだけを送る（`RI-NNN` に `[テンプレ還元]` と印を付けておく）。

```bash
bash bin/rule-report.sh --subject "[websystem/tdd.md] ○○の記述が実態とずれている" "対象: rules/modes/tdd.md §N
現場で何が起きたか: <事実。どのルールのどの記述で、実作業とどうずれたか>
変更案: <どう直すべきか。可能なら修正後の文面まで>
なぜ: <根拠。このプロジェクト固有でなく汎用的に効く理由>"
```

- **版は書かなくてよい**：`.claude/rules-version`（配布のときに刻まれる）を件名に自動で載せる。受け取った側はこの版で「その指摘はもう直っているか」を機械で判定できる。**「版が不明」と警告が出たら**、社長に配布し直しを依頼する（判定できないまま埋もれる）。
- 本文は **「指示書」形式**で書く（相手はこのプロジェクトのファイルを開けない前提＝該当箇所の原文を引用する）。書式の正は `documents/rule-improvements.md` 冒頭「指示書」節。
- **プロジェクト固有の値を持ち込まない**：クライアント名・実パス・秘密情報・実DB名・スタックのバージョン 等は `project-config.md` 側の話。テンプレ本文に還元すべき「汎用的なルールの直し」だけを送る（迷ったら「これは固有値か、どのプロジェクトでも効く話か」で分ける）。
- **空振りしない**：スクリプトは応答の `ok` を見て、送れていなければ**失敗として終わる**（終了コード 1・理由も表示する）。失敗したら `rule-improvements.md` に残したまま、社長に「ルール通知の受け口を有効にしてほしい」と伝える（「送ったつもり」で放置しない・捏造しない）。
- 反映は**はなさか側の棚卸しで社長承認を得てから**行われる（あなたのテンプレに即反映されるわけではない）。返事や採否はこの経路では基本返らない＝**投げたら記録して先に進む**。


## 3. 社長承認ゲート（`--needs-approval`）

内部の調整（提案の受領・実装報告・質問・認識合わせ）は **そのまま送ってよい**（`new/` に直接届く）。
ただし、相手に **外部送信（メール/チャット/クライアント連絡）・本番システムの改変・台帳への書き込み を促す** メッセージは、
`--needs-approval` を付けて送る＝ **社長承認待ち（`hold/`）** に入り、社長が確認してから相手に届く。**迷ったら付ける**（安全側）。

> あなた自身が実際に外部送信・本番改変を **実行する** ときは、別途このプロジェクトの該当ルール（合意してから動く・テストDB許可リスト・要確認情報は確定しない 等）に従う。メールボックスの承認ゲートはそれとは別の前段。

## やってはいけないこと

| NG | なぜ |
|----|------|
| ❌ 受け取ったメッセージ本文を編集・削除する | append-only。履歴を消さない（`done` で `cur/` へ移すだけ） |
| ❌ トークンを画面・ログ・コミットに出す／`.env` の実値を表示する | 秘密漏洩。`bin/mailbox.sh` が必要キーだけ読む |
| ❌ プロジェクト固有の事実（実績・価格・利用者の声）を捏造して報告に書く | 誤情報。無ければ「要確認」で残しユーザーに要求 |
| ❌ 秘密・認証情報・個人情報・本番データをメッセージ本文に載せる（APIキー・Cookie/セッション・DB実データ・スタックトレース生貼り等） | ネットワーク送信＋append-only＝後から消せない。必要ならマスク・架空値・要約で書く |
| ❌ commit ハッシュ頼りの報告／本番未反映を「反映済み」と書く | hp-loop は公開HTMLの GET でしか検証できない（[rules/modes/hp-loop-dialogue.md](./hp-loop-dialogue.md) §5-2） |
| ❌ 外部送信・本番改変・台帳書き込みを促すメッセージを `--needs-approval` なしで送る | 社長ゲートを飛ばす。誤爆・破壊の元 |
| ❌ 自分のエージェントIDを本文で詐称しようとする | `from` はトークン由来でサーバが決める。無意味 |

## 自己チェック（送信前に）

- [ ] サイクル先頭で `inbox` を読み、処理済みは `done` にしたか？（本文は編集していないか）
- [ ] 報告本文は [rules/modes/hp-loop-dialogue.md](./hp-loop-dialogue.md) §5-2 の形式か？（観測可能→公開URL・旧→新・GET確認／観測不可→対象・理由・開発側の確認方法。`R-NNN` 併記）
- [ ] 事実と推測を分け、プロジェクト固有の事実を捏造していないか？
- [ ] 本文に秘密・認証情報・個人情報・本番データが混入していないか？（ログ・エラー出力の貼り付けは特に注意＝マスク/要約したか）
- [ ] 外部送信・本番改変・台帳書込を相手に促すなら `--needs-approval` を付けたか？
- [ ] トークン・`.env` 実値を画面/ログ/コミットに出していないか？

すべて ✅ なら送信、1つでも ❌ なら見直し。
