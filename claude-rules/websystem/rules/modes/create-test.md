# テスト仕様書作成ルール

## 基本方針

- **test.csv には「人間（手動）が行うテスト」のみを書く**。自動テスト（バックエンド／フロントエンド）でカバーする項目は書かない（自動テストの仕様はテストコード自体が正＝二重管理しない）
- CSV形式でテスト仕様書を作成する
- 大項目から小項目まで最大5段階の階層構造で整理する
- 各テストケースには期待される動作結果と備考を記載する

## 記録（test.csv）と提示（プロンプト）は別物

test.csv は**後から誰でも同じ手順で追試できるようにするための記録**であり、ユーザーがその場で読むものではない。ユーザーが見ているのは**プロンプト画面だけ**なので、csv に書いただけでは「実装したものが本当に問題ないか」は誰にも確認されないまま通過してしまう。

そこで、**機能を実装したとき・コミットを提案するときは、今回の変更でユーザーに確認してほしいことをチャット上に列挙する**。test.csv は記録、チャットの確認事項は**いま潰すためのもの**。

### いつ提示するか

| タイミング | 出すもの |
|---|---|
| 実装完了・動作確認の報告時（`rules/modes/agent.md` Step 8・9） | ユーザーがこれから触って確かめる項目 |
| コミット提案時（`/commit`・`/commit-pipeline` ステップ2） | **今回の差分に対する確認事項**（コミット前に潰す最後の関門） |

毎回同じ内容を長々と繰り返さない。コミット提案時は**今回のコミットに含まれる分だけ**に絞って再掲する。

### 何を提示するか（5項目）

今回の変更に**実際に関係するものだけ**を書く。該当が無い項目は「なし」と1行で済ませる。

1. **動作確認してほしいこと** — 「どこで・何をすると・どうなれば OK」の形。画面名／URL・操作・期待結果を含める。今回の変更で挙動が変わるところだけ、3〜7件を目安に
2. **判断してほしいこと（AI が仮で決めたこと）** — 仕様に書かれておらず AI が決めた既定値・文言・並び順・命名など。「このままでよいか」を問う
3. **AI が確認できていない範囲** — 自動テストで担保できず AI 側でも見ていないもの（実機の見た目・メールの実受信・決済・外部APIの本結合・本番データでの挙動）。**「見ていないので保証できない」と明示する**
4. **影響が及びうる既存機能** — 共通部品・共通処理を変更した場合に、今回触っていないが波及しうる画面・機能
5. **自動テストの結果** — 実行したテストの件数と成否（＝AI 側で担保できている範囲の裏付け）。該当しないコミットは「該当なし」

### 書き方

- チェックボックス `- [ ]` で1項目1行。ユーザーが上から順に手を動かせる粒度にする
- **専門用語を確認手順に出さない**（クラス名・メソッド名・テーブル名ではなく、画面で見えるもので書く）
- 差分を読めば分かる実装の説明は書かない。「**確認すること**」だけを書く
- 確認して NG が出たら、**コミット前なら修正してから再提示**、コミット後なら別コミットで直す

### test.csv との関係（二重管理しない）

- 今回 test.csv に追加した手動テスト項目は、**そこから今回分を抜き出して提示**する（csv と別に書き起こさない）
- 今回の差分でだけ確認すればよい一過性の項目（移行したデータの見た目確認など）は、**csv に書かず提示だけ**でよい
- 提示した項目が今後も繰り返し必要な確認だと分かったら、test.csv に追加する

## 何を書くか／書かないか（人間テストの判定基準）

判定の既定は「**自動テストで書けるなら自動テストに書く（test.csv には書かない）**」。test.csv に載せるのは、自動化できない・していない確認だけ。

| 書く（人間テスト） | 例 |
|---|---|
| 目視でしか判定できない表示・デザイン | レイアウト崩れ・配色・階層感・レスポンシブの見た目 |
| 実機・実ブラウザでの操作感 | スマホ実機のタップ操作・ブラウザ差・印刷/PDF出力の見た目 |
| 実環境の外部連携 | メールの実受信・決済・外部API/サービスとの本結合確認 |
| 業務シナリオの通し確認 | 複数画面をまたぐ一連の業務フロー（E2E自動化していない場合） |
| 自動化が未整備・困難な確認 | テスト基盤の制約で自動化していない項目（備考に理由を書く） |

| 書かない | 理由 |
|---|---|
| バリデーション・API レスポンス・計算ロジック等、自動テストでカバーする項目 | テストコードが仕様。転記すると版ズレ・二重メンテになる |

> **旧運用からの移行**：以前の運用（全テストを test.csv に書き、自動化分に「自動テスト」と記載）で作られた既存の test.csv は、**ユーザー確認のうえ**「自動テスト」印の項目を削除して手動テストだけに整理してよい。

## CSVフォーマット

### 列構成（11列）

```
チェック, 通常系/異常系, 大項目, 中項目, 小項目, 手順1, 手順2, 手順3, 手順4, 動作結果, 備考
```

### 各列の説明

1. **チェック**: チェックマーク用（空欄可）。テスターが実施時に記入する
2. **通常系/異常系**: テストの種類（通常系 or 異常系）
3. **大項目**: テスト対象の大分類（機能グループ）
4. **中項目**: テスト対象の中分類（機能名）
5. **小項目**: テスト対象の小分類（具体的なテスト項目）
6. **手順1-4**: テスト実行手順（最大4つ、空欄可）
7. **動作結果**: 期待される結果・確認すべき事項
8. **備考**: 補足情報（空欄可）

### 空セルの扱い

- 手順や備考は必ずしも全て埋める必要はない
- 空セルでもカンマは必ず記載（スプレッドシート貼り付け時の体裁維持）
- 例: `通常系,,大項目,中項目,小項目,手順1,手順2,,,動作結果,`

## 記述ルール

### 1. 項目名の設定

- **大項目・中項目**: 仕様書の項目名から適切に設定し、テスト対象の機能が明確にわかるようにする
- 機能の階層構造を反映させる

### 2. 手順の記述

- **細かくしすぎない**: テスターが理解できる範囲でまとめる
- **同じ手順はまとめる**:
  - ❌ 悪い例: `Aを入力,Bを入力,Cを入力,Dを入力`
  - ✅ 良い例: `A,B,C,Dを入力`
- **内部処理は不要**: ユーザーが実際に確認できる手順のみ記載
- **表示関係のテスト**: 確認すべき項目をまとめて1行に記載
  - 例: `商品名、商品画像、商品価格、商品キャッチコピー、商品説明、オプション選択が正しく表示される`

### 3. 動作結果の記述

- テストの判断基準となる確認すべき事項を明確に記載
- 期待される結果を具体的に記述

### 4. 冗長性の排除

- **縦に連続する同名の手順内容は省略**（入れ子形式で整理）
- 親項目で定義された手順は子項目で繰り返さない

### 5. 並び順

以下の順序でソートする:

1. 大項目
2. 中項目
3. 系の種類（通常系 → 異常系）
4. 手順

### 6. 列数の制限

- 上記11列を超えないこと

## 記述例

### 例1: 基本的なテストケース

```
通常系,,ログイン,認証,正しい認証情報でログイン,メールアドレスを入力,パスワードを入力,ログインボタンをクリック,,ダッシュボード画面に遷移する,
```

### 例2: 表示確認テスト（項目をまとめる）

```
通常系,,商品詳細,商品情報表示,基本情報表示,商品詳細画面を表示,,,商品名、商品画像、商品価格、商品キャッチコピー、商品説明、オプション選択が正しく表示される,
```

### 例3: 複数手順をまとめる

```
通常系,,商品登録,商品情報入力,必須項目入力,商品名・価格・カテゴリを入力,保存ボタンをクリック,,,商品が登録され、一覧画面に遷移する,
```

### 例4: 空セルの扱い

```
異常系,,ログイン,認証,メールアドレス未入力,パスワードを入力,ログインボタンをクリック,,,エラーメッセージが表示される,
```
