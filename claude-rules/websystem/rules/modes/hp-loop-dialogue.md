# 外部分析ループ（はなさかAI HP分析ループ）との対話ルール

外部の診断エージェント「**はなさかAI HP分析ループ**」から **改善提案を受け取り、検証 → 対応 → 報告（提案元へ返す）** するときの標準フロー。
このループは **診断・提案だけを行い、実装はしない**。実装はこのプロジェクト（managing側＝あなた）が担う、という分担が前提。

`CLAUDE.md` の協働原則（鵜呑みにしない／不明点は質問／より良い案は提案）と、`rules/modes/developer.md`（実装の流れ）・`rules/modes/tdd.md`・`rules/modes/refactoring.md`・`rules/modes/ui-check.md` を土台とする。

> 提案の受け取り・報告の **送受信の経路（土管）** は [rules/modes/mailbox.md](./mailbox.md)（メールボックス）に従う。本ファイルは **報告の中身（何を検証し・何を書くか）** を定義する。

---

## 1. このループとは何か（相手の素性を知る）

| 項目 | 内容 |
|------|------|
| 相手 | はなさかAI が回す HP分析ループ（`/hp-loop`）。定期/都度にサイトを分析し、改善提案と質問を「掲示板」に積む |
| 掲示板 | 提案・質問・履歴が並ぶページ（はなさか側 `site/hp-analysis/`。ユーザー＝社長が閲覧し、内容を転送してくることもある） |
| 提案の粒度 | 「観察（事実）／なぜ問題か／改善案／効果／工数／優先度」付き。番号は **提案＝`R-NNN`／質問＝`Q-NNN`／サイクル＝`Cycle NNN`** |
| 相手の役割 | **診断・提案まで**（本番改変・実装はしない）。あなたが実装する |
| やり取りの経路 | **メールボックス経由が基本**（→ [rules/modes/mailbox.md](./mailbox.md)）：提案・質問が **対の分析ループ `hp-loop-<site>`**（このプロジェクト担当の分析ループ。`<site>`・宛名は [project-config.md](../../project-config.md)「HP分析ループ連携」を正とする）から直接届き、報告も `bash bin/mailbox.sh send --to hp-loop-<site>` で直接返せる。メールボックス未整備の拠点では従来どおり **ユーザー（社長）が橋渡し**（提案を転送し、報告は社長がループへ戻す） |
| 相手の次の動き | 後続サイクルで **公開HTMLを再取得（GET）して実装結果を再監査・検証** してくる。だから報告には「何を・どう直したか」を **公開HTMLの再取得で確認できる観測可能な変更点** として具体的に書く（commit は辿れない） |

### 相手の能力と限界（ここを理解しておくと検証が速い）

このループの監査は基本 **HTTP GET による静的HTML取得 + 解析**。次の前提・弱点があるので、提案を疑う材料にし、**かつ報告をこの観測面に合わせて書く**：

- **ソース・commit・ステージング・ローカルは見られない**：ループがアクセスできるのは **公開URLの実HTMLを HTTP GET で再取得した結果だけ**。「commit を見れば分かる」「ステージングで確認して」「ローカルの○○を見て」は通じない。検証の唯一の手がかりが公開HTMLなので、報告は **公開URLに反映済みの、GETで観測できる変化** で書く（→ §5-2）
- **JS による後処理・SPA の描画が見えない（JSを実行しない）**：**このテンプレの対象（Webシステム／Webアプリ）ではここが最大の非対称**。配信HTMLがアプリのシェルだけで title/meta/h1 や本文が JS 描画されるサイトでは、ループには**画面の中身がほぼ映らない**。逆に、**JS 描画でしか現れない変更を直しても、ループの再監査では「未反映」に見える** → 報告で「これは静的HTMLには出ない／JS実行後の挙動」と明示しないと、ループが誤って未対応と判定する
- **ログイン後・フォーム送信先には入れない**：ループは GET のみ（フォーム送信・ログイン・アカウント作成はしない）。認証後の画面・登録フローの中身は原理的に監査できず、提案は**公開・未認証の外形**（トップ・LP・OGP・robots/sitemap・応答ヘッダ・構造化データ等）に偏る。内側の実態はあなたが唯一の情報源（→ §3）
- **CMS/構成の判定はヒューリスティック**（資産参照を見るだけ）で外れることがある。「WordPressだから」「○○フレームワークだから」系の前提は鵜呑みにせず、**自プロジェクトの実構成（project-config.md・実コード）を確認してから判定する**
- **件数カウントは共通レイアウト分と画面固有分を区別しない**（「h1が12個」等は内訳を自分で数え直す）
- 実測データ（検索クエリ・順位・流入・CV）は相手も持っていないことが多い（GSC/GA4 未連携なら「データ未取得」と明示してくる）

## 2. 対話の全体像

```
（ループ）掲示板に R-NNN 提案・Q-NNN 質問を積む
   │  mailbox で直接届く（未整備の拠点は社長が転送）
   ▼
（あなた）Step1 検証 → Step2 影響範囲整理・合意 → Step3 実装 → Step4 残課題記録 → Step5 報告
   │  mailbox send --to hp-loop-<site> で直接返す（未整備なら報告文を社長に渡す）
   ▼
（ループ）次サイクルで実装を再監査・検証し、残課題と次の提案を出す … 以降ループ
```

---

## 3. 基本方針

- **提案を鵜呑みにしない。** ループは実コードを直接見られず、静的取得＋テンプレ知識で書いている。必ず **実コードと突き合わせて検証** してから着手する
- 提案の **事実誤認は遠慮なく指摘** する（深刻度の過大評価、構成の誤認など）。ただし **「方向性は妥当」「ここは正しい」も明示** し、フェアに評価する（ループはこの指摘を歓迎し、次サイクルで前提を修正する）
- **着手前にユーザーの合意を取る。** 特に **影響範囲（1画面か／共通レイアウト・共通コンポーネント＝全画面か／API・DB に及ぶか）** と着手順を確認する。**カードの実装中でも同じ**：hp-loop 提案への対応は進行中の `goals.md` のゴール外＝カードの中で進めてよい変更には当たらない。受信したら `documents/pending-issues.md` に記録し（次サイクル候補として扱う）、**統括との合意を経てから着手する**（現行ゴールの達成を優先し、割り込ませない）
- 一度に全部やらない。**Quick win から段階的に**。やり切れない分は `documents/pending-issues.md` に残す
- 最後に **ユーザー向け完了報告** と **提案元ループへ返す報告文** の両方を用意する
- **内部アクセスという非対称の強みを活かす（受け身で実装するだけにしない）。** 分析ループは **公開HTMLを外から見る（GET）ことしかできず**、コード・構成・パフォーマンス・保守性・テスト・セキュリティ・ログイン後のUXなど **内部からしか気づけない改善点は原理的に提案できない**。Webアプリではこの見えない領域が特に広い。あなたは実コードを直接読める立場なので、**ループ提案の実装に留まらず、内部を見て気づいた改善点は自分から積極的に提案・改善する**（外形監査では出てこない領域こそ、あなたの価値）。気づいた内部課題は報告（§5-2）に添えて **ループにもフィードバック** し、次サイクルの提案精度を上げる。
- **あなたは「ループが調べられない内部」を確認できる情報源。依頼に応える／こちらからも聞く。** ループは内部を見られないため、判断に必要な内部事実（この実装は実際どうなっているか／JSで何をしているか／ログイン後はどう見えるか／この値はどこ由来か 等）を **`type: request` であなたに調査・確認依頼してくる** ことがある。コードを直接確認して `report`/`ack` で返す。逆に、外形的にどう見えているか・どのURLで何を観測したかは **あなたからループに聞ける**。**互いに見えている面が違う（あなた＝内部／ループ＝外形）ことを前提に、不足を問い合わせ合う**。

## 4. 実施手順

### Step 1: 提案の検証（実コードとの突き合わせ）

各 `R-NNN` について、**該当ファイル・行を実際に確認**し、主張が事実か判定する。

| 判定 | 意味 |
|---|---|
| ✅ 正確 | 主張どおり。対応する |
| ⚠️ 部分的に正しい | 方向性は妥当だが、深刻度・対処法・前提に誤りがある（修正して対応） |
| ❌ 不正確 | 事実と異なる。対応不要、または前提から見直し |

検証時の典型的な落とし穴（「相手の限界」と対応）：

- 「`title`/`meta`/`h1` が無い」とあっても **JS 描画（SPA）で実行後には存在する** ことがある（逆に、配信HTMLにあるが JS が上書きしていることも）。**配信HTML（静的GET相当）と実行後DOM の両方**で確認し、どちらの話かを区別する
- 「本番に出ている」とあっても **コメントアウトで無効化** されていることがある（→ 配信されているか実DOM/実コードで確認）
- **構成の誤認**（フレームワーク・CMS前提の対処提案など）。自プロジェクトの実構成（project-config.md・実コード）を確認してから適合を判定する
- 件数（「h1が12個」）は **共通レイアウト分と画面固有分を分けて** 数える

### Step 2: 影響範囲と着手順の整理 → ユーザー確認

各項目に付けて提示する：

- **影響範囲**：単一画面 / 共通レイアウト・共通コンポーネント（＝全画面）/ API・DB / 特定機能
- **工数・リスク**：小/中/大、見た目・挙動への影響有無（表示だけか、ロジック・データに触るか）
- **着手順**：Quick win（小・低リスク・即効）を先頭に

ユーザーに確認すること：どこから着手するか（全部／一部／公開面先行）／ユーザー側で用意が要る素材（画像・原稿・アカウント連携・**実績の成果数値や利用者の声**等）／段階実施なら今回スコープと残す分の線引き。**合意を得てから着手する。**

### Step 3: 実装

- 実装は通常の開発規律に従う：`rules/modes/developer.md` §2.1 の実装の流れを土台に、**判定ロジック・API に触るならテスト先行**（`rules/modes/tdd.md`）、リファクタは `rules/modes/refactoring.md`、UI 変更は `rules/modes/ui-check.md` の品質ゲートを通す
- **DB・環境の安全規律を守る**：テストは **テストDB許可リスト**（project-config.md）の範囲でのみ・本番DBに触らない。本番反映（デプロイ）はこのプロジェクトの手順とユーザー合意に従う（分析ループへの報告のために先走って本番を変えない）
- **共通レイアウト・共通コンポーネントを変更する場合は「全画面に影響する」ことを必ず明記**する（このループの提案は「トップで効いた修正を全ページへ」という展開系が多い）

### Step 4: 残課題の記録

その場でやり切らない項目は `documents/pending-issues.md` に記録する（`CLAUDE.md`「残存課題の記録ルール」準拠）。

- 完了した範囲 / 未対応の範囲を分けて書く（例：R-011 メタ整備＝公開LPは完了、アプリ内画面が未対応）
- 未対応の影響範囲（どのファイル・どの画面）／着手時の安全性メモ（表示のみで挙動不変 等）
- 対応する `R-NNN` を併記し、ループ側の提案と突合できるようにする

### Step 5: 報告（2系統）

#### 5-1. ユーザー向け完了報告
実施項目（`R-NNN` と対応内容の対応表）／検証で判明した提案の誤り／残課題（pending-issues 記録済みの旨）／ユーザーに依頼する目視確認・素材配置。

#### 5-2. 提案元ループへ返す報告文
ループは後続サイクルでこれを読んで **再監査・検証** する。mailbox 配線済みなら `bash bin/mailbox.sh send --to hp-loop-<site>` で直接送る（[rules/modes/mailbox.md](./mailbox.md) §2）。次の要素を入れる：

- **実施済み**：`R-NNN` ごとに、まず **その変更が静的GETで観測可能か** を判定し、**二分岐で書く**。**観測可能**→ループが公開URLを HTTP GET で再取得して照合できる「観測可能な変化」として書く（下記）。**観測不可**（SPA描画・ログイン後・API/DB・アプリ内挙動）→「観測不可」と明示し、対象画面/機能・観測不可の理由・開発側で何をどう確認したかを書く（下記3項目め）。**形式を満たすために無関係な公開URLや作り物の「旧→新」を書かない**（観測不可は観測不可と書くのが正しい報告）。観測可能な場合は次を満たす：
  - **どのURLの・何が・どう変わったか**を具体値で：対象の **公開URL** ＋ 観測できる信号を **「旧→新」の値**で書く（例：`h1数: 2→1`、`title: 旧文言→新文言`、`canonical: なし→https://…`、OGPタグの値、応答ヘッダ）。可能なら対象要素の識別子も添える（`meta[name="description"]`／`link[rel="canonical"]`／`script[type="application/ld+json"]`）。ループはこの値を再GETして直接照合する
  - **公開URLでGET確認済みかを明記**：「反映済み」は *Managing側のデプロイ操作* ではなく **公開URLを実際に GET して現値を確認できた** ことを指す。デプロイしたがGET未確認なら「デプロイ済み・GET未確認」と区別して書く。本番に出ていない（ステージング止まり・ビルド/デプロイ待ち）ならその旨と反映予定を。CDN/キャッシュがあるなら **GET確認した時刻 or キャッシュ反映待ち** を添える（書かないとループの再監査で「未反映」と誤判定される）
  - **静的HTML(GET)では確認できない変更は、その旨を明示**：**SPA・Webアプリでは画面変更の多くがこれに該当し得る**。JS 描画でしか現れない変更・ログイン後の画面・アプリ内の挙動・画像バイナリの内容などは、ループが再監査しても観測できない。「これは静的取得には出ない」と添え、代わりに**開発側で何をどう確認したか**（実行後DOM・テスト・スクリーンショット等）を書く。これらは **ループの `R-NNN` 完了判定には使えない＝別確認扱い**（観測できないものを観測前提で報告しない）
  - **commit ハッシュは載せない**：ループの検証には使えない。commit は当方の社内記録用にとどめ、報告文では検証手段として頼らない
  - **対応した `R-NNN` の併記は必須**（ループ側の提案番号と突合するため）
- **認識合わせ**：提案の事実誤りと正しい実態（**フェアに、正しかった点も明記**）。例「R-002：本サイトは SPA で meta は JS 注入。指摘の『title 無し』は配信HTMLとしては正確、実行後は存在。SSR/プリレンダ導入で静的GETにも出るよう対応」
- **残課題**：段階的に継続する項目（`R-NNN`・影響範囲つき）
- **データ補完依頼**：内部改善だけでは「どのページ/クエリを伸ばすか」決められない。GSC/GA4 の検索クエリ・順位・流入元・CV数の共有を、ループ側の `Q-NNN`（データ要求）に答える形で依頼/相談する
- **社長への伝言（あれば）**：あなたには社長への直接窓口が無いので、社長に伝えたいこと（クライアント確認が要る素材の依頼＝実績数値・利用者の声・価格・法的表記、方針判断のお願い、内部から気づいた要判断の改善提案 等）は本文に **`【社長へ】`** の見出しで明示する。ループが社長への連絡資料（掲示板・日報）に載せて橋渡しする（→ 経路は [rules/modes/mailbox.md](./mailbox.md) §2-2）。**外部送信・本番改変・台帳書込の「承認」がほしい場合は伝言ではなく `--needs-approval`**（[rules/modes/mailbox.md](./mailbox.md) §3）を使う

> コミットが必要なら `/commit-pipeline` に流す。

#### 5-3. 解析からの「在庫の解消のお願い」への返事（2026-10-20 追加）

解析（`hp-loop-<site>`）から、thread `<site>-inventory` で「在庫の解消のお願い」が届くことがある。
そのサイトの在庫（まだ決着していない提案 R・質問 Q）が上限に達したときに、**こちら（実装側）の手にあるもの**を一覧にして送ってくる。
通常の対応報告（5-1／5-2）とは別の便で、**在庫を決着させるための返事**を求めるもの。

- **これは本番の変更の承認ではない。** 実装するかどうか・本番に入れる手順は、これまでの決まりどおり（§4）。
- 一覧の1件ずつに、次のどれかで返す。1通にまとめ、同じ thread（`<site>-inventory`）・`type: report` で送る。
  - `実装した`（反映した日・どこで確かめられるか。**書き方は 5-2「実施済み」と同じ**＝観測可能なら公開URL・旧→新の値・GET確認済みか／観測できないなら「観測不可」と理由・開発側で何をどう確かめたか）
  - `できない`（理由）
  - `取り下げたい`（理由。例：前提が変わった・効果が見込めない）
  - `まとめたい`（どの R とまとめるか）
  - `まだ`（いつごろ・何待ちか）
- 書き方の例：

      R-R28: 実装した（2026-10-22 反映・GET確認済み・https://…/map の下部に「アクセス」見出し：なし→あり）
      R-R31: 実装した（2026-10-22 反映・観測不可＝ログイン後の画面。実行後DOMとテストで確認）
      R-R37: まだ（11月中・説明文の元データ待ち）
      R-R40: できない（旧サーバーの管理権限が無い）→【社長へ】旧サイトの扱いの判断をお願いします

- 事業の方針・お金・クライアントの意向が要るものは、これまでどおり `【社長へ】` を付けて添える（解析が社長に届ける）。
- 一覧に無いものの話や、自由な文の返事でもかまわない。解析は形にこだわらずに読む。
- 解析は、返事を確かめてから（`実装した` は本番で確かめてから）在庫を閉じる。`取り下げたい`・`まとめたい` は、解析が筋を確かめて閉じるか、社長に回す。

#### 5-4. 依頼が無くても、作業を終えたら解析へ伝える（作業の通知・2026-11-05 追加）

🚨 **解析の提案に応えたときだけでなく、クライアントの依頼で直したとき・開発が自分から改善したときも、作業を終えたら解析（`hp-loop-<site>`）へ伝える。**

- **なぜ①**：解析が見られるのは公開ページの「いまの姿」だけで、**何が・いつ・なぜ変わったかを知っているのは開発だけ**。伝えないと、解析は新しいコンテンツに気づくのが遅れ、対応済みの点を「未対応」と判定し、同じ提案を繰り返す。
- **なぜ②**：解析は、社長がクライアントへ出す月次レポートの「**この1ヵ月で何が変わったか**」をこの通知から組み立てる。お客様にとっては、変化が分かること自体が安心につながる。**開発が自発的に行った改善こそ、伝えないと誰も知らない。**

**いつ送るか**：コミットしたら、送るかどうかを決める（2窓なら統括が `rules/modes/director.md` §7.3 で決める）。**同じカード・同じ機能の連続コミット**（`[be]`／`[fe]`／`[test]` に分けた等）は、**機能が一区切りした時点で1通にまとめてよい**（月次レポートを技術の単位に割らない）。

- 🚨 **解析の提案への対応は、§5-2 の報告で返す。** その報告に「区分」と「何をしたか（レポート用の1行）」を入れれば、**別に作業の通知は送らない**（同じ変更を2通にしない）。

- **意味のある変更を伝える。完璧な網羅は要らない。** 目安は「お客様が読んで、この1ヵ月で何が変わったかが分かるか」。**迷ったら送る**。次の**どれかに当たれば送る**：
  - 表示・内容・使い方が変わった（ページ・セクション・機能が**増えた**ものを含む）
  - 速さ・安定性・安全性が上がった（公開ページに出ない作業でもよい＝解析には見えないが、お客様にとっては「やってもらったこと」になる）
  - 不具合を直した・将来の不具合を防いだ
- **原則として省くもの**：誤字1文字のような表記の微修正（いくつかあれば「細かな表記の修正」と1行にまとめてよい）／コードの整理・テストの追加・文書・部品の更新**だけ**で、お客様への効果を説明できないもの。
- **書くために別の記録を持たない。** 何を変えたかはリポジトリの履歴（そのコミットの差分とメッセージ）に残っている。開発が書き足すのは、**履歴に無い「なぜ」と、お客様向けの言い方**だけ。

**書くこと**（1件ごとに）：

| 項目 | 書き方 |
|---|---|
| 区分 | `依頼対応`（クライアント・社長の依頼）／`提案対応 R-NNN`（解析の提案。ただし上のとおり §5-2 の報告に含める）／`自発的な改善`（開発が自分で気づいて直した）のどれか。**`R-NNN` は提案対応のときだけ**書く（他には番号が無い＝作らない） |
| 何をしたか | **クライアント向けのレポートにそのまま載る1行**（専門用語を避ける。例：「トップページに新着情報の欄を追加しました」） |
| 対象 | 変えたページの**公開URL**。公開URLで見えない変更（JS で描く画面・ログイン後・API／DB・公開ページに出ない作業）は、**対象の画面・機能**を書いて「**解析から観測不可**」と明記する（§5-2 と同じ＝**形式を満たすために無関係な公開URLを書かない**） |
| 変化 | 観測できるなら「旧→新」の値（5-2 と同じ）。**新しく増えたページ・セクション・コンテンツは「追加」と明記**（解析が新しい対象として扱えるように） |
| 作業日・反映日 | 作業した日と、公開ページに反映した日。🚨 **反映していないなら「未反映（反映待ち）」と書く**（5-2 と同じ＝反映済みと書かない）。未反映で送ったら、反映を確かめた時点で**1行の続報**を同じ thread に送る。確かめ方は §5-2 と同じ＝**公開URLで見える変更は GET で、見えない変更は「観測不可」と書いて、反映した環境とこちらでの確認方法・結果**を添える |
| 技術の詳細（任意） | 変えたファイル・やり方。解析の判定材料。**レポート用の1行とは分けて書く** |

**送り方**：[rules/modes/mailbox.md](./mailbox.md) で `hp-loop-<site>` 宛て・`type: report`・thread は `<site>-worklog`。宛名は `project-config.md`「HP分析ループ連携」が正。**対の解析ループが無い案件は出番なし**。

- **社長承認ゲート（`--needs-approval`）は付けない**＝事実の共有で、解析に何かを実行させる依頼ではないから（付けると承認待ちで止まり、月次の材料が欠ける）。
- 🚨 **通知は単独で送る＝依頼を混ぜない。** 承認が要る依頼（外部送信・本番改変・台帳書き込みを促すもの）を同じ便に入れると、**通知ごと承認待ちで止まる**。依頼は別便にして [mailbox.md](./mailbox.md) §3 に従う。ふつうの質問・認識合わせは承認不要。

書き方の例：

    【作業の通知】2026-11-05
    - 区分: 自発的な改善
      何をしたか: スマートフォンでお問い合わせボタンが押しにくかったので、大きくしました
      対象: https://example.com/contact/
      変化: ボタンの高さ 32px→48px
      作業日: 2026-11-05 ／ 反映日: 2026-11-05（公開URLで確認）
    - 区分: 依頼対応
      何をしたか: 「採用情報」ページを追加しました
      対象: https://example.com/recruit/（追加）
      作業日: 2026-11-05 ／ 反映日: 未反映（11/7 公開予定）

> 🚨 **この節は website / websystem の両テンプレートに同じ内容で置いてある。片方だけ直さない。**

## 6. やってはいけないこと

| NG | なぜ |
|----|------|
| ❌ 提案を検証せずそのまま実装する | ループは静的取得＋推測。実コードと食い違うことがある |
| ❌ 影響範囲（特に共通レイアウト＝全画面・API/DB）を確認せず着手する | 全画面事故・データ事故の元。展開系の提案が多い |
| ❌ 構成前提（CMS・フレームワーク等）を確かめずに提案の対処法を実行する | ループの構成判定はヒューリスティックで外れることがある。実構成（project-config.md・実コード）を確認してから対処する |
| ❌ 分析ループへの報告のために、合意・テスト・デプロイ手順を飛ばして本番を変える | 本番の安全規律（tdd.md・テストDB許可リスト・ユーザー合意）が優先。報告は「未反映」と正直に書けばよい |
| ❌ 残課題を口頭報告だけで済ませ記録しない | 取りこぼし。`documents/pending-issues.md` に残す |
| ❌ 提案元への報告で誤りの指摘だけして正しかった点を無視する | フェアでない。ループの前提修正を妨げる |
| ❌ 報告を「公開HTMLで確認できない形」で書く（commitハッシュ頼り等） | ループはHTTP GETで公開HTMLを再取得して再監査するため、観測可能な変更点で書かないと検証できない。対応 `R-NNN` の併記は引き続き必須 |
| ❌ ループが観測できない状態を前提に報告する（未公開／ステージング止まり／JS依存・SPA描画・ログイン後 等） | ループが見るのは公開URLの実HTMLの静的GETのみ。本番反映前や JS でしか現れない変更は再監査で観測できず「未反映」と誤判定される。公開URL・本番反映済みか・静的取得で見えるかを明示する |
| ❌ ループ提案の実装だけで終わり、内部からしか気づけない改善を黙っている | 内部（コード・構成・保守性・テスト・セキュリティ・ログイン後UX）を見られるのは開発側だけ。外形監査では出ない改善が埋もれる。気づいたら提案・改善し、ループにも共有する（§3） |
| ❌ ループに「内部を見て確認して」「ログインして確認して」と求める | ループは公開HTMLの外形しか見られない（GETのみ・ログイン不可）。内部の確認・調査は **依頼されたら開発側が行う**。ループへ尋ねてよいのは外形的観測（どのURLで何が見えるか）だけ |
| ❌ 依頼されていない作業だから（クライアントの依頼で直した・自分で改善した）と、意味のある変更を解析へ伝えない | 解析は変化を知る手段が無い＝新しいコンテンツに気づけず、対応済みを「未対応」と判定する。月次レポートの「この1ヵ月で何が変わったか」にも載らない（§5-4） |

## 7. このルール自体の改善

ループとの対話で「掲示板の番号体系が変わった」「報告フォーマットの過不足」等に気付いたら、`CLAUDE.md`「ルールファイル自体の改善も提案する」に従い `documents/rule-improvements.md` に記録し、テンプレ級なら `[テンプレ還元]` 印を付けて還元する（[rules/modes/mailbox.md](./mailbox.md) §2-3）。
