# 見積もり用タスク抽出・難易度評価ルール

このファイルは、**新機能を実装する前に見積もりを行うため、タスクを洗い出し評価する**ときに参照する。

## 目的

新機能の開発見積もりの精度を上げるため、以下を標準化する。

1. タスクの抽出（漏れなく・見積もれる粒度で）
2. 3 軸 × 10 段階での評価
3. 要確認事項の明示（見積もり前に決めること）
4. 推奨実装順序の提示

---

## 1. タスクの抽出

### 区分（レイヤー）で洗い出す

機能ごとに、以下の区分でタスクを列挙する。区分は対象機能に応じて取捨する。

| 区分 | 内容 |
|---|---|
| バックエンド | マイグレーション・モデル・FormRequest・コントローラ・API |
| 管理画面フロントエンド | 管理画面の UI・フォーム・一覧 |
| ユーザー／カタログ画面フロントエンド | エンドユーザー向け画面 |
| **既存機能への波及** | 新機能のデータ構造変更などが影響する既存機能 |
| テスト | バックエンド／フロントエンド／回帰／既存データ互換確認 |
| ドキュメント | 仕様書（`documents/specs/`）・テスト仕様書（`documents/test.csv`） |

### 工程区分（設計・開発 ／ 確認・対応）

区分（レイヤー）とは別に、各タスクを **2 つの工程区分**のどちらかに分ける。分かれ目は
「**その時間が縮むかどうか**」で、金額の算定（`rules/modes/quotation.md` §5-1）で扱いが変わる。

| 工程区分 | 中身 |
|---|---|
| 設計・開発 | 仕様整理・実装・自動テスト・ドキュメント |
| 確認・対応 | 実環境での結合確認・受け入れテスト支援・本番リリース・顧客とのやり取り＝**人の時間が縮まない作業** |

- 判定に迷ったら「**担当者が替わっても・道具が変わっても、この時間は短くならないか**」を問う。短くならないなら「確認・対応」。
- 「確認・対応」に入るものは、`rules/modes/quotation.md` §1 手順2 が**必ず洗い出すと定めている3つ**（仕様整理・リリース作業・受け入れテスト支援／運用案内）のうち、仕様整理を除いた分とほぼ重なる（仕様整理は設計・開発側）。**洗い出しの正は quotation.md §1**で、ここはその分類だけを決める（重複定義しない）。

### タスク ID

各タスクに「区分の英字 + 連番」で ID を付与する（例：`A-1`, `B-2`）。
見積もり表や依存関係・タスク間参照の記述で使いやすくする。

### 粒度

**「項目 → 機能 → 詳細」の第 3 階層（機能単位）まで分ける。**

- 🚨 **粗い 1 行に高い品質係数を付けると、その中の定型部分にまで高い係数が乗る**（`rules/modes/quotation.md` §5-1）。現場実例＝お金の安全に関わる機能として 1 行で高い係数を付けていた中に、受け口・メール通知といった定型部分が混ざっていた。機能ごとに分け直すと**金額は下がり、逆にお金の安全に関わるテストは上がった**。粒度の規定そのものが精度を上げる。
- 分けすぎれば管理コストが上がるので、**係数と工程区分が同じ作業はまとめてよい**（＝分ける理由は「係数か工程区分が変わるから」）。
- 顧客に出す見積書の階層もこの粒度に揃える（`rules/modes/quotation.md` §5-3）。

### 見落としやすい観点（必ず確認する）

- **既存機能への波及**：新機能がデータ構造を変える場合、それを使う既存機能（カート・注文・
  CSV 出力・価格計算など）すべてに波及タスクが発生する。ここの洗い出し漏れが見積もりを
  最も大きく狂わせる。
- **サーバー側の整合性・バリデーション**：フロントの表示制御だけに頼らず、API 側でも
  不正な入力を拒否するタスクを立てる。
- **既存データ互換**：マイグレーション後、既存データが従来どおり動くかの確認タスク。
- **付随機能の改修**：新機能によって既存の関連機能（複製・エクスポート等）にも改修が
  必要になることがある。
- **権限・ロール**：新機能が、そのプロジェクトに存在する **どの Authenticatable 種別・ロール**
  （`project-config.md` を正とする）からアクセスされうるか、Policy の対応が必要かを確認する。
- **デプロイ順序**：マイグレーションとコードリリースの順序に注意が要る変更か
  （順序を誤ると一時的に不整合が起きうる）。
- **推奨・オプション項目の自動テスト**：必須機能にはテストを積んでいるのに、推奨・オプションとして
  足した項目にはテストを積み忘れる（項目を後から足したときに起きる）。
- **既存システムの更新か、新規構築か**：同じ「リリース作業」でも重さが違う。既存の更新なら
  **反映とマイグレーション・外部サービスの本番設定・本番での少額（最小）確認**の実内容で積む
  （新規構築並みに積むと過大になる。現場実例＝10 時間で積んでいたものが実内容では 3 時間だった）。
- **保守・運用契約で賄う作業**：運用資料の作成・リリース後の操作相談などが契約の運用保守費に
  含まれている場合、見積もりに**二重計上**しない。範囲は `project-config.md`「見積もり」節の
  「保守・運用契約で賄う範囲」が正。🚨 **項目そのものは消さない**＝「運用保守費にて対応」と
  書いて 0 円にする（消すと「やらない」と読まれ、後の無償対応の元になる）。

## 2. 3 軸 × 10 段階評価

各タスクを次の 3 軸で評価する。**各軸 1〜10 の 10 段階**。

| 軸 | 観点 |
|---|---|
| リスク（影響度） | 他機能への影響度・影響範囲。変更・不具合時に波及する広さ |
| 難易度（技術） | 技術的な難しさ |
| 工数（作業量） | 作業のボリューム |

### なぜ 10 段階か

5 段階では中間（3 前後）に集中し、難しいものと簡単なものの差が出にくい。
10 段階で **裾を広く使い**、メリハリをつける。

### 値の振り分け目安（アンカー）

評価者によって点数がぶれないよう、各軸に以下のアンカーを置く。

| 値 | リスク（影響度） | 難易度（技術） | 工数（作業量）※目安 |
|---|---|---|---|
| 1-3 | 影響はそのタスク内でほぼ完結（マイグレーション・型定義・ドキュメント） | 定型・既存パターンの踏襲（単純な CRUD・UI） | 数十分〜1 日 |
| 4-6 | 一部の関連機能に波及（API レスポンス変更・特定画面） | 設計の判断が必要（連動 UI・条件付きバリデーション） | 1〜2 日 |
| 7-8 | 中核機能に波及し回帰リスクが大きい（カート・注文・商品表示） | 技術的に難しい（ID 再マッピング・複雑な状態管理） | 3〜5 日 |
| 9-10 | システム横断で波及（価格計算など全フローに関わる） | 新規性が高く設計が重い（前例のない仕組み） | 1 週間以上 |

- 工数の日数アンカーは目安。チームの実装速度に合わせて調整してよい。
- 全タスクが中間に固まらないよう、定型タスクは思い切って 1-2 に下げる。
- 9-10 は本当に突出したものだけに使う（乱発しない）。
- 🚨 **「工数（作業量）」軸は優先順位づけ専用。金額の元ではない。** 金額は §5 の
  **「作業時間」**から出す（`rules/modes/quotation.md` §5-1）。この軸のアンカー（数十分〜1 週間以上）は
  **人が手で書く速度**を前提にした目安なので、実装・自動テストの大半を AI が行う案件では実時間と
  大きくずれる。ずれ自体は構わない（順位づけには使える）が、**この日数をそのまま人日として
  積み上げて金額にしない。**

## 3. 見積もり前の要確認事項

タスク一覧とは別に、「**見積もり前に決めると精度が上がる論点**」を列挙する
（節 2 の「リスク（影響度）」軸とは別物。こちらは仕様・スコープの不確実性を扱う）。

- スコープの線引き（例：階層は何段まで対応するか）
- データ構造から変えるのか、表示ロジックだけ変えるのか（工数が大きく振れる分岐）
- 機能が v1 必須か、補助・次版送りか
- 工数が振れるタスクは、出力（CSV）の備考欄に分岐条件を明記する

---

## 4. 推奨実装順序

依存関係に沿った順序を示す。原則：

```
データ基盤（DB・モデル・API）
  → 管理機能
  → ユーザー／カタログ向け機能
  → 既存機能への波及（回帰）
  → 付随機能（CSV 入出力 等）
テスト・ドキュメントは各段階で並行
```

- 難易度が高いタスク（目安 7 以上）は、本実装の前に設計レビュー／スパイク調査の
  時間を別タスクとして見込む。

## 5. 出力形式

### CSV（見積もり計算に使う場合）

列構成：

```
タスクID, 機能, 区分, 工程区分, タスク内容, リスク(影響度1-10), 難易度(技術1-10), 工数(作業量1-10), 作業時間(h), 標準工数(人日), 備考
```

- UTF-8 **BOM 付き**で保存する（Excel で開いた際の文字化け回避）
- テスト・ドキュメント区分なども含め、全タスクに 3 軸の評価値を入れる（空欄にしない）
- **工程区分**：`設計・開発` / `確認・対応` のどちらか（§1「工程区分」）。空欄にしない。
- **作業時間(h)**：実際にかかる見込み時間。**検品・確認の時間を含める。**金額はここから出す
  （`rules/modes/quotation.md` §5-1）。刻みは `project-config.md`「見積もり」節が正。
- **標準工数(人日)**：人の作業に換算した**参考値**。社内で規模感を比べるためだけに持ち、
  🚨 **顧客に出す資料には載せない**（作業時間と並べると「なぜこの差が？」という説明のつかない
  疑問を招く。`rules/modes/quotation.md` §5-3）。
- この CSV は**社内用**。顧客提示用は §5-3 の規定に従い、**同じ定義から生成する**
  （`rules/modes/quotation.md` §5-3）。

### HTML（クライアント提示や仕様の記録を兼ねる場合）

- `documents/specs/proposals/` 配下に配置する（`.claude/rules/spec-format.md` のフォーマットに準じる）
- リスク・難易度は色バッジ等で視認性を上げる
- タスク一覧・見積もり前の要確認事項・推奨実装順序を含める
