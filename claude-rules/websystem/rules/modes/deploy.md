# デプロイ手順の提示ルール

> **AI はデプロイを実行しない。** `git push` / PR 作成・マージ / 本番サーバーでのコマンド実行は **すべてユーザーが行う**。
> AI の役割は「**実状態を読み取り → 手順を確定し → 出力を読んで次を判断する**」ことに徹する。
> 本番反映は `rules/modes/developer.md` §4.1「**必ず止まるもの**」に当たる（AI は実行しない）。

固有値（ブランチ名・昇格経路・サーバー・サービス構成・実コマンド）は **`project-config.md`「ブランチ運用・デプロイ」欄を正**とする。
本ファイルには**手順の型**だけを置く。

---

## 1. 手順を提示する前に、本番の実状態を読む

**手順を推測で書かない。** 次をユーザーに実行してもらい、**出力を見てから**手順を確定する。

```bash
git log -1 --oneline      # HEAD の実体（ブランチ名ではなく中身）
git branch --show-current # ブランチ名（中身と食い違うことがある）
git status --short        # 未コミットのローカル変更
```

- **ブランチ名を信用しない。** `git log -1` が表示する `(HEAD -> X, origin/Y)` の **`origin/Y` が実際の追従先**。
  ローカル名が `X` でも中身が別ブランチの先端であることは実際に起きる。ここを見ずに `git checkout <名前>` を指示すると、
  **本番コードが数十コミット巻き戻る**
- **どのブランチが本番かを推測しない。** 使われなくなった古いブランチが残っているのは普通のこと
  （最終コミットが 1 年前のブランチを「本番」と読み違える事故が実際に起きている）。
  `project-config.md` の記入が無ければ**ユーザーに確認する**
- **ローカル変更があったら、流入するコミットがそのファイルに触れるか事前に確認する**

  ```bash
  git log --oneline <本番HEAD>..<デプロイ対象> -- <ファイル>
  ```

  触れるなら pull は中断する（マージ衝突で作業が止まる）。**触れないことを確認してから進める**

---

## 2. 反映に何が必要かは「構成」で決まる

サービスごとに「**ソースをマウントしているか、成果物に焼き込んでいるか**」を確認する。
同一プロジェクト内でもサービスによって違うことがある（片方だけ古いまま、という発見しづらい事故になる）。

| 構成 | 反映に必要なこと |
|---|---|
| ソースをバインドマウント／サーバー上で直接実行 | `git pull` だけで**即反映される**（**だから危険でもある**＝下記 3 の順序に注意） |
| ビルド成果物・イメージに焼き込み | **再ビルドが必須**。pull しても古いまま |

どのサービスがどちらかは `project-config.md` に記入しておく（毎回調べ直さない）。

---

## 3. 順序（スキーマ変更・破壊的マイグレーションを含む場合）

1. **メンテナンスモード ON** — 即反映される構成では **`git pull` より先**。
   pull した瞬間に「**新コード × 旧スキーマ**」の窓が開く
2. **DB バックアップ** — テーブル・カラムのリネームや削除を含むなら必須。
   取得後に**ファイルサイズが 0 でないこと**を確認する
3. `git pull`
4. **マイグレーション** — 実行前に **pending の一覧を確認**する
5. **焼き込み構成のサービスを再ビルド**
6. **キャッシュクリア**（ルート・設定を追加したときは必須）・**キューワーカー再起動**
7. **メンテ中のまま**スキーマ・件数を確認する
8. **メンテナンス OFF** → 画面で確認（**確認するURLは `project-config.md`「URL・確認環境」の本番行**。「デプロイした」で終わらせず、実際にそのURLを開いて確認する）

スキーマ変更を伴わない軽微な反映では 1・2・7 を省略してよいが、**省略したことを明示して**ユーザーの判断を仰ぐ。

### 3.1 人が打つ手順書に「確認」と「判断の分岐」があるとき（削除リスト・移行手順・本番 SQL）

🚨 **判断の分岐を足したら、その分岐が要求するデータを確認の側にも足す。**

手順書の「確認（実行前に数える・見るクエリ）」と「判断（結果に応じてどうするかの表）」は**別々に育つ**。
あとから分岐を1つ足した瞬間に、確認が不足することがある。**足した時点では、どちらも単体では正しく見える**
＝レビューで見つからず、SQL はエラーにならず値を返す（**足りないことは出力に現れない**）。

> 実例（2026-09-20・現場報告）：本番 DB の重複レコードを消す手順書。確認クエリは「消す側」の件数だけを数えていたが、
> あとから足した判断表は3通りのうち2通りが「**残す側**」の件数を要求していた。「両方 0 に見える」とき消すのは
> 残す側だったので、**守りたかったデータが、いちばん消えやすい経路に乗っていた**。

- **点検のしかた**（「気をつける」では見つからない）：**判断表の各行を指差して、「この行を決めるのに必要な値は、
  確認クエリの出力に入っているか」を1行ずつ問う。**
- 🔑 **さらに良いのは、判断そのものをクエリに入れてしまうこと。** `CASE` で「どうするか」を1列出せば、
  **人が対応表を突き合わせる工程ごと消える**（人が目視で突き合わせる限り、同じ型の間違いが起き続ける）。
- 手順書を人に渡す前に、上の点検をした・判定列を出した、のどちらかを手順書に書いておく。

---

## 4. やってはいけないこと

| ❌ | 理由 |
|---|---|
| 実状態を読まずに手順を書く | ブランチ名と中身の乖離・死んだブランチへのマージ事故 |
| AI が `git push` / PR マージ / 本番コマンドを実行する | 本番反映はユーザーの操作（クリティカル判断） |
| ローカル変更を確認せずに `git pull` を指示する | 中断・意図しない上書き |
| バックアップ無しで破壊的マイグレーションを流す | 戻せない |
| 手順書の判断表に分岐を足して、確認クエリを直さない | 分岐が要る値を確認が数えていないと、守りたいデータが消える側に回る。エラーにならないので気づけない（§3.1） |
| 「pull すれば全部反映される」と決めつける | 焼き込み構成のサービスが古いまま残る |
