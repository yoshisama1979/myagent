# TDD/BDD 開発ルール

> 『確認を必ず取る』は、ユーザーと1件ずつ進めるときの規律。**委任カードで進めるときは、確認ポイントを報告（`rules/modes/developer.md` §7）と判断ログ（`rules/modes/director.md` §5.2）への記録に読み替える**（手を止めるのは `rules/modes/developer.md` §4.1「必ず止まるもの」だけ）。

## 共通

-   シナリオを作成したら確認を必ず取る
-   バックエンドを開発したら確認をとり次に進む

## 1. 📄 既存コード・ドキュメントの調査

・既存コードベースの構造を分析
・関連するドキュメントを確認
・統合ポイントを特定
・現在のパターンや規約を理解

## 1.5 🔍 三者整合性チェック（必須）

シナリオ作成前に以下の3つを突き合わせ、不整合があればユーザーに報告する。
・仕様書: `documents/specs/` 配下の該当HTML（specs/ 未整備で `document.md` しか無いプロジェクトはそれ）
・テスト仕様書（documents/test.csv）
・実装コード（該当ファイル）

不整合パターンと対応：
・仕様書 ≠ 実装コード → 差異を具体的に示し、どちらが正しいか確認する
・仕様書 ≠ test.csv → test.csv の期待値が仕様書と矛盾している箇所を指摘する
・test.csv ≠ 実装コード → test.csv の期待値と実際の挙動の差異を示す

ルール：
・推測で「正しい方」を判断しない。ユーザーの判断を仰ぐ
・シナリオの期待値は仕様書（`documents/specs/` 配下の該当HTML。specs/ 未整備なら `document.md`）を正とする
・不整合が解消されてからシナリオ作成に進む

## 1.6 🧾 既知のテスト失敗（ベースライン）は「既知」であって「無害」ではない

着手前にテストを流して**既存の失敗件数（ベースライン）**を把握し、リグレッション判定は
**「新規失敗が 0 件であること」**で行う（この判定基準は維持する）。そのうえで：

・**ベースライン計測時に失敗一覧を眺め、「今回触る領域に関係する失敗が混ざっていないか」を必ず確認する**
・関係するものが 1 件でもあれば、**中身を読む**（件数だけ数えて次へ進まない）
・読んだ結果、いま直す案件と同根なら**そのラウンドで直す**
・同根でなければ、なぜ落ちているかを 1 行で `documents/pending-issues.md` に残す

件数の差分しか見ない運用は「既知＝無害」と読めてしまう。ベースライン失敗の一覧は
「見なくてよいもの」ではなく、**過去の自分が残した未読の通知**である。
（既知失敗の件数・一覧をプロジェクトで管理している場合、その置き場は `project-config.md` を正とする）

## 2. 🎯 対話的な BDD シナリオ作成

・会話を通して機能要件を定義
・Gherkin スタイルのシナリオを作成:
Feature: [機能名]
As a [役割]
I want [機能]
So that [利点]

    Scenario: [シナリオ名]
        Given [初期状態]
        When [行動]
        Then [期待される結果]

・受け入れ基準を共同で作成
・フィードバックに基づきシナリオを改善

## 3. 🔄 RGBC サイクル（繰り返し）

3.0 ⚠️ Red を経ていないテストは、まだ担保になっていない
・**既存の実装に対して後からテストを書くとき**（実装を終えてからテストを足す／
リファクタ前に現在の挙動を固定する）は、Red フェーズが存在しない。
このとき「テストが通った」は「テストが効いている」を意味しない。
・書いたら、**守りたい実装をわざと 1 つ壊し、そのテストが落ちることを確認する**
（確認したら必ず元に戻す）。落ちなければアサーションが緩い＝書き直す。
・これは Red の代替。3.1 の手順で書いたテストには不要（Red で証明済み）。
3.0.1 ⚠️ テストが「素通り」していないか疑う
・**テストが通ることと、テストが検証していることは別**である。次の 2 パターンは、
通ったまま（あるいは落ちたまま）何も守っていないテストになる。
・**① 期待値が既定値・初期値と同じ** — セットアップが効いていなくても通ってしまう。
**必ず「既定値とは異なる値」でも 1 ケース検証する**（例: 既定値 10000 の設定をテストするなら、
3000 を差し込んで 3000 が返ることを見る）。差し込みが効いていなければここで落ちる。
・**② 期待値を実行環境に依存させている** — `.env`・OS・時刻・ロケール等、実行環境で変わる値を
期待値に直書きしない。**テスト内で明示的に差し込む**（`Config::set()` 等）。環境依存の期待値は
「別のマシンでは落ちる」のではなく、**「書いた本人の環境でも最初から落ちていて、誰も気づかない」**
形で腐る（1.6 のベースライン失敗の山に埋もれる）。
・3.0 の「わざと壊して落ちることを確認する」は、後追いテストだけの作法ではなく
**セットアップが効いているかの確認**でもある。新規テストを書いたら必ず通す。
3.1 🔴 テスト作成（Red フェーズ）
・失敗する最小限のテストを書く
・1 つの特定の振る舞いに集中
・要件を明確に表現したテストにする
・テストが失敗することを確認
3.2 🟢 コード実装（Green フェーズ）
・最小限の本番コードを書く
・テストを通すことだけに集中
・テストコードは絶対に変更しない
・実装コードのみを変更してテストを通す
・過剰な設計を避ける
・テストが通ることを確認
3.3 🔵 細かくコミット（Blue フェーズ）
・テストがグリーンのままリファクタリング
・コードの品質と可読性を向上
・重複を削除
・意味のある小さなコミットを、明確なメッセージで行う

## 4. 📋 test.csv 連携

・test.csv には **人間（手動）が行うテストのみ** を書く（rules/modes/create-test.md）。**自動テストでカバーした項目は test.csv に追加しない**（テストコードが自動テストの仕様）
・実装した機能に、自動テストでカバーできない確認（目視・実機・メール実受信・外部サービス等）があれば、その項目だけを test.csv に追加する
・test.csv の既存項目（手動テスト）の期待値が今回の仕様・実装と矛盾する場合は、ユーザーに報告する
・旧運用（自動化分を「自動テスト」と記載）の項目が残っている場合は、ユーザー確認のうえ整理（削除）してよい
