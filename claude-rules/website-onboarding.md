# website テンプレート 運用ガイド（統括 / 開発 / 進捗チェックシート）

制作案件を **AI と 2 つのセッションで回す**ための手引き。
はじめて触るスタッフが、この 1 枚だけ読めば動かせることを目指しています。

- 対象：`claude-rules/website/` テンプレートを配ったプロジェクト
- 前提：Claude Code（CLI）が使えること
- ルールの原典：`CLAUDE.md` / `rules/modes/director.md` / `rules/modes/developer.md` / `rules/modes/build-progress.md`
  （このガイドは要約です。**食い違ったら原典が正**）

---

## 1. 3 行でいうと

1. **ウィンドウを 2 つ開く**（以下このガイドでは「**窓**」と呼びます）。片方が **統括（`/director`）**、もう片方が **開発（`/dev`）**。
2. 統括が「何を作るか」を決めて **委任カード**（`documents/handoff.md`）に書き、開発がそれを実装して同じカードに報告を返す。
3. 案件全体の残工程は **チェックシート**（`documents/build-checklist.md`）で管理し、`/progress` で「次の一手」を出す。

> 🚨 **2 つのセッションは互いの会話が見えません。** ファイルに書いていないことは、相手にとって存在しません。

---

## 2. 全体像

```
   あなた（人間）
        │  方針・判断・素材                     ← 話しかける先は原則こちら
        ▼
┌──────────────────┐        委任カード H-NNN        ┌──────────────────┐
│  統括 /director   │ ──────────────────────────→ │   開発 /dev       │
│  決める・渡す      │      documents/handoff.md     │   実装する         │
│  検品する・commit  │ ←────────────────────────── │   報告する         │
└──────────────────┘        報告・質問                └──────────────────┘
        │                                                   ▲
        │ 進捗を更新                                          │ 目の前の実装の直しは
        ▼                                                   │ 直接聞いてOK
 documents/build-checklist.md（工程 B-NNN）  ─────────────────┘
```

### 役割

| | 統括（ディレクター） | 開発（デベロッパー） |
|---|---|---|
| 起動 | `/director` | `/dev` |
| ひとこと | **方針の窓口**。全体を見て決める人 | **実装担当**。手を動かす人 |
| やること | 優先順位・スコープ・公開判断・見積もり／委任カード起票／検品／コミット／報告 | HTML・SCSS・JS・PHP を書く／確認する／報告する |
| **やらないこと** | 🚨 **実装しない**（制作ファイルを触らない） | 🚨 **コミットしない**（`git add` / `commit` / `push` を打たない） |
| 動作ルール | `rules/modes/director.md` | `rules/modes/developer.md` |

### どっちに話しかける？

| 話したいこと | 相手 |
|---|---|
| 方針・優先順位・スコープ・公開してよいか・見積もり | **統括** |
| 「この画像を差し替えて」「ここの余白を詰めて」など目の前の実装の直し | **開発** |
| 迷ったら | **統括** |

## 3. はじめかた（初回 5 分）

### Step 1. プロジェクトの設定を書く（初回だけ）

`project-config.md` の **`（記入。…）` が残っている行をすべて埋める**。とくに以下：

- **エージェント構成** … 2 セッション構成を `使う` / `使わない`、開発セッションの開き方、統括セッションの開き方
- **URL・確認環境** … ローカル / ステージング / 本番
- **環境** … OS、SCSS 自動コンパイルの有無

> 🚨 ID・パスワード・API キーの**実値は絶対に書かない**（「あり／なし」と保管場所まで）。

> **1 人で全部やりたい場合**は「2 セッション構成を使うか」に `使わない` と書く。すると `/director` `/dev` の役割分担・コミット制限はすべて無効になり、従来どおり 1 セッションで回せます。

### Step 2. 統括のウィンドウを開く

```
（プロジェクトのフォルダで）
claude
/director
```

統括は起動すると**環境点検**を行い、足りないものを教えてくれます（点検 7 項目）。

| # | 見るもの |
|---|---|
| 1 | 開発セッションが開いているか（**あなたに聞いてきます**。仕組みでは検知しません） |
| 2 | `project-config.md` が記入済みか |
| 3 | `Design.md` があるか |
| 4 | `documents/build-checklist.md` が案件用に展開されているか |
| 5 | `documents/company-facts.md` に確定事実が入っているか |
| 6 | SCSS 自動コンパイル環境 |
| 7 | 統括が拾うカード（`質問中` / `レビュー待ち`）があるか |

全部 OK なら 1 行で報告、NG があるときだけ詳しく出ます。

### Step 3. 開発のウィンドウを開く

**別のターミナル／別のタブ**でもう 1 つ起動します。

```
（同じプロジェクトのフォルダで）
claude
/dev
```

開発は起動すると `documents/handoff.md` を読み、自分が拾うカード（`未着手` / `着手中` / `差戻し` で `担当` が自分のもの）を 1 行で教えてくれます。

> **開発を 2 枚以上開くこともできます**（上限 3）。その場合は `/dev dev-A` `/dev dev-B` のように**名前を付けて**開きます。引数なしの `/dev` は `dev-A` です。どのカードをどの窓に渡すかは統括が `担当:` で決めるので、あなたが振り分ける必要はありません。→ 5.7

> 起動時に読むのは `handoff.md` だけではありません。`project-config.md`（確認URL・コンパイル方針・ディレクトリ構成）と、**見た目に触れる作業なら `Design.md`** も読みます。そのため確認URLなどを毎回聞いてくることはありません。

> 開発セッションを開き忘れていても大丈夫です。統括が「開いてください」と手順つきで促します。

## 4. 1 日の流れ（典型的な 1 往復）

| # | どこで | 何が起きるか |
|---|---|---|
| 1 | 統括 | あなたが「トップに導線を足したい」と相談する |
| 2 | 統括 | スコープ・優先度を決め、**委任カード `H-003`** を `documents/handoff.md` に起票（状態 `未着手`） |
| 3 | 統括 | 🚨 **「開発セッションに切り替えて『handoff を読んで』と伝えてください」** と頼まれる ← **これがあなたの仕事** |
| 4 | 開発 | あなたが開発ウィンドウで「handoff を読んで」と言う → 着手（状態 `着手中`） |
| 5 | 開発 | 実装 → 状態 `レビュー待ち` にして**報告 8 項目**（→ 5.3）をカードに追記 |
| 6 | 開発 | 🚨 「統括セッションに切り替えて『検品して』と伝えてください」 ← **またあなたの仕事** |
| 7 | 統括 | 受け入れ条件を自分で確認 → OK なら `/commit-pipeline` でコミット → 状態 `クローズ` |
| 8 | 統括 | `documents/build-checklist.md` の `B-NNN` を更新し、次の一手を提示 |

> 🚨 **人間が唯一の通知経路です。** ファイルに書いただけでは相手のウィンドウは気づきません。
> 切り替えを頼まれたら、必ずもう一方の窓で伝えてください。伝えないと**両方が相手待ちで止まります**。

## 5. 委任台帳 `documents/handoff.md`

統括と開発の**受け渡しはこのファイルだけが正**。パスは固定で、変更できません（両者が別ファイルを見る事故を防ぐため）。

### 5.1 状態は 6 つだけ

| 状態 | 誰が設定する | 意味 |
|---|---|---|
| `未着手` | **統括** | 起票した／**次ラウンドの指示を書いた**。開発が着手できる |
| `着手中` | **開発** | 実装している |
| `質問中` | **開発** | 判断が要る。統括の回答待ち |
| `レビュー待ち` | **開発** | 実装が終わった（**まだコミットしていない**）。統括の検品待ち |
| `差戻し` | **統括** | 検品で条件未達。開発が直す |
| `クローズ` | **統括** | 検品を通り、受け入れ条件を満たし、**統括がコミットまで済ませた** |

- **統括が拾う** ＝ `質問中` `レビュー待ち`
- **開発が拾う** ＝ `未着手` `着手中` `差戻し`
- 🚨 **各状態を設定できるのは、上の表で決まった側だけ**（相手が設定した状態を、別の状態へ勝手に書き換えない）
- **ただし持ち場が移る遷移は、受け取った側が次の状態を設定する**（`質問中` → 統括が回答して `未着手` へ／`レビュー待ち` → 統括が `クローズ` か `差戻し` へ）

```
統括: 未着手 ──→ 開発: 着手中 ──→ 開発: レビュー待ち ──→ 統括: クローズ
                    │                      │
                    ├──→ 開発: 質問中       ├──→ 統括: 差戻し ──→ 開発: 着手中
                    │        └──→ 統括が回答して 未着手 へ戻す
                    │                      └──→ 統括: 未着手（合格だが、まだ途中
                    │                             ＝次ラウンドへ）
```

> 🚨 **`差戻し` と `未着手` を混ぜない**（統括が検品したあと）。**`差戻し`** ＝ 不合格だからやり直す。
> **`未着手`** ＝ 合格だが**まだ途中**なので、次に何をするかを追記して返す。
> 1ページを何度か往復する案件ではこの2つが並ぶので、混ぜると開発が「直すのか進むのか」を判断できません。

### 5.2 カードの形

```markdown
### H-003 トップページに下層への導線を追加

- 状態: 未着手
- 担当: dev-A
- 優先度: 1
- 依存: なし
- 更新: 2026-09-10 14:30 / director

**やること**（1行）
**対象**（必須）
**受け入れ条件**（必須・完了を機械で判定できる形で）
**触らない範囲**（必須）
**使う確定事実**（コンテンツを書くとき必須）
**デザインの根拠**（見た目を触るとき必須）
**読むルール**
**確認環境**
```

- **必須 4 項目**＝ やること / 対象 / **受け入れ条件** / **触らない範囲**
  - 🚨 省略しても開発は**推測で補いません**。原則 `質問中` にして統括へ返すため、**作業がそこで止まります**
  - 例外は `触らない範囲` だけ。無い場合は「**カードの対象ファイル以外は触らない**」と解釈して進みます
- `- 状態:` `- 優先度:` `- 依存:` `- 更新:` の 4 行は**固定形式**（grep で拾うため、見出しに埋め込まない）
- **1 カード＝1 論点**。ページ 5 枚をまとめない（検品も差戻しもできなくなる）
- 開発は「**`依存` が解決済みで、最も `優先度` が高いカード**」から着手します。**順番は聞いてきません**

### 5.3 開発が返す「報告 8 項目」

実装が終わると、開発は状態を `レビュー待ち` にして、**同じカードの下**に次の 8 項目を追記します。

| # | 項目 | 中身 |
|---|---|---|
| 1 | やったこと | 1行 |
| 2 | 変更ファイル | パスと増減行数、何をしたか |
| 3 | 受け入れ条件 | 1つずつ `[x]` と、その根拠 |
| 4 | **確認できていないこと** | 🚨 **空にしない**。全部確認したなら「全部確認した」と書く |
| 5 | 質問 | 無ければ「なし」 |
| 6 | 範囲外の気づき（直していない） | **直さずに残すのが正解**。重いものは `pending-issues.md` へ |
| 7 | **コミット材料** | 🚨 **空にしない**。変更の意図・コミットメッセージ案・レビューで見てほしい点 |
| 8 | **統括の前提と食い違った点** | 統括の指摘が実測と合わなかったとき、**合わせに行かず**測定条件つきでここに書く（無ければ「なし」）。存在しない不具合を直すと別の不具合が生まれます |

> 1 ファイル・数行の修正には**軽量版**があります。統括がカードに `- 報告: 軽量` と書いたときだけ、変更ファイル／確認できていないこと／コミット材料／食い違った点の 4 つで返せます。

> 4 と 7 が要になります。4 はあなたと統括にとって**最後の関門**、7 は「作った本人が一番よく分かっている」知識を、コミットを打つ統括へ引き継ぐための欄です。

> 🚨 **「確認した」の根拠に、件数だけを書かないでください。** 「0 件でした」「✅ 12 項目」は、**本当に無い／壊れている／取りに行けなかった**の3つに同じ値を返します。**1件以上なら実際の値を1つ**（画像なら開いたファイル名と見た中身）、**0 件なら「取りに行けていた根拠」**（見た URL・対象範囲と絞り込み条件・権限・取得元が在るか）を添えてください。詳しくは `rules/modes/developer.md` §6.1。

### 5.4 書き込むときの約束（両者共通）

1. **書く直前に読み直す**（相手が更新しているかも）
2. **対象のカードだけを直す**。ファイル全体を書き戻さない
3. 読んだ状態が**想定と違ったら、書かずに止まる**
4. `更新` 行を自分の名前と日時にする

### 5.5 開発からの質問は「二段構え」で返ってくる

開発が `質問中` で返した質問を、統括は**そのままあなたに流しません**。

- **第 1 段**：SSOT を読めば分かること・過去に決まったこと・スコープの解釈 → **統括が答えて再委任**
- **第 2 段**：本当にあなたの判断が要るものだけ、**推奨と理由を添えて選択肢で**上がってくる

### 5.6 開発が「直接指示」を受けたとき

開発ウィンドウであなたが直接お願いした内容も、**必ずカードに残ります**。

| あなたの指示 | 開発の扱い |
|---|---|
| 着手中カード内の微調整（画像・余白・リンク先） | その場で対応し、カードの `**ユーザー直接指示**` 欄に追記 |
| カード外の新しい作業 | 開発が 1 枚なら**自分で新しいカードを起票**して対応。**2 枚以上なら起票せず、`handoff.md` の「統括への依頼」節に 1 行書いて統括のカード化を待つ**（→ 5.7） |
| 受け入れ条件・触らない範囲が変わる指示 | **直さず** `質問中` にして統括へ返す |

### 5.7 開発が 2 枚以上あるとき（1 対 n）

統括 1 枚に対して開発を最大 3 枚まで開けます。**カードは統括が `担当:` で割り当て、開発は自分の担当だけを拾います**（同じカードを 2 人が取る事故を構造で消しています）。

干渉を防ぐ「交通整理」は統括の仕事で、3 種類を見ています：

| 種類 | 統括がどうするか |
|---|---|
| 同じファイルを触る 2 枚 | 同時に出さない（`依存` で直列化） |
| `Design.md`・`company-facts.md`・共通 SCSS 等の**共有基盤**に触る 1 枚 | 単独で出し、終わるまで他を出さない |
| 同じ画面の別機能など**意味の干渉** | 質問が複数来たら矛盾しないよう一括で答える |

開発が 2 枚以上のときは、**古いカード（`担当` 行が無いもの）は `dev-A` 扱い**になります。2 枚目を開く前に、統括が既存カードへ `担当` を補完します（統括の環境点検に入っています）。

統括は、**開発からの戻り（質問・レビュー待ち）を自分の作業より先に返します**。あなたが「handoff を読んで」と伝えた時点で作業を中断して対応するので、遠慮なく伝えてください。逆に伝え忘れると、統括は区切りごとに `handoff.md` を読み直して拾いますが、それまで待たせることになります。

**あなたの仕事は中継が枚数分増えること**です。統括は報告の最後に「**窓別の伝言**」（dev-A には○○・dev-B は待機）を表で出すので、それを見て各窓に伝えてください。

### 5.8 台帳が長くなったら（退避）

**`クローズ` が 50 件を超えた** か、**ファイルが 1000 行を超えた**ら、`クローズ` 済みのカードだけを古い順に `documents/handoff-archive.md` へ移します（削除しない）。
`未着手` `着手中` `質問中` `レビュー待ち` `差戻し` は、何件あっても退避しません。

## 6. 進捗チェックシート `documents/build-checklist.md`

「委任台帳＝いま誰が何を実装しているか」に対して、こちらは **案件全体で完成までに何が残っているか**の正本です。
回し方は `/progress`（ルールは `rules/modes/build-progress.md`）。

### 6.1 なぜ必要か

サイトが完成しない理由の大半は AI の手が止まったからではなく、**決め事・原稿・素材・アカウントが揃わないから**。
誰かが「次にこれが要る」と言い続けないと止まります。**進捗は会話ではなくファイルに置きます。**

### 6.2 使い始め（ひな形 → 台帳）

配布時点の中身は **ひな形（標準工程のカタログ）で、番号が付いていません**。案件に合わせて育てます。

1. **展開**：ページ数・LP 本数など複数になるものは、実体の数だけ行を起こす（例：「各ページ実装」→ `B-021 トップ` `B-022 会社概要` …）
2. **追加**：ひな形に無い案件固有の工程は、提案・合意のうえ足す（🚨 **ひな形に無い＝やらなくてよい、ではない**）
3. **対象外化**：当てはまらない項目は**削らずに** `[-]` ＋ 理由
4. ドラフトを見せて**合意を得てから確定**（勝手に作らない）

### 6.3 記法

```markdown
- [ ] B-012 ｜ 会社概要ページの実装 ｜ 担当: AI ｜ 依存: B-005 ｜ 更新: 2026-09-01
- [?] B-007 ｜ 施工事例の写真3点 ｜ 担当: ユーザー ｜ 依頼先: クライアント ｜ 更新: 2026-08-25 ｜ 督促: 2
```

| 記号 | 意味 |
|---|---|
| `[ ]` | 未着手 |
| `[~]` | 進行中 |
| `[?]` | **待ち**（誰の何待ちかを必ず書く。`督促:` カウンタを持つ） |
| `[x]` | 完了（**確認できたものだけ**） |
| `[-]` | 閉じた（対象外・見送り。**理由必須**、見送り合意なら `PI-NNN` を併記） |

- 担当は**必ず一者**（`AI` か `ユーザー`）。クライアント作業は担当 `ユーザー` ＋ `依頼先:` に実作業者
- 番号は「既存の最大番号＋1」。**欠番を再利用しない・付けた番号を変えない**
- `[~]` `[?]` `[-]` は Markdown 標準のチェックボックスではありません（Notion でも素のテキストとして表示されます）

### 6.4 標準工程（フェーズ 0〜8）

> 🚨 **フェーズ 0〜2 は「何を載せるか」を決める段で、進め方の手順があります**（`rules/modes/content-planning.md`）。
> 相談を受けたらまずここを通します。ポイントは3つ：**①手元の資料（旧サイト・パンフレット）を見る前に「本来あるべきもの」を出す**
> （資料から始めると、もともと無い情報は候補にすら上がりません）／**②足りない情報は `documents/client-questions.md` にまとめ、
> あなたが聞ける形でお渡しします**（何を聞くか・なぜ必要か・回答欄／必須とあるとよいを分けます）／**③サイトマップの合意を

> **載せる内容を決めるのはクライアント**で、AI が出す「読者の不安」「追加・不要の提案」はすべて仮説です。

**フェーズ 7 へ進める条件と、指摘が出たときの扱い**

- **フェーズ 0〜6 の該当項目が `[x]` または `[-]` になったら 7 へ進む。** 台帳の**全項目**が片付くのを待たない（フェーズ 7・8 自体が台帳の項目なので、待つと永久に進めません）
- **A〜I で指摘が出たら**：フェーズ 7 の項目は `[~]` のままにし、**指摘ごとに修正用の `B-NNN` を起こす**。修正後に該当チェックを再実施して、**初めて `[x]`**

### 6.5 促し方（このモードの本体）

- 提示は **1 回あたり合計 3 件まで**（「AI がやること」「お願いしたいこと」「決めてほしいこと」に分けて）
- `[?]`（待ち）を再掲するたび `督促:` が **+1**。**2 以上の項目は報告の冒頭**に出ます。動いたら 0 に戻る
- 促すときは**代案とセット**（①いただく ②仮画像で組む ③後回し）
- 🚨 **仮置きへの切り替え・見送りへの変更は、あなたの明示合意が必要**（AI の判断で待ちを畳みません）
- 🚨 **期限・スケジュールは AI が決めません**。示すのは「何が止まっているか」まで
- 🚨 **台帳は 1 件終わるごとに更新**します（まとめて後で直さない）。古い状態のまま放置すると、もう一方の窓が**それを正として動きます**

### 6.6 「完了 `[x]`」にしてよい根拠

| 種類 | 根拠 |
|---|---|
| 実装 | ファイルが実在し、ブラウザで表示を確認した |
| 反映（デプロイ） | **公開 URL を実際に取得して確認した**（「アップした」と「公開URLで見えた」は別） |
| 素材・原稿 | 受領した実物を確認した（「送ると言われた」は `[?]` のまま） |
| ユーザー判断 | **明示的な回答**があった（沈黙・話題の移動を承認と解釈しない） |

### 6.8 1 プロジェクトに納品単位が複数あるとき（LP を都度制作 等）

## 7. 正本（SSOT）と記録先・番号の使い分け

**主要な正本（SSOT）**

| ファイル | 何の正本か | 番号 | 更新するのは |
|---|---|---|---|
| `Design.md` | **デザイン**（色・タイポ・余白・コンポーネント） | — | 統括 |
| `documents/company-facts.md` | **確定事実**（社名・住所・料金・実績） | `F-NNN` | 統括 |
| `documents/build-checklist.md` | **進捗**（完成までに片付ける工程） | `B-NNN` | 統括 |
| `documents/handoff.md` | **受け渡し**（いま何を誰が実装しているか） | `H-NNN` | 統括・開発（持ち場ごと） |

**補助の記録先**（正本ではないが、取りこぼさないための置き場）

| ファイル | 何を書くか | 番号 | 更新するのは |
|---|---|---|---|
| `documents/pending-issues.md` | 判断が要る／今回は着手しない課題 | `PI-NNN` | 両方（記録は常に可） |
| `documents/rule-improvements.md` | ルールへの気づき・改善案 | `RI-NNN` | 両方 |

> 同じ作業を `build-checklist` と `pending-issues` の両方に載せない。見送ると決めたら `[-]` ＋ `PI-NNN` を書き、以後の正本は PI 側。

**ルール自体がおかしいと思ったら、知らせる経路があります。** この `CLAUDE.md`・`rules/` は、はなさか側の共通テンプレートから配布されたもの。「実態とずれている／危険／抜けている」と気づいたら `rule-improvements.md` に `RI-NNN` で記録し、**このプロジェクト固有でなく他の案件でも効く話**なら `[テンプレ還元]` と印を付けて次で送ります。

```bash
bash bin/rule-report.sh --subject "[<ファイル名>] 要旨" "（対象／現場で何が起きたか／変更案／なぜ）"
```

- **投函専用**の経路です（受信箱は無く、返事は返りません）。投げたら記録して先に進んでください。
- 使っているテンプレの**版は自動で載る**ので書かなくて構いません。受け取った側が「その指摘はもう直っているか」を版で判定します。
- **送れなければ失敗として終わります**（終了コード 1）。その場合は `rule-improvements.md` に残したまま、社長に「ルール通知の受け口を有効にしてほしい」と伝えてください（送ったことにしない）。

**逆に、新しい版のルールはこちらから取りに来ます。** テンプレートは改善され続けるので、統括が起動時の点検で「新しい版が出ています」と気づき、**変更点を添えて更新してよいか聞きます**。

- 確認だけなら**何も書き換えません**（`bash bin/rules-update.sh`）。**適用はあなたの承認後**＝ルールが変わると作業の前提が変わるため、作業の区切りで行います。
  - 🚨 **変更点の中に `[🚨重要]` で始まる行があれば、それは「適用の前に済ませる手当て」の指示です。** 手当てをしないと適用が通らない版もあります（統括が気づいて一緒に伝えますが、一覧の下のほうに沈んで見落とされることがあるので、ご承認のときに一緒に見てください）。
- **案件の記録は上書きされません**（`documents/`・`project-config.md`・`Design.md`・あなたの成果物）。上書き前の退避も必ず作ります。
  - 🚨 **上書きされない代わりに、テンプレート側で増えた記入欄は自動では現れません。** 適用のあとに `project-config.md` の見出しを控え（`.claude/rules-base.tar.gz`）と突き合わせ、増えた節は自分で足してください（手順は `rules/modes/rules-update.md` §4）。
- 🚨 **配布されたファイル（`CLAUDE.md`・`rules/`・`.claude/commands/` 等）には書き足さないでください。** 更新で上書きされ、書き足した行は消えます。この案件だけのコマンド・ルールは、ファイルを新しく作り、一覧は `project-config.md`「固有の追加」に書きます。書き足しがあると、更新の確認で名指しされ、適用は止まります。
- 手順は `rules/modes/rules-update.md`（エージェント向け）。初回の受け取り設定（`.env` の3行）は社長側で用意します。

## 8. コマンド早見表

> **下の「窓」は 2 セッション構成を `使う` 場合の話です。** `使わない`（1 セッション運用）を選んだ場合は、統括／開発の窓分けも、git 系コマンドの統括限定ガードも**適用されません**。

| コマンド | 窓 | 何をする |
|---|---|---|
| `/director` | 統括 | 統括として起動。環境点検 → 方針・委任・検品・報告 |
| `/dev` | 開発 | 開発として起動。`handoff.md` を読んで実装。`/dev dev-B` のように名前を付けると 2 枚目以降になる（→ 5.7） |
| `/progress` | 統括（役割ルールによる） | チェックシートを読み、**次の一手を 3 件まで**提示 |
| `/staging` | **統括（コマンドにガード行あり）** | 個別パスでステージング（`git add .` は使わない） |
| `/commit` | **統括（ガード行あり）** | ステージ済み差分を検査し、日本語のコミットメッセージを**提案する**（🚨 **コミット自体は実行しません**） |
| `/commit-pipeline` | **統括（ガード行あり）** | ステージング → 差分確認 → `Design.md` 整合確認 → **Codex クロスレビュー（原則実施。使えないときだけ Claude 単独）** → 承認後に**コミット** → リファクタ提案 |
| `/refactor` | ガード行なし（提案は統括／実施は開発） | ステージング差分からリファクタ候補を**列挙**する。承認後の制作ファイル変更は `H-NNN` で開発へ委任 |
| `/hana-memo` | 統括（役割ルールによる＝外部への書き込みは統括） | 外部のプロジェクトメモを更新。🚨 **POST は追記ではなく全置換**。`project_id` を確認し、GET →既存内容と統合→変更内容を提示→**承認**→POST の順を厳守 |
| `/cleanup-permissions` | 指定なし | 権限設定の整理 |

> 🚨 **git 系（`/staging` `/commit` `/commit-pipeline`）は、2 セッション構成では統括セッションで実行**します（この 3 つはコマンド本体にその旨のガード行が入っています）。
> 2 つの窓が同時に `git add` すると index が壊れます。**`git push` は AI が行いません**（人が手動で）。
> なお `/progress` と `/hana-memo` にガード行はありません。統括の担当なのは「進捗 SSOT の更新」「外部への書き込み」がモードのルールで統括の持ち場と決まっているためです。

## 9. やってはいけないこと（抜粋）

### 統括

- ❌ 制作ファイル（HTML/PHP/SCSS/JS/画像）を自分で編集する → 委任カードにする
- ❌ 必須 4 項目を省いたカードを書く（開発はあなたの会話を見ていません）
- ❌ 開発から来た質問をそのままユーザーへ流す → 推奨と理由を添える
- ❌ 「✅ と書いてあるから ✅」で検品を済ませる → 実物を見る

### 開発

- ❌ `git add` / `git commit` / `git push` を打つ
- ❌ `company-facts.md` に無い**事実を作る**（→ `【要確認】` を残して質問で返す）
- ❌ `Design.md` に無い**色・余白・ブレークポイントを足す**
- ❌ カードの**範囲を広げる**（気づきは直さず「範囲外の気づき」に書く）
- ❌ 不明点で**全部止める**（依存しない部分は進め、依存する分だけ `質問中`）
- ❌ 統括の指摘が実測と合わないのに**合わせに行く**（測定条件を添えて差し戻す→ 5.3 の 8 番）
- ❌ 開発が 2 枚以上のとき、**他の開発の持ち場や共有ファイル**（`project-config.md`「共有ファイルの所有者」表）を触る

### 人間（あなた）

- ❌ 切り替えの声かけを忘れる → 両方が相手待ちで止まります
- ❌ 統括の窓で細かい実装を頼み続ける → 全体を見る役が実装の詳細で埋まります
- ❌ 実値のパスワード・API キーを台帳やリポジトリに書く
- ❌ `CLAUDE.md` の表などの配布ファイルに行を書き足す → ルールの更新で消えます（`project-config.md`「固有の追加」へ）

## 10. よくある質問

**Q. ウィンドウを 2 つ開くのが面倒です。**
A. `project-config.md` の「2 セッション構成を使うか」に `使わない` と書けば、1 セッションで全部やる従来の運用に戻ります。

**Q. 開発セッションを閉じてしまいました。**
A. 問題ありません。状態はすべて `documents/handoff.md` にあります。開き直して `/dev` → 「handoff を読んで」で再開できます。

**Q. 統括は開発の窓が開いているか分かりますか？**
A. 分かりません。**あなたに聞いてきます**。仕組みで追わない設計です。

**Q. 開発に直接お願いしてもいいですか？**
A. 目の前の実装の直し（画像・余白・リンク先）は OK。方針・スコープ・事実に関わることは統括へ。

**Q. `H-NNN` と `B-NNN` の違いは？**
A. `B-NNN` ＝ **完成までに残っている工程**（案件の地図）。`H-NNN` ＝ **いま開発に渡している 1 件の作業**（受け渡しの伝票）。1 つの `B-NNN` を進めるために `H-NNN` を 1〜数枚切る、という関係です。

**Q. 同じファイルを両方が触ってしまいませんか？**
A. 統括は制作ファイルを触らないのが原則です。例外は「**1 ファイル・数行で、判断を伴わない**明らかな typo やリンク切れ」だけ。その場合も ①触る前に「対象ファイルを含む `着手中` のカードが無いこと」を確認し、②**触ったら必ず `handoff.md` に記録**します（開発が知らないまま同じ場所を触ると壊れるため）。それ以外はすべて委任カードで開発へ渡します。
