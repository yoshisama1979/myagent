# テンプレート整備バックログ

`claude-rules/` テンプレート自体の未完課題（宿題）の置き場。
**配布物（各テンプレートの `documents/pending-issues.md`）には入れない** — コピー先プロジェクトが他人の課題を初期状態で抱えないため（2026-07-02 に website/documents/pending-issues.md から移設）。

通し番号 `TB-NNN`。解決したら削除する。

> **現場からの提案の受け皿でもある**：開発エージェントが `rule-kaizen` 宛に送ってきた（または `rule-improvements.md` の `[テンプレ還元]` 印で持ち帰った）テンプレ改善提案のうち、**その場で反映しない・要検討のもの**をここに `TB-NNN` で起票する。選別〜反映の流れは [README.md](README.md)「テンプレート自体の育て方」③参照（反映は社長承認後）。

### TB-001: 解析データの取得権限を開発エージェントへ委譲するか〔website / websystem 共通〕

> 旧 TB-001（オンページ監査のツール化）・TB-002（GA4/GSC 連携手順）・TB-004（Before/After 記録様式）を統合。
> 旧 TB-003（業種別テンプレ）は 2026-08-17 の棚卸しでクローズ（下記）。

- **経緯**: 3件はいずれも「**配布先の開発エージェントが自分で監査・計測する**」前提（2026-07-02 時点）で起票された。その後 **HP分析ループ（解析エージェント）が中央で回る体制**が整い、前提が入れ替わった。実体はすべて はなさか側に存在する：
  - オンページ監査 → `bin/hp-audit.sh`（T-001・稼働中。依存は curl と python3 のみ＝**認証情報を持たない**）
  - アクセス解析・検索データ → `bin/gsc-fetch.py` / `ga4-fetch.py` / `clarity-fetch.py`（稼働中。**サービスアカウントJSON＋BigQuery＋専用venv が必要**）
  - 効果検証 → `bin/hp-diff.py`（T-009・稼働中。標準ライブラリのみ）
- **決定（社長判断 2026-08-17）**: **判断＝解析エージェント／実行＝開発エージェント**の棲み分けを現状の正とする。解析基盤は中央に集約したままにし、**開発側は計測基盤を作らない・認証情報を持たない**。必要な一次情報は mailbox（対の分析ループがあれば）または社長経由で**要求する**。この棲み分けは `website/rules/modes/seo-operation.md` Step 2 に明記済み（2026-08-17 反映）。
- **未対応（＝この起票が残る理由）**: **将来的には開発エージェント側にもデータ取得権限を与えた方がやり取りがスムーズになる**（社長の方向性）。ただし時期は前倒しで決めず、**実際のやり取りの挙動を見ながら判断する**。
- **委譲を検討するトリガー（観察すべき症状）**:
  - 開発側が一次情報を要求 → 解析側が返す、の往復で**着手が実際に止まっている**（要求が習慣化し、待ち時間が施策のボトルネックになっている）
  - 対の分析ループが**付いていない** website 案件で、暫定の `curl`/`grep` が常態化している
  - 開発側が「解析ループの提案待ち」で受け身になり、内部起点の改善提案が出なくなっている
- **委譲するときの設計論点（先に決めること）**:
  - **認証情報を配らずに委譲する形**を採る（拠点PCへ SA JSON を配らない）。候補＝VPS 側にトークン認証の読み取り専用エンドポイントを立て、開発側はそれを叩く（mailbox と同じ構図）
  - **認証不要のツール（`hp-audit.sh` / `hp-diff.py`）は先行して同梱できる**が、配ると**版ズレ管理の対象がルールに加えてコードにも増える**（テンプレ本体と同じ問題がコードで再発する）。同梱するなら更新の配布手順とセットで決める
    - **2026-09-11 追記：この前提は変わった。** 配布が `bin/distribute-rules.py` になり、版（`.claude/rules-version`）が刻まれ、配布先が `data/rules-distribution.md` に記録されるようになった＝**コードを同梱しても「どの案件がどの版を持っているか」は追える**。`bin/rule-report.sh` が最初の同梱コードで、既にこの仕組みに乗っている。残る論点は「更新を配り直す手間を誰がいつ払うか」だけ
- **クローズした旧 TB-003（業種別の訴求・SEOテンプレ）**: 業種軸の定型より、`data/hp-loop/win-patterns.md`（**効果検証済みの型**を全サイト横断で貯める勝ちパターン共有ライブラリ・反証も記録する運用）の方が実測に基づき信頼できる。受託が特定業種に偏り、同じ提案を繰り返し組み直している実感が出てから再起票する。

### TB-008: 見積もりルール新設にともなう2つの先送り判断〔website / 共通〕

- **未対応**:

- **今後の判断ポイント**: 1 は website 案件で見積もり改定が2回以上発生し、原本参照だけで足りるかが観測できた時点。2 は **見積もり以外の文脈で同じ誤読が再発したら**、汎用の置き場（website は受け皿が無い＝TB-007 の「汎用の開発規約の置き場を新設するか」と合わせて判断）へ一本化する。

### TB-015: `/commit-pipeline` のリファクタ段が「作業ツリー」を見ている（`git diff HEAD~1`）〔website / websystem 共通〕

- **対象（4ファイル）**:

  - myagent 側 `.claude/commands/commit-pipeline.md`（テンプレ外・同じ誤り）

### TB-019: 🚨 `bin/rules-update.sh` が実行中に自分自身を上書きして壊れる（exit 127）〔common・最優先〕

- **経緯**: 2026-09-18、`rr-toyopet-lp`（website@2026-09-18/c63ba9b00332）から報告。現場の実測＝Windows 11 / Git Bash（bash 5.x）で `bash bin/rules-update.sh --apply` を実行し、変更点の一覧までは正常に出たあと `bin/rules-update.sh: line 272: =: command not found` で exit 127。停止後に見るとスクリプト自身が旧版（288行）から新版（583行）へ置き換わっていた（新版の272行目は `fi` の1語でエラー内容と一致しない）。
- **原因（推測ではなく bash の仕様）**: bash はスクリプトを**バイトオフセットで逐次読み込む**。実行中のスクリプト自身を書き換えると、以降の読み取り位置が新しい中身の別の場所を指し、行の途中から実行される。288→583行と伸びたため、ずれた先が `= "…"` のような断片になった。
- **何が残るか（これが厄介）**: 中断時点で**できていた**＝退避 `.claude/rules-backup/<日時>.tar.gz`・ルール層の上書き・`.claude/rules-keep`。**できていなかった**＝`.claude/rules-version`（版の刻印）と `.claude/rules-base.tar.gz`（控え）。🚨 **「適用は実質終わっているのに版も控えも無い」**状態が残り、以後ずっと `--force` を要求される。`rules-update.md` §4 が約束するロールバック（書いた分を退避から戻して止まる）も**働かない**。
- **2026-11-01 に直した（スクリプト側）**: 本体の処理全体を **`main() { … }`** に入れ、末尾を **`main "$@"; exit`**（同じ行）にした。bash は**関数定義の本体をまとめて読んでから**実行するので、中身は最初の1回でメモリに載り、途中でファイルが差し替わっても影響を受けない。
  - 🚨 **中身は字下げしていない**（終端が行頭でなければならないヒアドキュメントが3つあり、字下げすると壊れる）。理由はスクリプト冒頭のコメントに書いた。
  - 🚨 **`main "$@"` と `exit` を別の行に置かないこと。** 別行だと、main が返ったあと bash が**差し替わったファイルの古い位置**から次の行を読もうとする。
  - **採らなかった案**: `exec` で複製に引き継ぐ案（現場提案の1）。ROOT_DIR を `$0` から求めているので環境変数で引き渡す手当てが要り、一時ファイルの後片付けも増える。`main()` 化は一時ファイルも環境変数も要らない。
  - **採らなかった案**: 「版の刻印と控えの作成を上書きより先に行う」（現場提案の3）。🚨 **これは意図的にこの順序**（`rules-update.sh:495` に理由がある＝途中で失敗したときに「更新済み」と名乗らせない）。先に書くとその安全性が落ちる。`main()` 化で順序を変える必要がなくなった。
