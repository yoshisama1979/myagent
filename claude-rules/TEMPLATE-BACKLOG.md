# テンプレート整備バックログ

`claude-rules/` テンプレート自体の未完課題（宿題）の置き場。
**配布物（各テンプレートの `documents/pending-issues.md`）には入れない** — コピー先プロジェクトが他人の課題を初期状態で抱えないため（2026-07-02 に website/documents/pending-issues.md から移設）。

通し番号 `TB-NNN`。解決したら削除する。

> **現場からの提案の受け皿でもある**：開発エージェントが `rule-kaizen` 宛に送ってきた（または `rule-improvements.md` の `[テンプレ還元]` 印で持ち帰った）テンプレ改善提案のうち、**その場で反映しない・要検討のもの**をここに `TB-NNN` で起票する。選別〜反映の流れは [README.md](README.md)「テンプレート自体の育て方」③参照（反映は社長承認後）。

## オープン

### TB-001: オンページ監査の自動化（監査ツール化）〔website〕

- **経緯**: 運用・SEO評価で title/meta/OGP/構造化データ/見出し/alt 等のオンページ信号を見る必要がある。現状は `curl`/`grep` 等の手作業（暫定）で確認している。
- **未対応**: 監査を自動化するツール（例: 対象URLを渡すと SEO 信号と仮置き残存を一覧出力するスクリプト）が未整備。
- **今後の判断ポイント**: 暫定の手作業を恒久ツールに置き換えるか。対象が静的HTMLか PHP/CMS かで取得方法が変わる。`seo-operation.md` Step 2 の「監査ツール優先」を実体化する位置づけ。※はなさか側には `bin/hp-audit.sh`（T-001）が既にあり、テンプレ同梱化・配布方法が論点。

### TB-002: GA4 / Search Console 連携の具体手順〔website〕

- **経緯**: 改善の効果計測（検索順位・流入・コンバージョン）には GA4 / Search Console のデータが要る。`seo-operation.md` では「LLM で代替せず取得手段を要求する」と原則化したが、取得・参照の具体手順はルール化できていない。
- **未対応**: 計測データをどう取得し、評価サイクルにどう取り込むかの手順・フォーマットが未定義。
- **今後の判断ポイント**: API 連携で自動取得するか、ユーザーがエクスポートを渡す運用にするか。計測の最小セット（流入・CV・主要KW順位）を先に定義する。

### TB-003: 業種別の訴求・SEOテンプレ〔website〕

- **経緯**: 士業／飲食／製造／クリニック等、業種ごとに刺さる訴求軸・SEOキーワード・信頼要素が異なる。汎用ルールだけでは毎回ゼロから組み立てになる。
- **未対応**: 業種別の訴求・SEO定型テンプレが未整備。
- **今後の判断ポイント**: 受託の多い業種から優先して定型化するか。汎用ルール（`seo-operation.md`）の評価観点を業種別に肉付けする形が候補。

### TB-004: Before/After の効果記録フォーマット〔website〕

- **経緯**: 「使いながら育てる」改善サイクルでは、施策の前後で効果を振り返れることが重要。現状その記録様式が無い。
- **未対応**: 改善前後の指標（流入・CV・速度スコア等）を残す Before/After フォーマットが未定義。
- **今後の判断ポイント**: TB-002（計測連携）と一体で設計する。記録粒度（施策単位／月次）を先に決める。

### TB-006: Red を経ていないテストの担保（わざと壊して落ちることを確認する）〔websystem〕｜**差分案あり・社長承認待ち**

- **経緯（現場で実際に起きたこと）**: 2026-08-11、myagent 側で「無人ループが実行するツール 21本のうちテストが無い 13本」を 0本にする作業を実施し、**既存の実装に対して後から**回帰テスト8本（621項目）を書いた。全スイートが一発で緑になったが、**実装をわざと壊して「テストが落ちるか」を確かめたところ、4件が落ちなかった**＝アサーションが緩く、守るべき保護を外しても通り続ける状態だった。
  代表例：hp-compete の「監査に失敗しても hp-audit の JSON を読む」を `fetch_ok is False` だけで見ていたため、**JSON を捨てて自前のエラー dict を返す実装に変えても通ってしまう**（テストが将来にわたり嘘をつく）。`r.get("error") == "取得失敗"` まで見るよう締め直して解決。
- **claude-rules 側の現状（原文）**:
  - `rules/modes/tdd.md` 3.1「・テストが失敗することを確認」／`.claude/rules/testcode.md`「- テスト実行で失敗を確認（Red）」／`.claude/rules/frontend-test.md` §1「不具合の再現ケースをテストとして記述してから修正する」
    → **Red-first が明文化されている経路は、この問題が構造的に起きない**（テストを書いた時点で「落ちうること」を実証済み＝わざと壊すのと同じ保証）。
  - 一方、**Red が原理的に取れない経路が2つ明文化されている**：
    - `frontend-test.md` §2「新機能を実装したとき ・機能の主要なユースケース（正常系）と境界条件をテストする」＝**実装後に書く形**で Red の指示が無い
    - `frontend-test.md` §3「カバーされていない挙動を発見したら、リファクタ前にテストを追加する」＝**既存挙動を固定するテスト**（characterization test）なので Red が存在しない
  - 65ファイルを横断検索した結果、`mutation`／`わざと壊`／`全緑`／`落ちることを確認` に相当する記述は**1件も無い**。
- **変更案（本家1箇所＋参照2箇所。README 設計原則2「重複定義しない」に従う）**:
  - **本家** `rules/modes/tdd.md` の §3 に `3.0` を新設（3.1 の直前）。全文は下記。
  - `.claude/rules/frontend-test.md` §2・§3 に、それぞれ「Red が無いので tdd.md 3.0 に従う」の1行を追加（本文は書かない）。
  - `.claude/rules/testcode.md`「テスト作成」節に同趣旨の1行を追加。
- **なぜこの範囲か（重要・スコープを広げないこと）**: 「全緑を疑え」を**格言として単独で入れてはいけない**。websystem は厳格TDDで、**最後に全緑なのが正しい姿**だからノイズになり、守られないルールが1本増えるだけになる。**Red が取れない場面に限定した条件付きルール**として入れる。
- **効果の正直な見積もり**: 上記の実例で見つかったのは「バグ」ではなく**緩いアサーション**。バグ3件を見つけたのは mutation ではなく「テストを書いたこと自体」だった。したがって本ルールの効果は *バグ発見* ではなく **テストが将来にわたって嘘をつかないこと**。費用は1節＋2行なので割に合う、という判断。
- **今後の判断ポイント**: (1) websystem のみで良いか（website にはテスト規律が無いため対象外と判断済み）。(2) 「わざと壊す」を手順として書くか、`git stash` 等の具体手順まで書くか（現状案は手順を書かず「壊したら必ず戻す」の1点だけ縛る）。
