# 経営会議（board）決定台帳 — source of truth

> **役割**：会社の向かう先について **社長が決めたこと** を1行ずつ残す台帳。
> 運用ルール＝[rules/modes/board.md](../../rules/modes/board.md)。掲示板・レポートはこの台帳に合わせる（**二重台帳にしない**）。
> **読むタイミング**：`/board` の起動時に `python3 bin/board-brief.py` が機械で読む。人が全文を読む必要は無い。

## 規律

1. **決めたことだけ書く**。検討中・アイデアは書かない（それは会話の中に置く）。
2. **1決定＝1行**。表の行だけが決定として扱われる（地の文・箇条書きはツールが拾わない＝triage と同じ制約）。
3. **`見直し` は open の行では必須**。決めっぱなしにしないための期日で、その日が来たら board が必ず再検討する。
4. **行を消さない・書き換えない**。取りやめは `dropped`、置き換えは `superseded:D-NNN` で**状態を変える**（判断の履歴を消さない）。
5. **遡って過去の決定を作らない**。この台帳は 2026-09-06 から始まる。それ以前の決定は `site/business/goals.html`・`data/partner/milestones.md` が持っており、**後から当時の判断を捏造しない**（partner.md の月次レビューと同じ規律）。
6. **実体（取引先名・生々しい金額・人の話）は `data/board/private/` へ**。この台帳は git 追跡下にある。

## 詳細（根拠・経緯）

> 1行では足りない決定だけ、`### D-NNN` の節を作って根拠を書く。**全部に書かなくてよい。**
> ツールはこの節を読まない（人が読むための場所）。

### D-001 HP制作への積極営業をやめる

**社長のご発言（2026-09-06 経営会議 #1）**：「あえて取れるものを減らすつもりはありませんが、**積極的な営業はしない**という意味です」「AIが出てきて、ホームページ作成は割に合わない。ただ、**入口としてはターゲットが広かったので悪いものではなかった**。引き続き続けてもいいが、社員がそれを全て対応できる状態にする必要がある。メインの事業としては、**システム開発や AI導入やフォローの事業**をしていきたい」。

**なぜ board で決めたか**：`goals.html` の G0 は 2026-05-08 から「システム制作・運用をメイン事業へ転換」と書かれているが、**「何を減らすか」が一度も書かれていなかった**。増やす側だけが書かれた目標ツリーは、社長の時間の配り方を変えられない。本決定が初めて減らす側を置く。

**⚠️ 誤読しないこと**：これは受注を絞る決定ではない。**絞るのは営業の矛先だけ**で、持ち込まれるHP案件は従来どおり受ける。partner が「HP案件を断ってください」と督促するのは誤り。

**測り方**：新規の営業活動（提案・資料・LP・広告・セミナー）が、HP制作向けか／システム開発・AI導入・フォロー向けか。

### D-002 G0.4 の数値目標を撤廃し、週末の仕分けへ差し替える

**撤廃の理由**：「社長保有率70%以下」は**分母に振られる指標**だった。2026-09-04 に comms→ToDo の自動起票が動いて29件が可視化された結果、**良い施策を打ったのに指標は悪化した**（4サイクル連続100%）。行動を歪める指標は、判断材料にならない。

**差し替え先に件数目標を置かない理由**：社長ご判断＝「件数というよりかは、どういったものを社員に渡していけるかだと思っています」。かつ実績が**ゼロからの立ち上がり**で、目標値を先に置くと捏造になる（数字を推測で埋めない＝board の規律）。まず3ヶ月 実績を数え、2026-12-01 の見直しで目標値を置くか判断する。

**渡す瞬間（ここが要）**：社長ご指定＝**週末（土日）の時間のあるときに仕分ける。必須事項ではなく翌週へ送る可能性はあるが、1ヶ月に1回は必ず仕分ける**。
- 柔らかい頻度（毎週末・任意）＋**硬い下限（月1回）**という設計。
- **⚠️ トリップワイヤ＝1ヶ月 仕分けが1度も行われなければ赤信号**。宣言ではなく機械で見張る（→ 実装は未着手。`board-brief.py` か partner のどちらが持つかは 2026-10-01 の見直しで決める）。
- 4サイクル連続0件だった原因は意思ではなく、**渡すかどうかを見る瞬間が決まっていなかった**こと（請求漏れ149件・「印を付ける瞬間が決まっていない」と同じ型）。

### D-003 外注は常設の枠にしない

**社長のご発言**：「外注にお願いできる事項は限られている。また**外注に依頼するための社員は必要、私がそれをするのはコスト**。社員ができる範囲は社員が、仕事が回らなくなった場合は外注という判断。**あふれるほどに仕事取れる、作れるのがよい**」。

**🔴 partner の前提が誤っていたことの確認**：partner は 2026-09-03〜09-06 の4サイクル連続で「外注へ1行送る（3分）」を今日の一手に出し、**9日間で1度も実行されなかった**。board は当初これを「判断コストがボトルネック（枠・単価が未定だから3分が3分にならない）」と診断し、常設枠の設置を推薦したが、**誤診だった**。真因は**発注役が社長になっていたこと**そのものであり、外注に出すこと自体が社長の時間を食う限り、何度督促しても出ない。

**partner への影響**：**社長への「外注へ1行」督促は本決定をもって止める**。外注が必要な局面では、督促先は社長ではなく「社員が発注できる状態か」を問う向きに変わる。

### D-004 採用は期日を切らず、判断の仕組みを作る

**社長のご発言**：「**社員がいている間が質の高い採用ができる**と考えてる。**焦っての採用は一番よくない**。採用判断の仕組みが必要」。加えて前提確認への回答＝「今のところやめるという話は出てません。週に1から2回程度在宅ですることを考えています。本人も続けたいと言っている。**体調面のことなので、いつ何が起こるかはわかりません。なので、バックアップというか、保険として次の人を作っておきたい**」。

**読み取り**：「採用しない」ではない。**「採用はする・焦らない・だから引き金を先に決めておく」**。いつ何が起こるか分からない事象に備えるのが保険であり、**引き金を先に決めておくことが保険の本体**である。基準が無いまま「焦らない」と「保険が要る」が同居し続けると、どちらにも動けない。

**降ろし方**：社長が別ウィンドウで `claude` を立て「**board の D-004 を読んで**」と言う。Main が1枚にまとめる。中身は3点＝①どうなったら動くか（引き金）②どんな人か（人物像・要件）③いつ動くか（リードタイムから逆算）。**採否そのものは board でも Main でもなく社長が決める**。

**⚠️ 個別の事情・お名前は書かない**（A-063 と同じ扱い）。本節に残すのは経営判断に必要な範囲のみ。

### D-005 セッション間の受け渡しは既存 mailbox を使う（新設しない）

**きっかけ**：社長のご指摘＝「今立ち上がっているセッションであれば直接通信して渡せるが、動いていないセッションと通信するにはメールボックスのようなものが要る」「誰から誰というのは書かれている？ main→finance とか、逆に finance→main に返すようなことができれば」。

**🔴 board 側の誤りを2つ訂正した（この決定の前提）**：
1. board は当初「`bin/board-brief.py` に `--for <降ろし先>` を足せば足りる」と推薦した。これは **board が唯一の差出人**という前提に立っており、社長がお求めの **任意のモード間・双方向** を満たさない。
2. board は「既存の mailbox（`site/tools/mailbox/`）は別マシン専用」と述べたが、**誤り**。`bash bin/mailbox.sh local-send --from <自分> --to <相手>` が同一VPS内の内部調整用に実装済みで、HTTP を通さず `data/mailbox/new/` へ直接投函できる（`rules/modes/mailbox.md` L119）。

**実測（2026-09-06）＝器はすでに全部そろっている**：
- 総メッセージ 600通超・**宛名20個が稼働中**（partner / hanasaka-main / overseer / talk / memo / hp-loop-* / web-hanasaka / *-dev）
- **from も to も記録される**。往復の実例あり（`hp-loop-yoshida → yoshida-dev` とその逆便）
- スレッド（`--thread`）・承認ゲート（`--needs-approval` → `hold/` で社長 approve 待ち）・処理済み（`done` で `new/` → `cur/`）まで実装済み
- ⇒ **`board-brief --for` は不要**（mailbox が双方向で上位互換）

**決めた運用（3点）**：
1. **宛名に `board` と `finance` を追加する**。同一VPS内の `local-send` で使う限り**トークン登録は不要**（別マシンから送る場合のみ `$known_agents` への登録が要る）。
2. **各モードの起動手順に「自分宛の未読を見る」1行**を入れる。ポストはあるのに読む習慣が無いのが穴だった。
3. **使い分けを一本化する＝「`ListAgents` に居れば直接メッセージ、居なければ mailbox」**。⚠️ 二重配管にすると、どちらを見ればよいか分からなくなる。

**⚠️ 未解決（board の担当外・overseer へ）**：`data/mailbox/new/` に **未読83通**が滞留している。

**yoshida-dev 宛は数十サイクル分が積み上がっており、読まれていない疑いが濃い**（[[project_cross-machine-mailbox]]＝沈黙の典型原因は先方 `.env` の設定漏れ）。`hanasaka-main` 宛2通は VPS 内なのに未読。
