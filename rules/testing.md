# テスト・品質担保ルール（TDD 適応形）

> **version 0.1**（2026-08-10 社長指示「TDDなどの品質担保の手順が無ければ、claude-rules の websystem を参考に必要なルールを作って」で新設）｜ changelog はファイル末尾。
> 出自＝`claude-rules/websystem/rules/modes/tdd.md`（RGBC サイクル・三者整合性チェック）を、このリポジトリの実態
> （bin/ の bash・python ツール＋無人 cron ループ＋Markdown ルール）に適応させたもの。**websystem の BDD シナリオ・
> test.csv はこのリポジトリでは使わない**（Web アプリでなく運用ツール群のため＝下記 §5 が代替）。

このリポジトリの品質事故は、ほぼ全部が**「無人ループの中で静かに壊れる」**形で起きてきた
（許可リスト片形欠けで配信5日停止／文字コード誤判定で本文2,562字が黙って消失／宛先を見ない蒸留が
他人宛の依頼を社長ボールに9件化けさせた／「サボり」誤判定の冷却が社長の返信を8時間眠らせた）。
だからここでのテストの目的は網羅率ではなく、**「静かに壊れる経路を機械で見張ること」**にある。

---

## 1. 適用範囲

| 対象 | 扱い |
|---|---|
| `bin/` のツールのうち **§2 の必須条件**に該当するもの | **回帰スイート必須**（`bin/test-<name>.sh` または `.py`） |
| 1回きりの調査・変換スクリプト | 不要。ただし**ファイル名を `_tmp_` 始まり**にして区別する（済んだら削除） |
| ルール（`rules/`・Markdown） | テストコードは書けない＝**§4 の三者整合と機械トリップワイヤ**で担保 |
| 掲示板・草案 HTML（`site/`） | テスト不要。ただし公開前に `curl` で HTTP 200 と生成サイズを確認する（実践済みの型） |

## 2. テストが必須になる条件（1つでも該当したら）

1. **無人ループ（cron・tick）から呼ばれる**
2. **状態ファイルを書く**（カーソル・マーカー・台帳・ロック等＝壊すと巻き戻し/二重処理が起きる）
3. **判定ロジックを持つ**（宛先・冷却・金額照合・文字コード・許可リスト等＝間違いが静かに伝播する）

→ 該当する新ツールは、**本体と同じコミットにテストを同梱する**（実例＝`comms-who.py` と `test-comms-who.sh` を同時に作成・35項目）。「あとで書く」は書かれない。

## 3. 直し方の手順（RGBC のこのリポジトリ版）

websystem の Red→Green→Blue を、バグ修正・機能追加の両方に使う：

1. **🔴 Red＝直す前に、失敗を再現するテストを書く**。
   バグ報告を受けたら、まず「その入力でテストが落ちる」ことを確認してから直す
   （実例＝bottom-post のメールが0字になる・`b"\x80..."` が utf-16 で「肀肀」に化ける・
   `## 除外しない` が除外扱いになる——すべて先に再現ケースを固定してから修正した）。
   **再現できないうちは直さない**（推測修正は別の場所を壊す）。
2. **🟢 Green＝テストを通す最小の修正**。テストコード側は変えない。
   既存テストの期待値が「古い仕様の追認」だったと判明した場合だけ、**理由を書いて**期待値を反転する
   （実例＝「daily はクールダウン対象外」の assert が Codex 🔴 で誤りと確定→反転）。
3. **🔵 Blue＝全スイートを流してからリファクタ**。重複の集約は挙動不変で行い、また全スイートを流す。
4. **コミット**は `/commit-pipeline`（Codex クロスレビューの提案・混入チェック込み）。

## 4. 三者整合（websystem「三者整合性チェック」のこのリポジトリ版）

websystem は「仕様書⇄test.csv⇄実装」を突き合わせる。ここでは対応物が違う：

```
ルール本文（rules/modes/*.md の宣言） ⇄ 実装（bin/・フック・cron） ⇄ テスト（bin/test-*）
```

- **3点のどれかを変えたら、残り2点も同じ変更に追随させる**（変更履歴に3点の対応を書く）。
- **宣言だけのルールを作らない**＝「スキップ不可」「必ず流す」と書くなら、機械の担保
  （tick での事前生成・事後検査・フック拒否・トリップワイヤ）を対で用意する
  （[[feedback_north-star-lens-not-filter]]「無人ループの義務は宣言でなく機械トリップワイヤで」）。
  実例＝comms の宛先把握は文章指示だけでなく `comms-tick.sh` が起動前レポート生成＋事後の 〔→〕検査を持つ。
- 食い違いを見つけたら**推測でどちらかに寄せない**＝どちらが正か社長に確認（websystem と同じ）。

## 5. 手動確認の扱い（test.csv は作らない）

このリポジトリに test.csv は導入しない（器を増やさない・[[feedback_gate-dont-degrade]] と同じ思想）。代わりに：

- **自動テストでカバーできない確認**（Slack 実配信・ブラウザ目視・本番 cron の初回発火・外部 API 実打）は、
  `/commit-pipeline` ステップ1の報告に **「👀 手動で確認が要ること」欄**として明示する（記録と提示の分離＝
  websystem create-test.md の原則だけ持ち込む）。
- 本番の初回発火は**日時を言って予告する**（実例＝「明日 06:55 に初の自動取得が走ります」）。
  黙って本番で試さない（automation.md §3「手動テスト→合意→自動化」の順は不変・あちらが正）。

## 6. テストの書き方の規律（8本のスイートで実証済みの型）

1. **本番のファイルに触れない**＝一時ディレクトリに書き先を差し替え、
   **「書き先が一時ディレクトリの外なら即 exit 2」のガードをテスト自身に入れる**（test-calendar-fetch の型）。
2. **cron 相当の空環境でも流す**＝`env -i HOME=... PATH=/usr/bin:/bin` で全モードが正常終了することを確認
   （対話環境でだけ動くツールを無人ループに乗せない）。
3. **許可リストは4形セット**＝`bin/x`・`bash bin/x`・`python3 bin/x` とその `:*` 形。
   片形欠けは無言停止する（[[reference_allowlist-bash-prefix-gap]]＝実害5日の前例）。テストではなく点検項目。
4. **出力に固有名詞・秘密値を出さない**＝テストデータは架空名。実データで検算するときは表示をマスクする
   （◯◯・●● 置換）。`--stats`（件数のみ）モードを持つツールはそれをログ用の正とする。
5. **合否は終了コードで返す**（合格 0／不合格 非0）＋末尾に「合計: 合格 N ／ 不合格 M」の1行
   （既存8本と同じ書式＝将来まとめ実行するときに機械で読める）。
6. **境界を固定する**＝「実機で動いた」は当日のデータでたまたま通っただけ
   （test-calendar-fetch 冒頭の注記が教訓の原文）。BOM・空・重複・壊れた JSON・引用の閉じ忘れ・
   タイムゾーン・複数日またぎのような**静かに壊す入力**を必ずケース化する。
7. テストファイル冒頭に**契機（どの事故・どのレビューで生まれたか）と「触ったら必ず流すこと」**を書く。
